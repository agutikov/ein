# The ein-lang grammar: `ein.l` and `ein.y`

> **This is the source of truth for what parses.**
> [`01_grammar.md`](01_grammar.md) explains intent and structure — the
> terminal table, the form set, what each declarator means. This file is the
> grammar.
>
> **§1's and §2's blocks are the grammar the engine parses with**: the
> parser generated by grmtools from
> [`ein-ir/src/ein.l` and `ein.y`](../../../../ein.rs/crates/ein-ir/src/ein.y)
> (`ein_ir::grammar`), the only parser since M1f S1f.5.5's swap (T1f.5.5.4,
> 2026-11-09). The blocks are written from the two files by
> [`ein-ir/tests/grammar_pages.rs`](../../../../ein.rs/crates/ein-ir/tests/grammar_pages.rs)
> since T1f.5.5.5, which fails when they differ (`EIN_BLESS=1` rewrites them),
> and the prose around them is restated to them since T1f.5.5.7: where the two
> disagree, the blocks are right. Until the swap the engine parsed by
> recursive descent (`ein-ir/src/{lex,parse}.rs`), and this page was a W3C
> EBNF written by hand beside it, held to it by a decision table (the page's
> title, *in EBNF*, until T1f.5.5.7).
> [§5](#5-what-keeps-this-document-honest) says what pins the parser's
> decisions now.

**Notation.** The two blocks are the two files as grmtools reads them:

| | |
|---|---|
| §1, `NAME ::= regex` | a lexer rule: the token's name, and its regular expression in Rust's `regex` syntax (`[a-z]`, `[^"\\]`, `\(`, `{0,5}`, `?`, `\|`); a quoted name, `'rule'`, is a token that is its own text |
| §1, `/* in …; then …; "…" */` | the start conditions the rule is tried in (every rule is tried in `INITIAL` unless it says otherwise), the one it enters, and the name a parse error gives the token (`%epp`) |
| §2, `A ::= B C \| D` | a Yacc production as `cfgrammar` reads it: concatenation, alternation, and `/* empty */` for the empty alternative; a list is a left-recursive rule, `Names ::= /* empty */ \| Names Name` |
| §2, `'x'`, `NAME` | a token, by the name of the lexer rule that makes it |

The lexer and the parser are separate layers, and the boundary between them
is the usual one: the lexer turns the text into tokens before the parser
reads one ([§3](#3-gone) says what this page said until the swap).

## §1 Lexical grammar

The lexer, `lrlex`, tries every rule its current start condition allows at
each position and takes the **longest** match; between two matches of one
length, the rule written first. Every terminal is ASCII-anchored: a
non-ASCII character can appear only inside a string (`TEXT`) or a comment.
Names are ASCII, forever (the user, 2026-11-07); a string is natural-language
text, and any Unicode (fact 4).

Five terminal facts that are load-bearing and easy to lose:

1. **A reserved word is a token only as a whole word.** The twelve words
   no name may be and the position words (`ein_ir::grammar::RESERVED_WORDS`
   and `POSITION_WORDS`) are rules written before `NAME`, and `NAME` is
   longest match: `neq` is the token `'neq'`, a tie the earlier rule wins,
   and `neqw`, `neq_test`, `neq-1`, `rule-x`, `rule.x` and `not-a` are each
   the one `NAME` they spell, wherever they are written. The eleven position
   words, `relation`, `step`, `eq`, `absent`, `false`, `true`, `open`, `model`,
   `region`, `merged` and `owing`, are tokens of their own and names too,
   wherever §2's `Name` goes; the twelve reserved words are never a name.
   A keyword is `:` and
   a run of name characters the same way: `:why` is the token `':why'`, and
   `:where` a `KEYWORD`, which no production of §2 takes, so a keyword a form
   does not take is a parse error that says so (S1f.5.11's ruling). *Since
   M1f S1f.5.5's swap* (2026-11-09), on S1f.5.4's ruling of 2026-11-06 (the
   name rule, below). From M1e2 S1e2.2.22 (2026-11-05, the user's ruling on
   [Q-M1e2.17](../../../../plans/m1e2_correctness/open_questions.md#q-m1e217--where-does-a-keyword-end)
   (i)(a) and (ii)(a)) to the swap a reserved word's literal ended at a word
   boundary, a `WordChar` being a letter, a digit, `_` or `*`, so `neqw` was a
   name and `(neq-1 ?x)` the keyword `neq` and the integer `-1`; the swap's
   name rule, in which `-` and a digit are name characters, overrides (i)(a)
   (`grammar_decisions`' `a_keyword_is_a_whole_word_in_every_place`: 348
   parses read `keyword-1` as the name it spells, where 435 read the keyword
   and `-1`). Until S1e2.2.22 the parser matched a literal as a prefix and
   tried the keyword reading first, so a name that started with a reserved
   word was read as the keyword and the rest of the name wherever the rest
   fitted the keyword's form: `(neqw ?x)` in a rule was the guard `(neq w ?x)`
   and stored `(neq w a)`, `(relationship a b)` declared a relation `ship`,
   and `(trace (stepx …))` was the step `x` (W22,
   [`corpus/wrong_answers.toml`](../../../../corpus/wrong_answers.toml)).
2. **A bare `_` and `?_` name nothing** (M1f [S1f.5.1](../../../../plans/m1f_hypothesis_and_documentation/p1f.5_the_no_owner_items/s1f.5.1_bare_underscore_refused.md), on the
   user's ruling of 2026-11-06, [Q-M1e2.22](../../../../plans/m1e2_correctness/open_questions.md#q-m1e222--does-ein-need-a-wildcard)). `UNDERSCORE` and
   `VARUNDERSCORE` are tokens no production of §2 takes: they are there so
   the parse error can say why, wherever either is written, with the note
   *`_ is reserved and names nothing: where any value will do, write a
   variable used once`*. Anywhere else in a word `_` is a name character:
   `_a_in_b_`, `_______01`, `A________B` and `__closed__` are names and
   `?_x` a variable. **Until S1f.5.5's swap** `WILDCARD`, a `_` no word
   character followed, was a token of its own, and `__dunder__` atoms lexed
   as `SYMBOL` through `(?:__)?` and a letter, so `_x` and `__` were no
   token: in a rule's pattern `_` matched any value and bound nothing (M1e2
   S1e2.2.20), as a relation, a guard's argument or a premise it was refused
   at load, and in a fact, a nested fact or an activator it was dropped in
   silence (W-22, W29). The AST's `Wildcard` node and the compiler's
   `Slot::Any` went with S1f.5.1's T1f.5.1.3 (`ef5374a1`).
3. **There is no `RANGE`, and no `INT`** (M1f
   [S1f.5.3](../../../../plans/m1f_hypothesis_and_documentation/p1f.5_the_no_owner_items/s1f.5.3_range_retired.md),
   2026-11-08, and S1f.5.5's swap): Ein has no numbers and no ranges, on the
   user's ruling of 2026-11-06
   ([Q-M1e2.24](../../../../plans/m1e2_correctness/open_questions.md#q-m1e224--are-there-numbers-in-ein)),
   and `1..5` and `7` are names (fact 5). From S1f.5.3 to the swap `1..5` was
   the `INT` `1` and then `..5`, which no terminal matched, so the parse
   stopped at the first `.`. Until S1f.5.3
   `RANGE ::= [0-9]+ '..' ( [0-9]+ | '*' )`, *UML-style cardinality* nothing
   read, was tried before `INT`: in a fact it stored the name `1..5`, as a
   keyword's value it was dropped, and in a rule the loader refused it (M1e2
   S1e2.2.20).
4. **A string is natural-language text, with five escapes and `\u{…}`**
   (M1f [S1f.5.2](../../../../plans/m1f_hypothesis_and_documentation/p1f.5_the_no_owner_items/s1f.5.2_strings_are_natural_language.md),
   on the user's rulings of 2026-11-06,
   [Q-M1e2.23](../../../../plans/m1e2_correctness/open_questions.md#q-m1e223--what-is-a-string-for)).
   `TEXT` is the value of `:why`, `:source` or `:goal-text` and nothing else
   (`ein.y`'s `Text`): written anywhere a value goes it is a parse error at the
   string, with a note saying so, and the name written bare is what it meant.
   It holds any character but `"` and `\` as itself, a raw newline among them,
   and reads `\n` `\t` `\r` `\"` `\\` and `\u{…}`, one to six hex digits
   naming a Unicode scalar value, 0 to 10FFFF and not D800 to DFFF (`\u{1F993}`
   is 🦓). Any other escape, `\x41`, `\u0416`, `\u{}`, and a `\u{…}` that names
   no character, `\u{110000}` or a surrogate, make the string a `BADESCAPE`,
   refused at its opening quote with a note per escape naming it and its line
   and column (T1f.5.2.5, W38). A backslash and a newline are no escape: the
   string is a `BAD` there. **Until S1f.5.5's swap** unescaping was minimal,
   `\n` `\t` `\r` mapped and every other `\X` was `X`, so `"\d"` was `d` and
   `"\u{1F993}"` was `u{1F993}`; and a string was also a fact's argument, the
   name it spells (M1e2 S1e2.2.16), and a rule's (S1e2.2.18). Until T1f.5.2.5
   a `\u{…}` whose digits named no character read as U+FFFD, in silence.
5. **A token ends at a separator.** After any token but `(` and `)` the lexer
   is in `AFTER_WORD`, where it tries `(`, `)` and the skip rule alone: a
   space, a paren, a comment or the end of input ends a token, and anything
   else continues it. So `a?x`, `?x?y`, `a,b` and `Жук` are each one `BAD`
   token, *a token that is not a name*, and `"a"b` one `BADTEXT`, *a string
   glued to what follows*, each a parse error at the token with the file,
   line and column; none splits in silence. **The name rule** (M1f
   [S1f.5.4](../../../../plans/m1f_hypothesis_and_documentation/p1f.5_the_no_owner_items/s1f.5.4_digits_are_names.md),
   the user's ruling of 2026-11-06): a `NAME` is a run of the ASCII name
   characters `ein.l` lists, letters, digits and
   `` _ . - $ % ^ * + = < > ! & @ ~ / ' ` [ ] { } ``, and a `VAR` is `?` and such a run, so `7`, `07`, `-7`,
   `1..5`, `=`, `<=`, `a/b` and `f'` are names, each printed as written, and
   `?a.b` is a variable. Until the swap the hand-written lexer's `SYMBOL` was
   a letter and then letters, digits, `_`, `*` and `-`, a run of digits an
   `INT`, and a token ended wherever the next could start, so `a?x` was two
   tokens and `?x?y` two variables.

A stored negative, `NotFact`, takes a fact's clauses, so a *derived*
`(not …)` fact's provenance (`:rule type-exclusivity :using ((c10 a))`)
attaches as a fact's does. A `(not …)` in a `:match` or an `:assert` is a
`Connective` or a `Conclusion` and takes no clause: a keyword pair there is a
parse error (S1f.5.11's ruling). Until S1f.5.5's swap the hand-written
grammar's `NotForm` carried trailing `KwPair*` wherever it was written, and
the loader rejected them in `:match` and `:assert` position.

Each form's keywords are its own productions (`RelationClauses`,
`RuleClause`, `QueryClause`, `SolveClause`, `ConfigClause`, `ImportClause`,
`StepClause`, `FactClause`), the lists of S1f.5.11, and each keyword's value is
the production after it: a claim is a `Claim` or a `RegionClaim`, a flag a
`Bool`, a `:hrules` value `Hrules`. Until the swap every form took
`KwPair*`, a keyword and any value, and the loader read each form's own
([`01_grammar.md` § The keywords each form takes](01_grammar.md#the-keywords-each-form-takes)).

## §3 (gone)

*Why this is not a plain CFG over a token stream* was this section until
T1f.5.5.7 (2026-11-09), and it described the hand-written parser: it had no
scanner pass, but asked at each position whether the terminal it wanted
started there, so a word lexed by what was being parsed, and at a head where
both could match it tried the literal reading before the `SYMBOL` reading
(`lex.rs`' `LITERALS` table). So `(rule.x A)` was a parse error, the literal
`rule` and then `.x`, and `(relation)` a fact. **Since S1f.5.5's swap §2 is a
plain grammar over §1's tokens**, with no lookahead into the text and no
contextual tokenizing: the lexer runs first, longest match (§1, fact 1), and
the parser is an LR(1) parser `lrpar` runs over tables `lrtable` builds by
Pager's method, from `ein.y`, at build time, a conflict failing the build
(`ein-ir`'s `build.rs`). `(rule.x A)` is a fact of the relation `rule.x`, and
`(relation)` is a parse error, a declaration needing a name (`DeclName`).

## §4 What the grammar deliberately does not enforce

Everything below parses and is refused later, by the loader
([`from_ir.rs`](../../../../ein.rs/crates/ein-ir/src/from_ir.rs)) or by the
compiler. A parse error and a load error are different exit paths with
different messages, and the corpus has a fixture directory for each
([`examples/broken/`](../../../../examples/broken/), and its `load/` and
`compile/`).

> **What those messages look like is specified.** A parse error is one line
> per error recovery reaches, `file:line:col: unexpected X`, the token's name
> after it where it has one, then the error's notes and at most three ranked
> repairs and a count of the rest; a report cut at the recovery budget says
> where. A loader error about a top-level form ends `at None`. Both are
> defined behaviour, stated in
> [`defined_behaviour.md` §1](../../defined_behaviour.md), and every
> `.expected` file under `examples/broken/` is baselined against them.

- **That a form's keywords are written, and once.** The grammar states which
  keywords each form takes (§2) and refuses any other, but takes them in any
  order and number: a rule with no `:match`, or with two, parses, and the
  loader refuses it (`(rule r) missing :match or :assert`). A query takes at
  least one clause of its four, any one (`QueryClausesPlus`).
- **What a claim names.** An expectation's facts are a fact's shape at the
  parse (`ClaimFact`); that the relations it names exist, and that it names
  the goal's, is the loader's.
- **Arity, ground-vs-pattern, and type-checking** of a fact's arguments
  against its `(relation …)` signature.
- **Unbound variables**: a `:assert` variable that no `:match` premise binds,
  and a guard on a variable no premise before it binds
  ([`defined_behaviour.md` § 4.9](../../defined_behaviour.md#49-a-rule-shape-that-reads-nothing--m1e2-s1e2224)).
- **What a macro's body expands to.** A `Template` takes any head at any
  arity, so a premise that is a name, an `(absent …)` with two premises or a
  conclusion that is a bare variable reach the loader and the compiler through
  a macro, which refuse each (S1f.5.5's T5 kept the twelve lines a program
  still reaches that way, `grammar_pages::the_lines_the_grammar_does_not_cover_are_still_reached`).
- **Where an `(or …)` sits, how many variables a clause writes, and a goal's
  relations.** `Connective` takes an `(or …)` wherever a premise goes, so an
  `(or …)` written as a premise of an `(and …)`, an `(absent …)` or a
  top-level `(or …)` parses; so do a `:match` or a `:goal` of any width, and a
  goal's premise whose relation is a variable (`PremiseHead`'s `Var`). The
  loader refuses each since M1f S1f.5.21, a macro's expansion included; until
  then the compiler did, where it compiled a plan, so a command that never
  compiled it answered
  ([`defined_behaviour.md` § 4.15](../../defined_behaviour.md#415-the-compilers-refusals-a-program-reached-at-load--m1f-s1f521)).
- **The kernel's names.** A dunder, `__closed__` or `__symmetric__`, is a
  `NAME` the loader refuses where a program binds one (Q-M1f.7 (b), T11),
  and `open` placed beside another conclusion or inside one is the loader's
  (`validate_open`); the computed predicates `eq` and `neq`, and `eq`'s arity
  through a macro, are the compiler's
  ([`06_reserved_names.md`](06_reserved_names.md)).

## §6 Derived artefacts

M2's GBNF for constrained LLM decoding is derived from this grammar
([`plans/ideas/01`](../../../../plans/ideas/01-self-modifying-constraint-language.md),
[S2.2.3](../../../../plans/m2_nl_to_ir/p2.2_formalizer/s2.2.3_gbnf.md)). The
source is `ein.l` and `ein.y`, which §1 and §2 print, read by grmtools'
public readers as `grammar_pages.rs` reads them: a lexer rule's regex and
start conditions, and each production's alternatives. GBNF has neither
longest match nor a start condition, so how a reserved word stays out of a
`NAME` and how a token ends at a separator are the generator's to write.
