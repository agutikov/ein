# 11 — Shared assets: one stdlib, one corpus

**Settles:** where the `.ein` library and the example corpus live, how the
engine finds them, and how drift is detected.
**Phase:** [P1a.0](../README.md#p1a0--corpus-and-shared-assets), stage
[S1a.0.3](../README.md#s1a03--shared-stdlib-and-examples).

---

## 1. Why this is a correctness requirement

A forked stdlib makes every result ambiguous: a changed answer would
read as "the engine moved" when in fact the *program* did. The
stdlib is 1 231 lines of ein-lang across seven modules
(`algebra` 454, `slots` 439, `bijection` 143, `elim` 76, `typing` 63,
`closure` 35, `macro` 21), and `zebra2.ein` imports from three of them.
It is not test data — it is part of the semantics under test.

The same argument holds, more weakly, for `examples/`: it is the corpus,
and a corpus kept in two places is two corpora.

---

## 3. Decision

**The stdlib lives at repo-root `stdlib/`, the single source of truth.
No crate keeps a checked-in copy.**

```
stdlib/
├── README.md
├── MANIFEST.sha256        ← one line per module: <sha256>  <name>.ein
├── algebra.ein
├── bijection.ein
├── closure.ein
├── elim.ein
├── macro.ein
├── slots.ein
└── typing.ein
```

### Resolution order

1. `$EIN_STDLIB` — an explicit override. Always wins. It is what points a
   run at a stdlib that is not the checkout's, which is how a test proves
   the resolution order rather than assumes it.
2. **The repo checkout**: `stdlib/` found by walking up from the
   binary's location and confirmed by the presence of
   `MANIFEST.sha256`. A source checkout is always authoritative, so
   editing a module takes effect without a rebuild or reinstall.
3. **The embedded copy** — the `include_dir!`-embedded tree in the
   binary.

Step 3 keeps the distribution promise intact: `ein` ships as one
self-contained binary.

### Packaging

`include_dir!("$CARGO_MANIFEST_DIR/../../stdlib")` in `ein-ir`, exposed
as an in-memory filesystem behind the same `StdlibSource` trait the
on-disk path implements.

### Drift detection

- `stdlib/MANIFEST.sha256` is regenerated by a script and checked in.
- CI runs `stdlib-check`: the manifest matches the files, and the
  embedded copy matches (a build-time `const` digest compared against the
  manifest).
- The manifest hash lands in `.einb`'s `META`
   ([10](10_binary_format.md) §4), so a stdlib edit invalidates every
   derived artefact automatically.

## 4. The corpus

`examples/` stays where it is. What is added is an explicit **manifest**
so every reader of the corpus enumerates the same entries with the same
run matrix:

```toml
# corpus/corpus.toml
[[entry]]
path   = "examples/zebra2.ein"
group  = "positive"
runs   = ["solve", "solve -e", "solve -n 3", "solve --trace", "saturate",
          "render rules", "render constraints", "render lattice"]
levers = "all"          # the SolverConfig on/off matrix
slow   = true

[[entry]]
path   = "examples/broken/unclosed_paren.ein"
group  = "parse-negative"
runs   = ["parse"]
```

- Generated once from the tree, then maintained by hand; a CI check fails
  on any `.ein` under `examples/` or `stdlib/` that has no entry, so the
  corpus cannot silently miss a file. This is the mechanical version of
  the rule [`examples/README.md`](../../../../examples/README.md) already
  states in prose ("one line per file / sub-dir").
- `slow = true` entries run in the nightly tier only.
- The load-negative fixtures live in **`examples/broken/load/*.ein`**,
  each with its expected message beside it, so the text a test asserts is
  a corpus file rather than an inline source string.

## 6. Acceptance

- `EIN_STDLIB=/tmp/empty ein solve examples/zebra2.ein` fails with a
  clear "module not found" (proving there is no hidden fallback).
- Editing `stdlib/algebra.ein` in a checkout changes the engine's
  behaviour without a rebuild.
- `stdlib-check` fails on a deliberately corrupted copy.
- The corpus completeness check fails when a new `examples/**/*.ein` is
  added without a manifest entry.
