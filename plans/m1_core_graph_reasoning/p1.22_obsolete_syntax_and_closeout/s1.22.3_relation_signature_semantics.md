### Q1 — the signature's dual role

The kernel claim "no internal type system" **holds** (since S1.7.23), but
the signature is *not* inert — it plays two unrelated roles, and the split
is documented nowhere:

**As types — userspace only.** The loader mirrors every declaration as an
ordinary fact `(relation Name A B)` precisely so rules can match it
(`ein.py/src/ein/kb/from_ir.py:187-194`). Everything type-like keys off
that fact, in rules: std.bijection's typecheck stack
(`stdlib/bijection.ein:71` — `(relation ?R ?A ?B) ∧ (bijective ?R) ∧
(typecheck-hierarchy ?isa)`), std.algebra's converse domain/range check
(`stdlib/algebra.ein:292`), std.typing's hierarchy wiring. The kernel
never resolves a signature atom to anything —
`Relation.signature` is "opaque atoms… no `signature → Type` resolution"
(`ein.py/src/ein/kb/entities.py:74-78`).

**As structure — kernel, three signals.** The kernel reads the signature's
*shape*, never its content-as-types:

| signal | site | effect |
|---|---|---|
| signature **non-empty** | `inference/hypgen.py:251`, `inference/closed.py:84` | "declared domain relation" — eligible for hypothesis generation and for `__closed__` auto-inference; property/rule-name relations (empty signature) are skipped by both |
| signature **length = 2** | `inference/hypgen.py:293` | hypgen fills slots only for arity-2 (the M1 limit) |
| signature **atoms** | `inference/hypgen.py:537-541` | the declared type-role names (`Attribute`, `House`, `T`, …) are excluded from candidate *objects* — the enumerator never guesses about a type node |

Plus two ergonomic reads: the `:why` render template
(`kb/from_ir.py:182`) and the CLI signature display
(`cli/saturate.py:388`).

So the answer to "explicitly through rules or implicitly in the kernel?"
is **both, in different roles** — and the roles never mix.

### Q2 — `T` is convention, and why the slots need *some* atom

`T` is an ordinary, undeclared, unreserved atom
([`06_reserved_names.md` §Not reserved](../../../docs/kernel/ir/03-ein-lang/06_reserved_names.md)).
What is *not* said anywhere: the slots cannot simply be omitted, because
(a) the grammar requires ≥1 type atom (`ir/grammar.lark:97` —
`relation_decl: "(" "relation" SYMBOL SYMBOL+ kw_pair* ")"`), and (b) the
kernel keys hypothesis-eligibility on signature **presence** (Q1 table).
`T` is the conventional "don't care" filler; any atom produces the same
kernel behaviour. Orthogonal type systems already coexist in-tree —
`zebra.ein`'s split `type`/`instance` vs `zebra2.ein`'s unified `is-a` —
and types *of relations* are already legal facts
(`(is-a co-located EquivalenceRelation)` parses and stores; only a rule
gives it meaning), because of Q3.

### Q3 — relations are objects, with one qualification

Yes, and it is implemented, not aspirational: declarations are mirrored as
facts, property tags take relation names as arguments, undeclared fact
heads get auto-created `Relation` entities (`kb/entities.py:80-89`). The
one place the kernel treats a relation name as *not* an object is
`NameRef.category`: hypgen's candidate-object pool excludes non-`object`
categories (`hypgen.py:547`) — a tractability device, not a semantic
stratification. [`08_self_describing.md`](../../../docs/kernel/ir/03-ein-lang/08_self_describing.md)
already tells the userspace half of this story ("relation signatures are
data rules consume"); the kernel half is the missing link.

### Q4 — unary relations exist; the limits are hypgen and rendering

- **De facto**: every property tag is a unary fact — `(bijective
  color-loc)`, `(symmetric next-to)`, `(__closed__ R)`,
  `(type-hierarchy is-a*)`.
- **De jure**: a unary *declaration* `(relation R T1)` parses
  (`grammar.lark:97` accepts one type atom) and loads
  (`from_ir.py:164` requires name + ≥1 type). **Doc bug found**:
  [`01_grammar.md:84`](../../../docs/kernel/ir/03-ein-lang/01_grammar.md)
  claims "arity ≥ 2" — it contradicts the grammar it documents.
- **The real limits**: hypgen fills arity-2 only (`hypgen.py:293-294`), so
  a declared unary relation is never a hypothesis target; and the compact
  DOT view has no unary convention (the Levi-bipartite view needs none —
  a fact node with one incident edge just works).
- The "unary relation = subset" reading is exactly how the property tags
  already function — `(symmetric R)` carves the subset of
  relation-objects that are symmetric. Worth one paragraph in the graph
  chapter; it is the standard predicate-as-subset view and makes the
  property-tag idiom less mysterious.
