## Framing — half of this is already true

**"Relation declarations are just facts"** — they already are, *in
addition to* being a kernel word: the loader mirrors every declaration as
an ordinary `(relation Name A B)` fact
(`ein.py/src/ein/kb/from_ir.py:187-194`), and `:match (relation ?R …)` is
exactly how std.bijection / std.algebra / std.typing consume it today.

**The sketched `typed-binary-relation` rule exists** — not with an empty
`:match` (invalid: a rule needs a premise), but in the established
*activator fact + generic rule* idiom: `(relation ?R ?A ?B)` +
`(bijective ?R)` + `(typecheck-hierarchy ?isa)` drives the
`typecheck-arg-*` stack (`stdlib/bijection.ein:71`). The functionality is
not the question.

**The question is only the residue**: what does the kernel *word* do that
the fact alone does not, and should that residue stay kernel-side? Per
S1.22.3's census, the residue is:

| what | site | if demoted, becomes… |
|---|---|---|
| reserved-name shadow check at load | `kb/from_ir.py:172` | ? — load-time errors have no rule-space analogue |
| duplicate-declaration check | `kb/from_ir.py:176` | expressible as a ⊥-rule for *conflicting* sigs: `(relation ?R ?A ?B) ∧ (relation ?R ?C ?D) ∧ (neq ?A ?C) → false`; identical re-declaration dedupes as any fact |
| `:why` render-template capture | `kb/from_ir.py:182` | needs a home — a kw on the fact, or a separate `(why R "…")` fact |
| `declared=True` + `signature` on the entity | `kb/entities.py:92-93` | kernel keys on the *fact* instead (it already reads `(__closed__ R)` facts, so the pattern exists) |
| `NameRef.category` assignment (name is a relation, not an object) | loader | derived from fact-head occurrence — already how undeclared heads work (`kb/entities.py:80-89`) |
| grammar production `relation_decl` | `ir/grammar.lark:97` | folds into `generic_fact` |

## The two options

**(i) Keep `relation` kernel-side; record why.** The mirrored fact already
gives userspace *full* reflection — demotion buys purity, and its price is
error ergonomics: shadow/duplicate mistakes become saturation-time
contradictions (or silence) instead of load errors with a `loc`. Under
this option the decision memo states the rationale, S1.22.3's docs are the
lasting artefact, and the scratchpad question is closed with "by design,
because X" rather than code.

**(ii) Demote to a stdlib/loader-convention word.** The kernel keys its
three structural signals off the `(relation …)` *fact*; validation
becomes rules where expressible and is otherwise dropped or moved;
`:why` gets a new carrier. This is a kernel refactor of the same species
as S1.7.23/S1.7.24 — grammar, loader, entities, hypgen, closed, CLI —
and therefore **cannot execute in this phase**: P1.22's own
[README §Out of scope](README.md) rules out engine behaviour change. If
(ii) wins, this stage *designs and parks* it.

Sub-items that ride along **whichever** option wins (each is independent
engine work; the memo only records + parks them):

- **Unary hypothesis targets** — hypgen's arity-2 limit
  (`inference/hypgen.py:293`) is an M1 cut, not a design position; a
  declared unary relation is never guessed today.
- **Bare untyped declaration `(relation R)`** — currently a grammar error
  (`SYMBOL+` requires a type atom); legalising it interacts with the
  kernel's signature-presence keying (S1.22.3 census Q2).
- **Unary rendering in the compact DOT view** — the "arrow with no
  head-object" question; the Levi view needs nothing.
