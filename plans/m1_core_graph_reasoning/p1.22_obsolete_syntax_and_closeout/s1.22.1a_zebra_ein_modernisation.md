# S1.22.1a — `zebra.ein`: modernise and make it solve

**Phase:** P1.22, inserted after
[S1.22.1](s1.22.1_obsolete_syntax.md) (whose census this consumes) and
**before** [S1.22.2](s1.22.2_m1_plans_deletion.md) (the plan-folder
deletion — this stage's rules and findings must land while the M1 plans
explaining them still exist).
**Priority:** P1. **Estimate:** L (a rule-library design problem, not a
syntax sweep). **Value:** H — it converts the repo's second encoding from
a museum piece into a *second solvable model of the same puzzle*, which is
the only way to tell which of Ein's reasoning power is general and which
is an artefact of how `zebra2.ein` happens to be written.

**Origin — user, 2026-08-17** (recorded in
[S1.22.1 §The ruling](s1.22.1_obsolete_syntax.md#the-ruling-user-2026-08-16)):

> Encoding of examples/zebra.ein now IS valid!
> It is not solvable now, but because of different reasons:
> - because some of relations properties are effectively NOT implemented in
>   this formulation;
> - and plus zebra.ein produce too many hypothesis.
>
> Not because it's language is broken, but because problem ontology is not
> sufficient.

## Why this is worth doing

`zebra2.ein` solves. `zebra.ein` does not, and the difference is **not**
the language — it is the shape of the ontology each one commits to:

| | `zebra.ein` (311 lines) | `zebra2.ein` (512 lines) |
|---|---|---|
| membership | `(instance …)` ×14, `(type …)` ×7 — *undeclared* heads | `(is-a …)` ×21 |
| attribute link | **one generic** `co-located` ×10 | **five typed** `*-loc` relations (`nation-loc`, `drink-loc`, …) |
| relation properties | `symmetric` ×2, `transitive`, `type-exclusivity` | `bijective` ×5, `includes`, `adjacent-via` ×4, `bijection-hierarchy` |
| stdlib | none | `(import …)` ×2 — `std.elim`, `std.macro`, … |
| search control | none | `(config …)`, `(hrule …)` |

The engine's elimination power is keyed to **relation properties**, and
those properties are declared *per relation*. With one universal
`co-located`, there is no per-attribute functional/total structure for
`std.elim`'s domain-elimination to bite on, so nothing narrows and the
hypothesis generator enumerates a space it cannot close. That is exactly
the user's two reasons, stated in engine terms:

1. *"some relation properties are effectively NOT implemented in this
   formulation"* — `zebra.ein` cannot say "`co-located` is bijective
   **between `Nationality` and `House`**". `bijective` is a property of a
   relation, not of a relation *restricted to a pair of types*.
2. *"too many hypotheses"* — a direct consequence: with no per-attribute
   bijection to eliminate against, `hypgen` has no fixed slot structure to
   exhaust and the lattice blows up.

So the interesting question this stage answers is not "can we make
`zebra.ein` look like `zebra2.ein`" — trivially yes, by rewriting it into
typed `*-loc` relations, at which point it *is* `zebra2.ein` and proves
nothing. It is:

> **Can the same inference be expressed over the original generic
> relations, by giving the engine type-scoped relation properties?**

## Scope — the user's four asks

1. **Use the new hypothesis-filtering features.** `(hrule …)` for
   candidate generation, `__closed__` / `std.closure` where a relation's
   extension really is fixed, `(config …)` knobs
   (`enable_pre_branch_lookahead`, `enable_lookahead_kill_cache`,
   `enable_forced_positive`, `lattice_order`, `max_set_size`), and the
   S1.21.8 boundary — with guards now judged against a positive fixpoint,
   elimination rules no longer need priority-band protection to be sound,
   which widens what a rule author may write.
2. **Use the modern surface syntax, including the NL-support kwargs.**
   `:why` templates on every rule (the trace renderer interpolates
   `{?var}`), `:source` on every given clue so the contradiction frontier
   and the trace can name the clue a conclusion rests on, `(import …)` for
   the stdlib instead of hand-rolled copies. This is what makes the file
   readable as the M2 NL⇄IR round-trip target rather than as a fixture.
3. **New rules giving zebra2-equivalent inference over the *original*
   relations.** The design question above. See § Design options.
4. **Solve in time comparable to `zebra2.ein`.** Concretely: the same
   verdict (`Solution`, k=1, exhausted) within the same order of magnitude
   — the S1.21.8 baseline for an exhaustive `zebra2` solve is ~8.5 s on
   PyPy, so **under ~30 s** is the bar, and a `stop_after=1` run should be
   seconds.

## Design options for ask 3 (the real work)

Weigh at least these; the report picks one with evidence.

- **(a) Type-scoped relation properties.** Extend the property vocabulary
  so `(bijective co-located Nationality House)` is expressible — a
  property of `(relation, domain-type, range-type)` rather than of the
  relation alone. Most faithful to the user's diagnosis ("properties not
  implemented *in this formulation*"), and the most reusable: any puzzle
  with one generic link relation and several typed attribute sets wants
  this. Cost: new property arity, and every `std.elim` / bijection rule
  re-expressed with the type pair threaded through.
- **(b) Derive the typed projections.** Keep `co-located` as the authored
  surface, and let *rules* derive per-type projections
  (`(nation-loc ?n ?h) ← (co-located ?n ?h) ∧ (is-a ?n Nationality) ∧
  (is-a ?h House)`), then run the existing zebra2 machinery on the
  projections. Cheapest, and it keeps the original relations *authored* —
  but the reasoning still happens on derived typed relations, which is a
  weaker answer to the question, and it doubles the fact population.
- **(c) Reflective property rules.** Use Ein's relation-polymorphic rules
  (`(rule r (?R) …)` activated by property facts — the mechanism
  `transitive` / `symmetric` already use) to *derive* the type-scoped
  properties from `is-a` structure, so the puzzle declares intent once and
  the stdlib expands it. Most in the spirit of the language; verify the
  activation story works when the activator is a 3-ary property fact.

Record which of the three the acceptance run used, and what the other two
would have cost — the comparison is half the value of the stage.

## Tasks

### T1.22.1a.1 — Investigate → `reports/c2_zebra_ein_gap.md`

Read-only. Deliver:

1. **Load-and-saturate baseline.** Does `zebra.ein` load today? Saturate
   it and report: fact count, which rules fire, which never do and why
   (undeclared relation? no activator fact? property never asserted?).
   Quantify "too many hypotheses" — run `solve` with a small
   `max_enterings` / time budget and report the candidate count per layer
   against `zebra2.ein`'s.
2. **Property gap census.** For every elimination/bijection rule that
   fires in `zebra2` and not in `zebra.ein`, the precise reason — the
   property fact that does not exist, or exists but is not type-scoped.
3. **Option weighing** (a)/(b)/(c) above with a prototype of the chosen
   one, plus the ripple list (stdlib modules touched, whether the property
   arity change breaks existing puzzles).
4. **NL-readiness gap.** Which clues lack `:source`, which rules lack a
   `:why` template, and what the trace of a solved `zebra.ein` would read
   like — this file is the M2 round-trip target
   ([`zebra_walkthrough.md`](../../../docs/kernel/inference/zebra_walkthrough.md)).

### T1.22.1a.2 — Execute

Rewrite `examples/zebra.ein` per the report; add whatever stdlib rules the
chosen option needs; wire the `(config …)` / `(hrule …)` filtering. Add an
acceptance case so the second encoding stays solvable
(`ein.py/acceptance/` — a `Solution`, k=1, exhausted, with the same
bindings as `zebra2.ein`'s answer: the Japanese owns the zebra, the
Norwegian drinks water).

**Gate:** `./run_tests.sh` + `ruff check .` green; `zebra2.ein`'s verdict,
bindings and runtime unchanged; `zebra.ein` solves within the § Scope-4
budget. Append `## Outcome (date)` here.

## Acceptance

1. `examples/zebra.ein` is modern-syntax, `:why`/`:source`-annotated, and
   **solves** to the same model as `zebra2.ein` within the stated budget.
2. The inference runs over the **original generic relations** (or the
   report justifies, with measurements, why a projection was necessary).
3. Both encodings are in the acceptance suite, and `examples/README.md`
   describes them as *two ontologies for one puzzle* — the comparison, not
   "classic vs modern".
4. Whatever property mechanism was added is documented in
   `docs/kernel/ir/` and `docs/kernel/inference/` like any other kernel
   feature, not left as a puzzle-local trick.
