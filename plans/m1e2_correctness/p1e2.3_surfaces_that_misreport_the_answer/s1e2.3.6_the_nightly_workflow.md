## The method

1. **Run every step of the three nightly jobs locally, at this stage's HEAD,
   in the workflow's order and with its environment.** The steps are:
   - `deep-corpus`, every step;
   - `frontend-fuzz`, both seeds at `EIN_FUZZ_ITERS=1000000`, timed;
   - `benches`, `cargo bench --bench engine -- --test`.

   A failure does not stop the sweep: each step runs, and each result is
   recorded. Master has moved a long way since `e13cd09f` (the walk is
   deleted, the levers retired, the root block rebuilt). So the list of what
   fails is taken here, not inherited from the table above.
2. **Each failure understood before it is fixed.** For the mutants step,
   explain each of the eight kills: which `tests/` program now kills the
   mutant, and through which change (commit and stage). Only then
   `--bless`. Record the new score and the survivors' diff in
   `tests/README.md`'s mutation section, where 157 of 217 is the recorded
   figure. A new survivor, if one appears, is a weakened test, not a bank
   entry: it is recorded and put to the user.
3. **The workflow's prose brought up to date.** Its comments say the slow
   set is two entries and quote `-e -m 3`. That was true at M1a. Today the
   set is fourteen and `-e` is a refused option. Every number gets its command,
   date or test (Q-M1e.4), or is cut.
4. **A local runner, held to the workflow.** Add `./run_tests.sh --nightly`,
   which runs the `deep-corpus` job's steps exactly. A sibling of
   `ein-cli/tests/gate_steps.rs`, which today diffs the script against
   `per-commit.yml` only, holds the `--nightly` list to `nightly.yml`'s.
   That way the nightly can be run before a push, and a step cannot be added
   to one list and not the other. The fuzz and bench jobs get their commands
   in `AGENTS.md`'s *Running the gate* block, not in `--nightly`. Whether
   they join `--nightly` is decided by step 1's timings and recorded.
5. **The proof is local.** The user pushes, and this stage never does. So
   "green" means every step green under `./run_tests.sh --nightly` and the
   two other jobs' commands, at the stage's HEAD. The first scheduled nightly
   after the user's next push is the confirmation, and the stage's record
   says so rather than claiming it.
