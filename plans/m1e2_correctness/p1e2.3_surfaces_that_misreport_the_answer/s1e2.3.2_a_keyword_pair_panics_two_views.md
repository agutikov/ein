The program is four lines, `trace` mutated to `tracex` by the fuzzer:

```lisp
(tracex (step s1 :rule from-condition :using (c10) :derives (lives-in N H1))
  (step s2 :rule adjacent :using (and s1 c15) :derives (color-loc Blue H2))
  (step s3 :using (s2))
  (step s4 :derives (final X)))
```

**The second door is new since the survey.** `ein render program` arrived at
[S1e2.1.3](../p1e2.1_seeing_the_answer/s1e2.1.3_the_doors.md), and its help
promises *"Parsed, never loaded, so a program the loader refuses still
draws"*. Here the loader accepts the program, and the view panics.

**No other panic.** `render rules|constraints|program|kb`, `solve` (bare,
`--maximal`, `--minimal`, `--single`) and `oracle` were run over the 281
`.ein` files under `examples/`, `tests/`, `stdlib/`, `corpus/fuzz_findings/`
and `plans/m1e2_correctness/probes/`, with a 15–20 s timeout each. These two
cells were the only exit 101, 134 or 139.

### The mechanism, read in the code

[`dot_util::value_label`](../../../ein.rs/crates/ein-render/src/dot_util.rs)
labels a value node and recurses into an `SForm`'s arguments. Its last arm is
`Node::KwPair { .. } => panic!("not a value node: KwPair")`. It is `pub`, and
re-exported from `ein_render`. Two views reach it:

- **`render constraints`**: `constraints.rs:130` treats `tracex` as an
  ontology declaration, filters keyword pairs out of the form's own arguments,
  and labels the rest. The filter is one level deep. `value_label` recurses
  into `(step s1 :rule …)`, whose arguments are keyword pairs.
- **`render program`**: `ir_dot::to_dot` → `render_ontology_forms` →
  `emit_fact` → `atom_id_for_value` → `value_label`, with no filter at all.

`ir_dot.rs:344` already spells a keyword pair, as `:{key} {value}`, in
`render_note` for `(query …)` and `(solve …)` blocks.

### Why nothing caught it

The file is not a corpus file. `corpus_files()` walks `examples/`, `stdlib/`
and `tests/`. `dot_wellformed::graphviz_accepts_every_view_of_every_corpus_file`
and `corpus_shapes.rs` run every view over every corpus file, and either one
would have caught it there.

## The question

The fuzz note left it open: *"there are two defensible answers and nothing
has chosen one"*. With the second door there are three:

| | (a) `value_label` renders a keyword pair | (b) each view filters keyword pairs at every depth | (c) (b) for `render constraints`, (a) for `render program` |
|---|---|---|---|
| what changes | one arm: `KwPair` → `:{key} {value}`, as `ir_dot.rs:344` spells it | `constraints.rs`'s filter recurses, and `ir_dot`'s ontology path gains one | (b)'s filter in `constraints.rs`, (a)'s arm in `value_label` |
| what `render constraints` shows here | `(step s1 :rule from-condition :using (c10) :derives (lives-in N H1))` as a label | `(step s1)` | `(step s1)` |
| what `render program` shows here | the form as written | the form with its keyword pairs dropped | the form as written |
| a future caller of `value_label` | cannot panic | can still panic | cannot panic |

**Recommendation, mine: (a).** One change makes the `pub` function total for
every caller, present and future, and the panic class goes with it. `render
program` is *the program as written*, so dropping what was written is wrong
there, whichever option is taken. Whether `render constraints` should also
hide nested keyword pairs is a presentation choice. Its top-level filter
already makes that choice for the form's own pairs, and (a) leaves that
filter as it is.

## Ruling

**Ruled 2026-11-03: (a).** `value_label` renders a keyword pair as `:key value` for every caller, as `ir_dot.rs` already does. Both views, `render constraints` and `render program`, then draw the witness. The witness is re-checked the same day: both still exit 101 with *not a value node: KwPair*. (the user, by AskUserQuestion, 2026-11-03, on this file's question with the witness re-checked that day at `318e23b9`.)
