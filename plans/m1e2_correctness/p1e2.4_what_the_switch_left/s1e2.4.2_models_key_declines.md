# S1e2.4.2 — `--models key` declines before it allocates

**Phase:** [P1e2.4](README.md) (What the switch left)
**Estimate:** 1 day.
**Depends on:** nothing.
**Blocks:** `utils/review_bundle.py --regions` building without a process
killed.
**Status:** done 2026-11-02, all three tasks.

## Context

`utils/review_bundle.py --regions`, the first gallery built against the region
modes, ran

```
ein solve examples/saturation/type-exclusivity/pets.ein --models key
```

on 2026-11-01, and the kernel's OOM killer killed it at **6.8 GB resident,
275 GB virtual** (18:07, kernel log; commit `43a40a84` names it). A bare
`solve` on `pets.ein` describes R, 11 339 states, every one listed, and
`--models key` asks for the determining key of those 11 339. The phase README
read the cause in the code without reproducing it: `ein_render::models::separating`
builds a k(k−1)/2-bit mask per varying slot before `min_key_size`'s node
budget is consulted, so the promised `KeyOutcome::Unaffordable` never gets to
answer.

Then it did not recur. The gallery's second build, at `17422b32` the same
evening (21:53), ran the same command and it **exited 0**, and
[S1e2.1a.7](../p1e2.1a_the_solution_region/s1e2.1a.7_the_bundle_shows_r.md#numbers)
recorded that without re-measuring. So the stage starts by finding out which
is true today, and why.

## Acceptance

From the [phase README](README.md#s1e242----models-key-declines-before-it-allocates):

- The key form declines with `KeyOutcome::Unaffordable` and its reason
  **before** it allocates whenever the pair table would pass a stated memory
  bound. The bound and the reason are written where `--models key` is
  documented. A decline is an answer: exit 0, and the states are still listed.
- A test holds it: a synthetic state set over the bound declines and
  allocates no pair table, and *allocates nothing* is measured, not asserted.
- `ein solve examples/saturation/type-exclusivity/pets.ein --models key`
  finishes, declining, with its peak RSS written down with the command and
  the date.
- `--models grid`, `--diff-models` and `-p` are measured the same way on the
  gallery's largest regions, `pets`, `square-bwd/houses` and
  `syntax/arg-kinds`. A form superlinear in memory gets the same treatment,
  or a row here saying why not.
- `utils/review_bundle.py --regions` builds the `pets` page with cross-check 1
  passing.

## How it is measured

Every number below is **peak RSS** and wall, of the `ein` process alone, under
a cgroup cap so a run cannot take the machine with it:

```sh
systemd-run --user --scope -q -p MemoryMax=9G -p MemorySwapMax=0 \
  python3 peak.py OUT -- ein.rs/target/release/ein solve FILE FLAGS…
```

`peak.py` forks, `execvp`s the command with stdout to `OUT`, and reads
`wait4`'s `ru_maxrss`, the number GNU `time -v` prints as *Maximum resident
set size* (`/usr/bin/time` is not installed on the machine). A run the cap
kills is read from the user journal's `oom-kill` line instead. The machine has
31 GiB and no swap. The release build is `./build.sh`'s, `snmalloc` linked.
The whole of `peak.py`, so every number here can be re-taken:

```python
import os, sys, time
out, argv = sys.argv[1], sys.argv[3:]          # peak.py OUT -- argv…
t0 = time.monotonic()
pid = os.fork()
if pid == 0:
    fd = os.open(out, os.O_WRONLY | os.O_CREAT | os.O_TRUNC, 0o644)
    os.dup2(fd, 1)
    os.execvp(argv[0], argv)
_, status, ru = os.wait4(pid, 0)
code = f"signal {os.WTERMSIG(status)}" if os.WIFSIGNALED(status) else f"exit {os.WEXITSTATUS(status)}"
print(f"{code}  wall {time.monotonic() - t0:.2f} s  peak RSS {ru.ru_maxrss / 1024:.1f} MiB", file=sys.stderr)
```

The `--diff-models` files are written from each run's own `--json-summary`
(`mkwant.py`): *the states themselves* lists every listed state's facts under
`closes` of their relations, so every state matches. *One fact off* adds a
fact over a closed relation to each, so nothing matches and every pair is a
candidate for *near*.

- **`--models grid` and `-p` are linear.** Both hold the listed states'
  fixpoints at once (`region::Nodes::with_fixpoints`), 44 MiB over the bare
  run for `pets`. On the 64 514-state `terminus --maximal` line they are 340 MiB
  against the bare run's 233 MiB. No treatment.
- **`--diff-models` is quadratic in what it fails to match.** Matching equal
  models is a scan, O(got × want) in time and nothing in memory. Pairing
  what is left *nearest first* collects every unmatched (got, want) pair
  within its distance bound before sorting, 24 bytes each, and on *one fact
  off* that is 11 339 × 11 339 candidates. It gets the same treatment, in
  T1e2.4.2.2.

### Task T1e2.4.2.2 — One bound on both pairwise forms

**The bound** is a constant, `ein_render::models::PAIR_TABLE_BOUND`, of
**16 MiB**. It bounds what a form holds, not how long its search runs, which
the node budgets bound.

**The key form** holds, for k distinct states over n varying slots:

- one mask of k(k−1)/2 bits per varying slot and one for the full set, which
  `separating` builds;
- as many again for the search's path, one per level of depth, since a level
  holds the mask it was handed;
- **4 bytes a pair** for the order the search takes pairs in, hardest first.

So `key_pair_table_bytes(k, n) = 2(n + 1) · ⌈k(k−1)/128⌉ · 8 + 4 · k(k−1)/2`.
`by_pair`'s per-pair lists go. The order becomes a `u32` per pair, sorted by a
counting sort on how many slots separate it. The sort is stable, so ties stay
in pair order as the stable sort left them, and a node reads the separating
slots off the masks. The search visits the same nodes in the same order. It
is priced twice, and both prices come before anything quadratic is allocated:

1. **on k alone**, with n = 1, the least any key over these states could
   hold. This comes before the decision variables, which are linear in memory
   but not in time. k is counted by sorting the states' keys, `O(k log k)`.
   The first build used `distinct_by_state`'s `O(k²)` scan here, and it spent
   6.2 s of a 64 514-state line's 8.0 s before the decline.
2. **on k and n**, after the variables.

Past either, `KeyOutcome::Unaffordable` with the numbers, which the CLI prints
under *determining key — none within budget*, exit 0, the states listed above
it as before:

```
models — the determining key of every state of R
  determining key — none within budget
    the 11 339 states are 64 280 791 pairs, and the pair table that tells them
    apart holds at least 276 MiB, its size over a single varying slot: past
    the key form's bound of 16 MiB.
```

**`--diff-models`' near pairing** holds 24 bytes per unmatched (recorded,
expected) pair, and is priced the same way: past the bound it pairs nothing
near, says why in its block (`SetDiff::unpaired`), and lists every unmatched
model as missing or spurious, which is what they are. `SetDiff::agrees` reads
the same, since a near pair is a disagreement either way. Under the bound the
list is reserved whole and sorted unstably, which allocates nothing more and is
the same order, since no two candidates share an `(i, j)`.

## Notes

- **Parked, not this stage's.** Each is named where it will be read again.
  - *The forms printed after the read-out are not under the 100-line rule.*
    `read_out.md` § 4.1 cuts the read-out's listings at 100 lines and says
    nothing of `--models key|grid`, `-p` or `--diff-models`, which follow it.
    Before this stage `pets`' key table was 11 339 rows on stdout, and
    `--models grid` still prints 11 339 grids (2.2 MB, the gallery's
    `grid.stdout.txt`). It is a surface question, so it is filed for P1e2.3
    in [Q-M1e2.6](../open_questions.md#q-m1e26--does-p1e23-become-a-phase)'s
    notes.
  - *The node budget does not bound time once masks are wide.* A node
    compares, scans and ORs masks of ⌈k(k−1)/128⌉ words, so 2 000 000 nodes
    cost in proportion to k². The bound caps k², and so it caps the time, but
    the cap is high. Measured on random states over 42 Boolean slots, a
    scratch test beside `key_declines.rs`, release build, 2026-11-02:
    k = 500 spends the node budget in 7.6 s, k = 1 000 in 27.7 s, and
    k = 1 400 in **66.6 s**. All three are under the bound, priced
    1.8–14.4 MB and holding 1.5–10.9 MB, so memory is held to its price
    there too. A key the search finds is quick: 2 000 states over 12 slots,
    0.12 s. No corpus run is in this range, since there is none between 169
    states and 4 096. Counting the budget in mask words rather than nodes would
    re-calibrate which corpus keys are found, the
    [`KEY_NODE_BUDGET`](../../../ein.rs/crates/ein-render/src/models.rs)
    calibration of M1d S1d.3.3. It is filed in the
    [phase README](README.md#s1e242----models-key-declines-before-it-allocates)
    as found by this stage and not in its acceptance.
