# S1e2.4.2 — `--models key` declines before it allocates

**Phase:** [P1e2.4](README.md) (What the switch left)
**Estimate:** 1 day.
**Depends on:** nothing.
**Blocks:** `utils/review_bundle.py --regions` building without a process
killed.
**Status:** started 2026-11-02. T1e2.4.2.1 done; T1e2.4.2.2–.4 open.

## Context

`utils/review_bundle.py --regions`, the first gallery built against the region
modes, ran

```
ein solve examples/saturation/type-exclusivity/pets.ein --models key
```

on 2026-11-01, and the kernel's OOM killer killed it at **6.8 GB resident,
275 GB virtual** (18:07, kernel log; commit `43a40a84` names it). A bare
`solve` on `pets.ein` describes R, 11 339 states, every one listed, and
`--models key` asks for the determining key of those 11 339. The phase README
read the cause in the code without reproducing it: `ein_render::models::separating`
builds a k(k−1)/2-bit mask per varying slot before `min_key_size`'s node
budget is consulted, so the promised `KeyOutcome::Unaffordable` never gets to
answer.

Then it did not recur. The gallery's second build, at `17422b32` the same
evening (21:53), ran the same command and it **exited 0**, and
[S1e2.1a.7](../p1e2.1a_the_solution_region/s1e2.1a.7_the_bundle_shows_r.md#numbers)
recorded that without re-measuring. So the stage starts by finding out which
is true today, and why.

## Acceptance

From the [phase README](README.md#s1e242--models-key-declines-before-it-allocates):

- The key form declines with `KeyOutcome::Unaffordable` and its reason
  **before** it allocates whenever the pair table would pass a stated memory
  bound. The bound and the reason are written where `--models key` is
  documented. A decline is an answer: exit 0, and the states are still listed.
- A test holds it: a synthetic state set over the bound declines and
  allocates no pair table, and *allocates nothing* is measured, not asserted.
- `ein solve examples/saturation/type-exclusivity/pets.ein --models key`
  finishes, declining, with its peak RSS written down with the command and
  the date.
- `--models grid`, `--diff-models` and `-p` are measured the same way on the
  gallery's largest regions, `pets`, `square-bwd/houses` and
  `syntax/arg-kinds`. A form superlinear in memory gets the same treatment,
  or a row here saying why not.
- `utils/review_bundle.py --regions` builds the `pets` page with cross-check 1
  passing.

## How it is measured

Every number below is **peak RSS** and wall, of the `ein` process alone, under
a cgroup cap so a run cannot take the machine with it:

```sh
systemd-run --user --scope -q -p MemoryMax=9G -p MemorySwapMax=0 \
  python3 peak.py OUT -- ein.rs/target/release/ein solve FILE FLAGS…
```

`peak.py` forks, `execvp`s the command with stdout to `OUT`, and reads
`wait4`'s `ru_maxrss`, the number GNU `time -v` prints as *Maximum resident
set size* (`/usr/bin/time` is not installed on the machine). A run the cap
kills is read from the user journal's `oom-kill` line instead. The machine has
31 GiB and no swap. The release build is `./build.sh`'s, `snmalloc` linked.

## Tasks

### Task T1e2.4.2.1 — Re-measure, and why the second build passed

**Done 2026-11-02.** On the release binary at `6e7dfc49`:

| command | peak RSS | wall | exit |
|---|---:|---:|---|
| `ein solve examples/saturation/type-exclusivity/pets.ein` | 37.3 MiB | 0.19 s | 0 |
| `ein solve examples/saturation/type-exclusivity/pets.ein --models key` | **8 150.4 MiB** | **16.41 s** | 0 |
| the same, the binary built from `43a40a84`'s tree (`git archive`) | 8 131.4 MiB | 16.56 s | 0 |

(2026-11-02 00:39–00:43, three runs at `6e7dfc49` between 8 145 and 8 150 MiB.)
The two binaries' stdout is byte-identical: the key is *15 of 15 varying
slots* and the table has 11 339 rows.

**So the failure is not a code change and not the gallery invoking the command
differently.** `ein-render/src/models.rs` and `ein-cli/src/modes.rs` have not
changed since `43a40a84`, and the gallery's `key` invocation is the same
argv in both builds (`raw/command.txt`). The process needs about 8 GB however
it is run. Whether it survives depends on what else holds the machine's 31 GiB.
The 18:07 kill is a **global** OOM (`constraint=CONSTRAINT_NONE`), with 29 GB
of anonymous memory resident machine-wide, no swap, a 4 GB `qemu` guest, 6.2 GB
of `shmem` and `ein` the largest process at 6.8 GB, on its way up. At 21:53
the 8 GB was free and the run finished. **The read-out's 100-line cap plays
no part.** It cuts the read-out's listing, while the key form's table is
printed after it and whole (11 339 rows, 3.1 MB of the build's
`key.stdout.txt`), and the memory is spent before a line of it is printed.

**The cause is the one the README read, but the arithmetic is not.** `pets`
has 15 varying slots, not 850. The same binary with the process's RSS printed
at each step (`/proc/self/statm`, 2026-11-02, peak 8 150.1 MiB, 16.0 s):

| step of `key_table_of` | RSS after it | it took |
|---|---:|---:|
| the 11 339 fixpoints and the decision variables (k = 11 339, n = 15) | 83.6 MiB | |
| `separating`: 16 masks of 64 280 791 bits, the slots' and the full set's | 211.8 MiB | 128 MiB |
| `min_key_size` builds `by_pair`: per pair a `(usize, Vec<usize>)` and a heap list of the slots that separate it | 7 044.9 MiB | **6 833 MiB** |
| `by_pair.sort_by_key`, the stable sort's scratch | 8 026.6 MiB | 982 MiB |
| the search, one mask per level | 8 149.7 MiB | 123 MiB |

So it is `by_pair`, the mask table transposed, with 64 million small
allocations at about 110 bytes a pair, that takes the 8 GB, and not the masks.
The README's mask arithmetic is right per slot, and it is what dominates on a
program with a hundred slots. The corpus has those too, see below.

**The corpus is worse than `pets`.** Every corpus entry was run under bare
`solve`, `--maximal` and `--minimal` with `--models key`, on a scratch build
that prints k and n where the pair table would be built and declines past
10 million pairs (`survey.py`, 2026-11-02; 128 runs reach the table):

| run | k states | n slots | the masks alone | at `6e7dfc49` |
|---|---:|---:|---:|---|
| `square-unique/terminus.ein --maximal` (and `--minimal`, `corner-house`, `cul-de-sac`, `features/04_open`, `features/01_not_and_absent`, each both lines) | 64 514 – 65 214 | 41 – 157 | 10 – 38 GiB | **killed** at the 9 GiB cap in 11 s (`terminus --maximal`, 00:54) |
| `type-exclusivity/pets.ein` | 11 339 | 15 | 123 MiB | 8 150 MiB, 16.4 s, a 15-of-15 table |
| `features/05_stdlib_domain_elim.ein --maximal` (and `--minimal`) | 7 176 | 35 | 110 MiB | 2 872 MiB, 8.55 s, a 35-of-35 table of 7 176 rows |

| `--diff-models`, every state one fact off | **889.2 MiB, 17.61 s** | 41.8 MiB, 0.24 s | 77.6 MiB, 0.23 s |

The `--diff-models` files are written from each run's own `--json-summary`
(`mkwant.py`): *the states themselves* lists every listed state's facts under
`closes` of their relations, so every state matches. *One fact off* adds a
fact over a closed relation to each, so nothing matches and every pair is a
candidate for *near*.

- **`--models grid` and `-p` are linear.** Both hold the listed states'
  fixpoints at once (`region::Nodes::with_fixpoints`), 44 MiB over the bare
  run for `pets`. On the 64 514-state `terminus --maximal` line they are 340 MiB
  against the bare run's 233 MiB. No treatment.
- **`--diff-models` is quadratic in what it fails to match.** Matching equal
  models is a scan, O(got × want) in time and nothing in memory. Pairing
  what is left *nearest first* collects every unmatched (got, want) pair
  within its distance bound before sorting, 24 bytes each, and on *one fact
  off* that is 11 339 × 11 339 candidates. It gets the same treatment, in
  T1e2.4.2.3.

### Task T1e2.4.2.2 — The key form's bound

**The bound** is a constant, `ein_render::models::PAIR_TABLE_BOUND`, of
**16 MiB**, and it bounds what the key form holds for its search, not the
search's length, which the node budget already bounds:

- one mask of k(k−1)/2 bits per varying slot and one for the full set, which
  `separating` builds;
- as many again for the search's path, one per level of depth, since a level
  holds the mask it was handed;
- **4 bytes a pair** for the order the search takes pairs in, hardest first.

So `2(n + 1) · ⌈k(k−1)/128⌉ · 8 + 4 · k(k−1)/2` bytes. `by_pair`'s per-pair
lists go: the order becomes a `u32` per pair, sorted by a counting sort on how
many slots separate it (stable, so ties stay in pair order as the stable sort
left them), and a node reads the separating slots off the masks. The search
visits the same nodes in the same order, so every table it prints is the
table it printed. The check runs twice, and both checks are cheap:

1. after the states are made distinct, with k alone and n = 1, the least any
   key over these states could hold, before the decision variables are
   built, which are linear in memory but not in time;
2. after the variables, with the real n.

**Goldens this task moves, named before they move:**

- `ein.rs/crates/ein-cli/tests/golden/help_shape.txt`. `--models`' help, on
  `ein solve` and on `ein oracle`, says the key declines past the bound. No
  option is added or removed, so the counts in `configuration.md` § 1 and
  `help_surface.rs` stay.

**What moves with no golden to move:** `features/05_stdlib_domain_elim.ein
--maximal --models key`, a 7 176-row table today, declines. So do
`constraint-scopes.ein`, which declines today on the node budget after 1.2 s,
and the ten 64 000-state lines, which are killed today. No corpus run declares
`--models key`, and every key table a test pins is under 0.1 MiB
(`model_set_report.rs`, `region_modes.rs`).

### Task T1e2.4.2.3 — The diff's near pairing, under the same bound

`diff_model_sets` pairs what equality left unmatched *nearest first* only
while the candidate list fits the same 16 MiB at 24 bytes a candidate. Past
it, it pairs nothing nearest, says so in the diff block with the numbers, and
lists every unmatched model as missing or spurious, which is what they are.
`SetDiff::agrees` is unchanged, since a near pair is a disagreement either
way. No golden moves: every diff a test pins is a handful of models.

## Notes

- **Parked, not this stage's.** Each is named where it will be read again.
  - *The key table, the grids and `-p` are not under the 100-line rule.*
    `read_out.md` § 4.1 cuts the read-out's listings at 100 lines and says
    nothing of the forms printed after it. `pets`' key table was 11 339

    surface, so it is P1e2.3's.
  - *The node budget does not bound time when a mask is wide.* A node ORs and
    compares two masks of ⌈k(k−1)/128⌉ words, so 2 000 000 nodes cost in
    proportion to k². The bound caps k² as well, which caps this. Whether the
    budget should be counted in words is a measurement nobody has taken, and
    it belongs to the representation's cost, `representations.md`'s.
