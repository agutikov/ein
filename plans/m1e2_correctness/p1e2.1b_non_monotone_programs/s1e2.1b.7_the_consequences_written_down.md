## Acceptance

- **The taxonomy**, in `monotonicity.md`, one row per cause, each with a
  fixture: an `absent` that concludes a positive fact (`features/07`,
  `stale-naf-fork`); one that refutes (W3's `bad`); the derived refutation,
  `via` (`via_hole.ein`); one that takes a witness away (`lattice/08`); an
  obligation's trigger (`lattice/04`); an activator that compiles an
  obligation (`lattice/09`); one that compiles a refutation, hiding its
  `absent` (`ACTIVATOR_REFUTES`); an even cycle through an `absent`
  (`features/07`); an odd one (`d3-unsat-core`); the FIFO gap (the fixture
  below). Columns: which arrow it breaks (the state, or the status alone);
  whether the static check sees it, and as which `SiteKind`; whether *forbid*
  covers it, and under which of S1e2.2.5's F1–F3; what S1e2.1b.5's detector
  reports; which of F21's decisions it bears on. Path dependence is a
  consequence, not a cause, and the table says which causes produce it.
- **The path census**: on every flagged cube within the limit, S1e2.4.1's
  probes and the written programs, every node built by every split,
  sat(sat(P ∪ C1) ∪ (C \ C1)) for each C1 ⊆ C, and along every maximal chain
  where |C|! stays under a bound the page states. Per program, the nodes whose
  state depends on the construction, against fork and scratch. The monotone
  cubes as the control, up to a stated n. Also, on the cubes small enough to
  allow it, the **state-memoized path DAG** of
  [`monotonicity.md` § 7.2](../../../docs/kernel/inference/monotonicity.md#72-paths-and-the-general-form):
  its size against 2ⁿ, how many distinct states each C reaches, and how many
  of them hold no stale fact, which is F21's D2 (F). It also checks the
  premise that a step is a function of the KB's contents.
- **The cumulativity census**: on the same programs, for each node and each
  fact f its fixpoint derived, whether adding f before saturating changes the
  fixpoint: sat(X ∪ {f}) = sat(X). Counted per program, the stratified
  programs named. This checks § 7.3's premise.
- **The FIFO-gap fixture**: the counter-example banked under
  `examples/lattice/` with a corpus entry, its two hypotheses written as
  hrules, and its header giving the state by fork from {a} and built at once.
  The node census reads it both ways. If the engine does not reproduce the
  gap as written, the fixture is rewritten until it does or the page says why
  not.
- **Its static variant**, written into the census, not banked: `a` given and
  only `b` a candidate, so `q` is outside D and the static check calls the
  program monotone. [`monotonicity.md` § 7.6](../../../docs/kernel/inference/monotonicity.md#76-the-program-the-third-stronger-property)
  argues that scratch would still hold a stale `p` on {b} where the fork does
  not. The census says whether it does. If so, the program is banked too, and
  § 7.6, [`solution_semantics.md` § 1.5](../../../docs/kernel/inference/solution_semantics.md#15-commitment-node-state)
  and F21's D2 (B) take the qualifier; S1e2.1b.5's robustness test 2 names it
  as the case where scratch departs from a *Monotone* verdict.
- **Each option's consequences, per program**, in `monotonicity.md`, labelled
  open and naming F21: (A), (B), (C) over (A) and over (B), (D) over D and
  over all relations, admission in stratum order, and (E) under each reading
  of S1e2.2.5's F1 and F2. For each, on each program it touches: R, the
  states, the `corpus_exits.txt` and `corpus_shapes.md5` lines, the register
  rows and the `:expect`s it would move, and the programs it refuses. Taken
  from the census pages, and re-taken here where a number is missing, or named
  with what would measure it. Beside them, the consequences of D3's (i) and
  (ii) for P1e2.1c, of D4's options from `hole_census.md`, of D6's from the
  taint census and of D7's from the guard split.
- **(E)'s rewrites.** For each of the 13 programs, what it would be written
  as under (E): the decided attribute of [`dual_rail.ein`](../p1e2.4_what_the_switch_left/s1e2.4.1_probes/dual_rail.ein),
  the relation closed (`:no-hypothesis`), an obligation with hrules, an
  explicit choice for `features/07`'s pair, or *no rewrite that keeps R was
  found*. Each rewrite is banked as a probe in this phase's directory, with
  the original's R as its own `(solve :expect (region …))` where n ≤ 16, and
  its verdict and route where n is past the limit.
- **The terms left.** `monotone.rs`'s module docs (*"Is a program's hypothesis
  lattice monotone?"*, *"A program with no site has a monotone lattice"*) say
  which property they mean, in the vocabulary of § 7. Any other `docs/kernel/`
  sentence a grep for *monotone lattice* finds outside quoted engine output is
  fixed; quoted engine output is S1e2.1b.5's.
- **§ 7.8 re-labelled**: each unverified row measured, or refuted with the
  probe banked. That includes the static variant's row.
- **F21** links each decision's consequences.
- **No answer moves.** The censuses are example code, the rewrites are probes

## How it is measured

```sh
cargo run --release --manifest-path ein.rs/Cargo.toml -p ein-infer --example node_census -- --paths        # the path census (new)
cargo run --release --manifest-path ein.rs/Cargo.toml -p ein-infer --example node_census -- --cumulative   # the cumulativity census (new)
cargo run --release --manifest-path ein.rs/Cargo.toml -p ein-infer --example site_census                  # the 13, re-taken
cargo run --release --manifest-path ein.rs/Cargo.toml -p ein-infer --example refutation_census            # F1 and F2's readings
```

The flags are the stage's to name. The release build, the commit and the date
go on the page. The censuses are new dated sections of
[`node_census.md`](node_census.md); the taxonomy and the consequences are
`monotonicity.md`'s.
