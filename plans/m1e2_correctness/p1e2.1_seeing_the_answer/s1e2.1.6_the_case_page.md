# S1e2.1.6 — The case page, and the bundle

**Phase:** [P1e2.1](README.md) (Seeing the answer)
**Estimate:** 1.5 days
**Depends on:** [S1e2.1.1](s1e2.1.1_the_case_register.md) (the register) and
[S1e2.1.5](s1e2.1.5_every_artefact_rendered.md) (a run, rendered).
**Blocks:** [S1e2.1.7](s1e2.1.7_the_review.md).

## Context

After S1e2.1.5, one run is fully visible. A **case** is several runs: the
wrong one, its control, sometimes a twin fixture one fact apart. It also has a
right answer that no run produced. So the case page compares, and the
line is the one [`utils/README.md`](../../../utils/README.md) § Renderers
draws: **`ein` writes DOT and markdown for one run, and a script that needs
several runs, the register and Graphviz assembles.** Putting the case page in
Rust would teach `ein-cli` the register, which is a corpus file, and that is
how `ein-cli` would grow a dependency on `ein-corpus`.

## The bundle

`utils/review_bundle.py [--bin EIN] [--out build/review] [CASE …]` builds
every register case by default. It also accepts any `.ein` path, which gets a
case page with the problem and one default run, so an *initial problem*
outside the register gets the same treatment.

```
build/review/
  README.md                index: one row per case (id · owner · settings · wrong verdict/k ·
                           right verdict/k · status · the date and commit of the build · link)
  <case-id>/
    README.md              the case page, below
    runs/wrong/            S1e2.1.5's run directory, for the register's `wrong.run`
    runs/control/          … for `control.run`, when the register names one
    runs/<twin>/           … for each twin fixture the register names
    right/                 the register's `right.models`, rendered as grids and graphs
```

**The case page, top to bottom.** The order is the order a reviewer checks
things in, and every section links into the run directories rather than
copying them.

1. **The case.** Id, owner stage, the question ids it carried, the register
   status, one line of *wrong vs right*, and the settings it needs (default
   flags, or a lever).
2. **The problem.** The witness's header comment as prose, the source in full,
   `render program`, every rule as its own graph, `render kb --state root`,
   and root's fact count by relation. For a twin, the **source diff**
   between witness and twin, which is usually one fact or one `(config …)`
   line and is the most informative ten lines on the page.
3. **The answers, side by side.** One column per run plus one for the right
   answer: verdict word, `k`, `exhausted`, the read-out's qualifier, the
   commitments that reached each model, and the core where there is one.
4. **The models, side by side.** For each run and for the right answer, every
   model as S1e2.1.4's grid (or fact list) and as root + added. Then the set
   diff of each run against the right answer: missing, spurious, and
   one-fact-off, each named.
5. **Where it went wrong.** Links into the wrong run's pages at the point
   that matters: the layer whose timeline row recorded or refuted the
   contested commitment, its `--dump-lattice` page, the reductio in
   `trace/refuted.md`, and the matching rows of the control run. The case
   row in the register names those points (`look_at = […]`). The script
   links them and does not find them.
6. **Every artefact.** The run directories' tables of contents, so nothing
   is more than two clicks away.
7. **What to check.** A fixed checklist the reviewer answers in S1e2.1.7:
   *is the program the one the case describes · is the right answer right ·
   is the wrong answer what the engine says · is it one defect · is the
   lever (if any) the only way in.*

## Acceptance

- One command, no arguments, writes the whole bundle. Every link and image
  reference resolves (checked by running
  [`doc_audit.py`](../../../utils/doc_audit.py) `--links --check` on
  `build/review/`), and every SVG is non-empty.
- **A smoke step in the gate**, after `cargo test`: the bundle for one case,
  into a temp dir, link-checked. Graphviz is already a hard gate dependency
  (`dot_wellformed.rs`), so it adds no requirement. `gate_steps.rs`' two step
  lists gain it on both sides, or its drift test fails. **The full bundle
  joins the nightly** beside `stdlib_census.py --check`, and a case whose
  page fails to build turns the nightly red.
- `utils/README.md` gains the row in § Renderers.
- Opened once in VS Code's markdown preview and once on GitHub (a committed
  sample in a scratch branch is not needed, the file view of a gist is
  enough). Both draw every graph on the case page, written down with the
  date.

It exists for the review's last acceptance line: a wrong answer noticed
outside the register.

## Notes

- **Not committed.** `build/` is gitignored, and a committed bundle is
  thousands of SVGs that go stale at the next engine change. The index
  records the commit it was built at, so the review can always be rebuilt
  exactly.
- **HTML is out of scope.** Markdown with SVG references is what was asked
  for, and both viewers the user works in draw it. Pan and zoom over a
  444-fact KB is [M20](../../m20_gui/README.md)'s.

## ✅ Done 2026-10-15 — one command, twenty-six pages, and a smoke step in the gate

`python3 utils/review_bundle.py` with no arguments writes `build/review/`:
an index (one row per register row: owner, settings, the wrong and right
verdict and `k`, **what differs**, status, and the build's date, commit and
binary) and one page per row. On this machine the whole bundle is **45.6 s,
392 MB, 6 788 pages, 996 SVGs**. `doc_audit.py --links --check` over it gives
**0 findings** across those 6 788 pages, and no case failed to build. The
modules are `utils/review/case.py`, and S1e2.1.5's run directories underneath
it.

### The case page, top to bottom

1. **The case**: id, class, settings, status, the owner stage linked, the
   question ids, and wrong against right in one row each.
2. **The problem**: the witness's own header as prose, the source (collapsed),
   `render program`, every rule, and root as graphs, and root's facts by
   relation. For a twin on another file, **the program diffed against the
   witness's with comments left out**, which is the one or two lines that
   matter (the whole-file diff is collapsed beneath). For a twin on the same
   file, the flags or environment that differ.
3. **The answers, side by side**: one column per run plus the right answer.
   Rows: the run (linked to its `run.md`), the verdict line verbatim, `k`,
   `exhausted`, the read-out's qualifier, the exit code, the commitment that
   reached each recorded state, and the core. Then the derivation of the right
   answer and every alternative reading.
4. **The models, side by side**: each run's recorded states over the
   register's `closes`, with the grid where one is licensed. Then each run
   **against the right answer through `ein solve --diff-models`** (verbatim),
   from a `right.models` the script writes out of the row. A run on a
   different program is labelled as held to the witness's right answer, not
   its own.
5. **Where it went wrong**: the row's `look_at` pointers resolved in every
   run, or named as absent from it.
6. **Every artefact**: each run's `run.md` and its section table, so any page
   is two clicks away.
7. **What to check**: the five questions, and the verdict vocabulary S1e2.1.7
   records.

### `look_at` (T2)

The register's schema grows `look_at`, with eleven words: `root`,
`root-writes`, `timeline`, `layer N`, `entering <facts>`, `refuted`,
`trace [step N]`, `answer`, `model N`, `summary`, `events <kind>`.
`register::defects` refuses any other word. Every row has pointers, written
from the inventory's mechanism for its case. W2 points at `root-writes` and
`events writeback`, where the `<forced-positive>` promotion is. W5 points at
`layer 3`, `model 3` and `events rung`. The script links them and finds
nothing itself.

### The other modes (T3)

- `review_bundle.py examples/zebra2.ein [-- FLAGS]`: a page with the problem,
  one run (`solve -e` by default), its models and every artefact. 4.1 s.
- `review_bundle.py --corpus`: one page per corpus entry with a declared
  `solve` run, at that run's flags and without events, into
  `build/review-corpus/`. Not in any gate.
- A row id (`W1/branching-15`) or a case (`W1`) builds a subset.

### In the gate, and in the nightly

`step "utils/review_bundle.py --smoke"` follows `cargo test --workspace` in
`run_tests.sh`, and the matching `# gate-step` in `per-commit.yml` runs from the
repo root. `gate_steps.rs` holds the two lists equal, and passes. The smoke
step builds `W2/forced-2` into a temporary directory with the **debug** `ein`
`cargo test` just built, checks every SVG is non-empty, and link-checks the
result. It takes 0.5 s and needs nothing the gate does not already require:
Graphviz is a hard dependency since `dot_wellformed.rs`, and Python since the
static checks. It sits outside the `--tests-only` guard, because it tests what
the engine writes rather than checking source, so the guarded set and
`gate_steps::what_tests_only_skips_is_what_the_script_guards` are unchanged.
The **whole bundle** joins `nightly.yml` beside `stdlib_census.py --check`,
with the release `ein` the corpus step built. A case whose page fails to
build exits 1, and so does a dangling link in it.

### One deviation, measured

**Event rows are rendered up to 10 000 per kind**: the first 5 000 and the
last 5 000. `C1`'s `branching/06 -e` narrates **2.2 million** verbose events.
Rendering every row made thousands of pages, half a gigabyte, and a build
longer than ten minutes for that one case, and a table that size is not
something a reviewer reads. A capped kind's page says how many lines there
are, which it shows, and that `raw/events.jsonl` keeps every one (`n` is each
line's place in it). The raw file is untouched. With the cap `C1` builds in
34 s. No other register run reaches the cap.
