**Phase:** [P1e2.1](README.md) (Seeing the answer)

**Blocks:** [S1e2.1.7](s1e2.1.7_the_review.md).

## Context

After S1e2.1.5, one run is fully visible. A **case** is several runs: the
wrong one, its control, sometimes a twin fixture one fact apart. It also has a
right answer that no run produced. So the case page compares, and the
line is the one [`utils/README.md`](../../../utils/README.md) § Renderers
draws: **`ein` writes DOT and markdown for one run, and a script that needs
several runs, the register and Graphviz assembles.** Putting the case page in
Rust would teach `ein-cli` the register, which is a corpus file, and that is
how `ein-cli` would grow a dependency on `ein-corpus`.

## The bundle

`utils/review_bundle.py [--bin EIN] [--out build/review] [CASE …]` builds
every register case by default. It also accepts any `.ein` path, which gets a
case page with the problem and one default run, so an *initial problem*
outside the register gets the same treatment.

```
build/review/
  README.md                index: one row per case (id · owner · settings · wrong verdict/k ·
                           right verdict/k · status · the date and commit of the build · link)
  <case-id>/
    README.md              the case page, below
    runs/wrong/            S1e2.1.5's run directory, for the register's `wrong.run`
    runs/control/          … for `control.run`, when the register names one
    runs/<twin>/           … for each twin fixture the register names
    right/                 the register's `right.models`, rendered as grids and graphs
```

**The case page, top to bottom.** The order is the order a reviewer checks
things in, and every section links into the run directories rather than
copying them.

1. **The case.** Id, owner stage, the question ids it carried, the register
   status, one line of *wrong vs right*, and the settings it needs (default
   flags, or a lever).
2. **The problem.** The witness's header comment as prose, the source in full,
   `render program`, every rule as its own graph, `render kb --state root`,
   and root's fact count by relation. For a twin, the **source diff**
   between witness and twin, which is usually one fact or one `(config …)`
   line and is the most informative ten lines on the page.
3. **The answers, side by side.** One column per run plus one for the right
   answer: verdict word, `k`, `exhausted`, the read-out's qualifier, the
   commitments that reached each model, and the core where there is one.
4. **The models, side by side.** For each run and for the right answer, every
   model as S1e2.1.4's grid (or fact list) and as root + added. Then the set
   diff of each run against the right answer: missing, spurious, and
   one-fact-off, each named.
5. **Where it went wrong.** Links into the wrong run's pages at the point
   that matters: the layer whose timeline row recorded or refuted the
   contested commitment, its `--dump-lattice` page, the reductio in
   `trace/refuted.md`, and the matching rows of the control run. The case
   row in the register names those points (`look_at = […]`). The script
   links them and does not find them.
6. **Every artefact.** The run directories' tables of contents, so nothing
   is more than two clicks away.
7. **What to check.** A fixed checklist the reviewer answers in S1e2.1.7:
   *is the program the one the case describes · is the right answer right ·
   is the wrong answer what the engine says · is it one defect · is the
   lever (if any) the only way in.*

## Acceptance

- One command, no arguments, writes the whole bundle. Every link and image
  reference resolves (checked by running
  [`doc_audit.py`](../../../utils/doc_audit.py) `--links --check` on
  `build/review/`), and every SVG is non-empty.
- **A smoke step in the gate**, after `cargo test`: the bundle for one case,
  into a temp dir, link-checked. Graphviz is already a hard gate dependency
  (`dot_wellformed.rs`), so it adds no requirement. `gate_steps.rs`' two step
  lists gain it on both sides, or its drift test fails. **The full bundle
  joins the nightly** beside `stdlib_census.py --check`, and a case whose
  page fails to build turns the nightly red.
- `utils/README.md` gains the row in § Renderers.
- Opened once in VS Code's markdown preview and once on GitHub (a committed
  sample in a scratch branch is not needed, the file view of a gist is
  enough). Both draw every graph on the case page, written down with the
  date.

## Tasks

### Task T1e2.1.6.1 — The case page and the index

Plain markdown. `<details>` for anything longer than a screen, so the first
screen is sections 1 and 3: the case and the two verdicts.

### Task T1e2.1.6.2 — `look_at`

A field in the register (S1e2.1.1's schema grows it), filled per case from
the inventory. The fixing stage reads the same pointers, so they are
written once.

### Task T1e2.1.6.3 — The non-register mode, and the corpus sweep

`utils/review_bundle.py examples/zebra2.ein` gives a page with sections 2, 3,
4 and 6. `--corpus` builds one for **every** corpus entry with a declared
`solve` run, with the `--no-events` switch for size. It is not in any gate.
It exists for the review's last acceptance line: a wrong answer noticed
outside the register.

## Notes

- **Not committed.** `build/` is gitignored, and a committed bundle is
  thousands of SVGs that go stale at the next engine change. The index
  records the commit it was built at, so the review can always be rebuilt
  exactly.
- **HTML is out of scope.** Markdown with SVG references is what was asked
  for, and both viewers the user works in draw it. Pan and zoom over a
  444-fact KB is [M20](../../m20_gui/README.md)'s.
