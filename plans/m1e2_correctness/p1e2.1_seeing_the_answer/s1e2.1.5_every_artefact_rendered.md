## Context

A reviewer who suspects a wrong answer wants to see **everything the engine
can say about the run**, not a summary of it. They want to see it laid out so
that nothing has to be decoded: no JSON to read by eye, no ` ```dot ` fence to
imagine, no `layer_03_post.ein` to diff by hand. The engine already writes
nearly all of it. One run of `examples/zebra2.ein -e` with every artefact flag
on, taken 2026-10-14 to size this stage:

| artefact | flag | what came out on `zebra2 -e` | read today as |
|---|---|---|---|
| the markdown trace, with the final whole-KB snapshot | `--trace FILE.md --full-kb-snapshots` | **15 566 lines**, **639** ` ```dot ` blocks: § Before any assumption (325 steps), one § per step, § Refuted hypotheses, § Commitment lattice, § Solution, § Full KB (final state) | a file no viewer draws a graph of |
| the state dump | `--dump-states DIR` | `00_root_initial.ein`, `00_timeline.jsonl`, `layers/layer_NN_{pre,post}.ein` (4 272 lines over the layers), `summary.json` | `.ein` snapshots to diff by hand and a JSONL timeline |
| the run summary | `--json-summary FILE` | `verdict`, `stats`, `owes`, `leftover`, `root`, `config` | JSON |
| the event stream | `--events FILE` | **63 475** lines, `ein-events/1` | JSONL |
| counters and timings | `--stats`, `--timing`, `--hyp-stats`, `--dump-config` | stdout tables | stdout |
| per-solution facts | `-p` / `-P` / `-f` | stdout blocks | stdout |
| the answer, as files | `--dump-answer DIR` ([S1e2.1.2](s1e2.1.2_every_answer_a_file.md)) | program, root, `models/`, `open/`, `refuted/` | new |
| every commitment tested | `--dump-lattice DIR` ([S1e2.1.3](s1e2.1.3_the_doors.md)) | `enterings/`, `proof_summary.json` | new door |
| the program, the rules, the constraints, the lattice | `ein render program` / `rules` / `constraints` / `lattice` / `kb` | DOT on stdout | DOT |

`--trace`, `--full-kb-snapshots`, `--events`, `--json-summary` and
`--dump-states` combine in **one** invocation (checked: exit 0). The
`--dump-lattice` door cannot share a solve with `--dump-states`, because one
`dumper` serves one solve. So a run is **two or three invocations**, and their
answers have to be the same answer, which is itself worth checking.

## The run directory

`utils/review_bundle.py run <file.ein> [solve flags…] --out DIR` writes one
directory per run. The **case** page in S1e2.1.6 is made of these. Every
rendered page links its raw file, and every raw file is kept verbatim.

```
DIR/
  run.md                   the run page: what was run, the answer, and a table of contents
                           linking every page below, each with its line/fact/graph counts
  raw/                     every artefact exactly as the engine wrote it, never edited
    command.txt            each invocation's argv, `ein --version` (all five lines), the commit
    stdout.txt stderr.txt exit.txt          per invocation
    trace.md               --trace --full-kb-snapshots
    states/                --dump-states, the whole tree
    answer/                --dump-answer, the whole tree
    lattice/               --dump-lattice, the whole tree
    summary.json  events.jsonl  config.txt (--dump-config)  stats.txt (--stats --timing --hyp-stats)
    program.dot  rules/*.dot  constraints.dot  lattice.dot  root.dot  models/NN.dot
  img/                     every DOT above and every ```dot block of trace.md, as SVG
  pages/
    program.md             the source, `render program`, `render rules` (one graph per rule,
                           with its :match / :assert / :why), `render constraints`
    root.md                root saturation: fact count by relation, `render kb --state root`,
                           and § Before any assumption from the trace, one step per row
    trace/                 the trace, split so a page is readable
      index.md             one row per step: step, rule, what it derived, link
      steps-NNN-MMM.md     the steps in pages of 50, every dot block replaced by its SVG
      refuted.md           § Refuted hypotheses, each reductio as an SVG, with its no-good
      lattice.md           § Commitment lattice as an SVG
      solution.md          § Solution
      full-kb.md           § Full KB (final state): the snapshot as a table by relation,
                           and as `render kb`
    states/                the --dump-states tree, made explicit
      timeline.md          00_timeline.jsonl as a table: seq · ms · event · layer · commitment
                           · outcome · firings · facts merged · core size · no-good
      layer-NN.md          per layer: alive size, every entering in it, and pre → post as a
                           fact diff (added / removed, by relation) plus both snapshots as graphs
    lattice/               the --dump-lattice tree: one page per commitment tested, its
                           firings and its outcome, linked from the timeline row that entered it
    answer.md              per model / open state: the grid, root + added as a graph, the
                           commitment that reached it; per refuted commitment: core + clause
    summary.md             summary.json as tables: verdict, every counter in `stats` with its
                           meaning from events.md / configuration.md, owes, the resolved config
    events.md              events.jsonl as counts per kind, then one table per kind (enter,
                           layer, nogood, owe, warn, fire …), each linked to the schema row in
                           docs/kernel/inference/events.md
    consistency.md         the cross-checks below, and their results
```

**Every page opens the same way.** It says what the artefact is, which flag
wrote it, which page of the kernel docs defines it, its raw file, and its
size. A reader who lands on `layer-03.md` from a search knows where they are.

## Acceptance

- **Nothing the engine writes is left out.** The run directory holds every
  artefact of the table above for the run, and `run.md` lists them. A test
  greps `ein solve --help`'s artefact flags out of `golden/help_shape.txt` and
  fails when a flag exists that the bundle does not drive. A new artefact
  flag then cannot silently escape the review.
- **Nothing is decoded by eye.** No page shows raw JSON or a ` ```dot ` fence
  as its content. The raw files are one link away and never inline.
- **The script computes nothing it did not read.** Tables are transcriptions
  of engine files, and the *diffs* (layer pre → post, model set against right
  answer) are set differences of fact lists the engine wrote, never a
  re-derivation. Each diff is labelled as such.
- **`consistency.md` holds five cross-checks**, each a pass or a named
  mismatch:
  1. the two or three invocations agree: `summary.json` identical apart from
     paths and wall times, which is the `--jobs` / id-order invariance
     discipline applied to artefact flags;
  2. `--dump-answer`'s `answer.json` is `--json-summary`;
  3. the trace's § Solution facts are the dumped models' facts;
  4. `Σ entered` from `events.jsonl` equals `stats.enterings_total`, on a
     lattice run, where the identity holds
     ([`configuration.md` § What `EIN_TRAVERSAL=tree` reports](../../../docs/kernel/configuration.md));
  5. the timeline's last layer and the summary's `layers_explored` agree.

  A mismatch on any of them is a finding, filed when it is seen, not
  smoothed over by the renderer.
- **Size is handled, not avoided.** On `zebra2 -e` the run directory renders
  the 639 graphs and the 63 475 events, and every page is readable: no page
  over ~2 000 lines, with `<details>` for anything longer than a screen. The
  cost is measured and written down (wall time and MB), and a
  `--no-events` / `--no-trace` switch exists for the corpus-wide mode, never
  for a case run.
- `utils/review_bundle.py run examples/zebra2.ein -e` and
  `… run examples/lattice/02_genuine_3set_death.ein -e -L` both produce a
  directory that VS Code's preview draws completely. Checked by opening
  `run.md`, one `layer-NN.md` and `trace/refuted.md` in each.

## Tasks

### Task T1e2.1.5.1 — Drive

The invocation plan (which flags share a solve, which cannot), each argv
recorded, and cross-check 1. Under `EIN_TRAVERSAL=tree` the lattice
artefacts are absent by design, and `run.md` says so instead of showing an
empty page.

### Task T1e2.1.5.2 — Lift the rasteriser

Out of [`utils/zebra2_trace.sh`](../../../utils/zebra2_trace.sh) (which
rasterises each ` ```dot ` block of a trace to `img/stepNNN.svg` and rewrites
the markdown to reference it, for one hard-coded program) into a function the
bundle and that script share. `zebra2_trace.sh` becomes a one-case caller of
it rather than a second copy, which is AR-M1's *one artefact, one owner*
applied to a script. A block `dot` refuses is rendered as the refusal text
and counted in `consistency.md`. It is never dropped, because a DOT the
renderer cannot draw is a `dot_wellformed.rs` gap.

### Task T1e2.1.5.3 — The trace, split

By its own `##` sections and then by step ranges. `index.md` is the table a
reader scans for *which rule fired when*. The step pages keep the trace's
text untouched around each image.

### Task T1e2.1.5.4 — The state dump, made explicit

The timeline table, and per layer the pre → post fact diff by relation. The
diff is what a reader of `--dump-states` has always had to compute by hand.
The snapshots are rendered with `ein render kb` on the snapshot file, which
loads as a program. Each timeline row that entered a commitment links to its
`--dump-lattice` page.

### Task T1e2.1.5.5 — Summary and events as tables

Every `stats` counter with its one-line meaning, taken from the page that
defines it and linked, never paraphrased in the script. Events grouped by
kind, the column set per kind read from `events.md`'s schema tables (the
ones `events_reference.rs` already parses), so a new kind gets a table
without a script change.

## Notes

- **Why one directory per run and not per case.** A case has two to four runs
  (wrong, control, a twin, a second lever), and a run is the unit the engine
  has an answer for. The case page compares runs. It never re-renders one.
- **The events table is not the trace.** The trace is the engine's
  *explanation* (what it chose to narrate, with `:why` text), and the event
  stream is its *record*. Where the two disagree on what happened, that is
  the most interesting line in the bundle, and cross-check 3 is the start of
  looking for it.
