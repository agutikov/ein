# S1e2.1.1 — The case register

**Phase:** [P1e2.1](README.md) (Seeing the answer)
**Estimate:** 1.5 days
**Depends on:** nothing.
**Blocks:** [S1e2.1.6](s1e2.1.6_the_case_page.md), which renders one page
per row, and every stage of [P1e2.2](../p1e2.2_wrong_answers/README.md), each
of which ends by flipping its rows from `open` to `fixed`.

## Context

The wrong answers are written down today in five registers that do not
know about each other. They are question entries
([`open_questions.md`](../../../docs/history/m1e_review_processing/open_questions.md)), the
header comments of `examples/ein-bugs/*.ein`, `:expect` clauses that state
**today's** answer on purpose (`branching/15`+`16`), the probe scripts under
S1e.1.1's `probes/`, and the milestone table in
[P1e2.2](../p1e2.2_wrong_answers/README.md). A renderer needs one list, and a
fix stage needs one place to say *done*.

The `:expect` clauses are the nearest thing to a register and cannot be it.
An expectation is a claim about the program's answer, so a witness whose
`:expect` stated the **right** answer would fail `ein test`, which is honest
but makes `corpus_exits.txt` carry a known-false claim with no pointer to its
owner. One whose `:expect` states the wrong answer, as `branching/15`+`16` do,
pins the defect but says nothing about what the answer should be. And
[Q-M1e.13](../../../docs/history/m1e_review_processing/open_questions.md#q-m1e13--expect-cannot-state-an-answer-with-an-empty-goal-extent)
is a case `:expect` cannot express at all.

## The shape

`corpus/wrong_answers.toml`, beside `corpus.toml` because it is a corpus
reader's table, not a plan. A plan is deleted when its milestone closes, and a
register that guards fixed cases has to outlive this milestone.

```toml
[[case]]
id       = "W1/lattice-02-L"               # <case>/<witness>; stable, the bundle's directory name
case     = "W1"                            # the inventory's id: W1–W12, C1
owner    = "S1e2.2.1"                      # the fixing stage while open
question = ["Q-M1e.8"]                     # the ids that carried it before
witness  = "examples/lattice/02_genuine_3set_death.ein"
status   = "open"                          # open | fixed | not-wrong | merged:<id>

[case.wrong]                               # what the engine answers today
run      = "solve -e -L"
verdict  = "Contradiction"
k        = 0
exhausted = true

[case.control]                             # optional: a run that gets it right
run      = "solve -e"
verdict  = "Ambiguity"
k        = 3

[case.right]                               # the answer, stated as data
verdict  = "Ambiguity"
k        = 3
models   = "examples/ein-bugs/expected/lookahead-off-3set.models"   # optional
derived  = "docs/kernel/inference/solution_semantics.md § 2 Worked"
```

`right.models` is a file of fact sets, one block per model, in the
`--json-summary` `solutions[].facts` spelling. That is what S1e2.1.4's diff
reads. It is optional because some right answers are a verdict word and a
`k` (a missing model is sometimes all a hand derivation can name). It is
required wherever the wrong answer is a **wrong model** rather than a wrong
count.

## Acceptance

- **One row per witness**, each naming its case. W1 alone has five
  witnesses (`branching/15`, two layer-0 probes, `lattice/02 -L`,
  `branching/16`), and a fix is done when **all** of them answer right. The
  case ids are [`inventory.md`](../inventory.md)'s, and P1e2.2's stage table
  uses the same ones.
- **The probes become fixtures.** Every witness that today exists only under
  [`plans/m1e2_correctness/probes/`](../probes/) is banked under
  `examples/ein-bugs/` with a corpus entry and a header carrying its
  derivation, because a plan directory is deleted when its milestone closes and
  a register row cannot point into it.
- **`ein-cli/tests/wrong_answers.rs`**, in the gate. For every row it runs
  `wrong.run` on `witness` in-process and asserts:
  - `open`: the answer is **still** `wrong`. An open case that changes answer
    is a fix nobody intended, or a new wrong answer, and either one is news;
  - `fixed`: the answer equals `right`, and `right.models` where given;
  - `not-wrong`: nothing, beyond the row naming the review that said so.
- The test **fails if a row's witness has no `corpus.toml` entry**. The
  register adds no new kind of file the completeness check does not know.
- `corpus/README.md` gains the table's row in § the readers, and the register
  is linked from [`examples/README.md`](../../../examples/README.md)'s
  `ein-bugs/` line.

## Tasks

### Task T1e2.1.1.1 — Write the rows from the inventory

From [P1e2.2](../p1e2.2_wrong_answers/README.md)'s table, each row's `wrong`
block **re-run**, not copied, and the run date written in the file header.
A row whose wrong answer does not reproduce stops this task: either the case
was fixed in passing, or the inventory misread it, and the review has to see
which.

### Task T1e2.1.1.2 — The test

Reuse `ein-corpus`'s manifest loader and the in-process solve the corpus sweep
uses (`corpus_cli.rs`). Do not shell out. Mutation-check it three ways: flip
one `open` row's `k`, set one row to `fixed`, and delete one witness's corpus
entry. Each must fail with a message naming the row.

### Task T1e2.1.1.3 — What `:expect` keeps

Write down, in the register's header, the rule for a witness that also carries
an `:expect`. **The `:expect` keeps stating today's answer until the fixing
stage moves it**, as `branching/15`+`16` already do, so the two cannot
disagree while the case is open. The fixing stage moves both in one commit.

## Notes

- The register is not a second corpus. A case is a *claim about one
  program*, and the program is already a corpus entry. The register adds the
  answer it should have.
- `status = "not-wrong"` is a first-class outcome of
  [S1e2.1.7](s1e2.1.7_the_review.md), not a deletion. A case the review
  rejects keeps its row, so the next reader who has the same suspicion finds
  the answer.

### Four deviations from the stage text, each with its reason

1. **Through the binary, not in-process.** The stage says *"the in-process
   solve the corpus sweep uses (`corpus_cli.rs`). Do not shell out"*, but
   `corpus_cli.rs` is a process sweep. Two rows need a process.
   `W5/owed-seats`'s tree twin sets `EIN_TRAVERSAL=tree`, which `ein-infer`
   reads from the environment at solve time, and an in-process test could set
   it only for every test in its binary at once. W7's debug abort is a `panic!`
   that would end the test rather than be observed by it. A row is also a claim
   about what `ein <run>` answers, which is what the review bundle will show.
   So `wrong_answers.rs` runs `CARGO_BIN_EXE_ein` through `ein_corpus::plan::argv`,
   the sweep's own argv builder, and compares the `--json-summary`. 46 runs,
   **0.47 s** in the dev profile.
2. **A witness may live in `corpus/fuzz_findings/`.** The stage says *"the
   test fails if a row's witness has no `corpus.toml` entry"*. Three witnesses
   cannot be corpus entries. W7's pair **aborts a debug build** (`check_layout`,
   on both activator orders, checked), and every in-process corpus sweep is a
   debug test binary. W11's two files **move under a permuted interner**, which
   `id_order_invariance` asserts of every corpus file. The rule is now *a
   corpus entry, or a file under `corpus/fuzz_findings/` with `not_in_corpus`
   saying why*. That directory's README already defines it as the place for
   inputs that violate a property the sweeps assert. Its README gains a
   section, and its *"`d3-unsat-core` … the id-space sweep is green on it"*
   gains *"at seed 1 only"*: at seed 15839 `trace[answer]` moves 4 → 6 facts.
3. **`right.models` is inline, with `closes`, and not a `.models` file.** Every
   case is a few facts, and a model set in the row reads where the case is
   read. A model is compared as the recorded state's facts **over the relations
   `closes` names**. That is `:expect`'s *naming a relation closes it*, made
   explicit so that `models = [[]]` with `closes = ["q"]` can say *one model
   with no `q`*, which `:expect` cannot (Q-M1e.13) and which six of the right
   answers are. S1e2.1.4's diff reads the same spelling.
4. **W11's permuted half is held in `ein-render`.** The permutation is a
   function in `id_order_invariance.rs`, and `ein-cli` cannot reach it. A row
   carrying `wrong.id_order = { op, seed }` has its plain half checked by
   `wrong_answers.rs` and its moved half by
   `id_order_invariance::the_register_s_id_order_rows_answer_what_they_record`.
   That test must count as *moved* exactly what the sweep reports, so the
   sweep's answer-vs-narration cut became one function, `moved_by_the_cut`,
   which both call.

Two things go **beyond** the stage text. Every control and twin is held to its
recorded answer as well as the wrong run, because a case page built from a
drifted control would be wrong without anything failing. A `not-wrong` row's
answer is held too, because an answer the review ruled right is one a
regression can break. The stage said *nothing* for that status.

### The test, and its mutation checks

`ein-corpus`'s new `register` module reads the file with
`deny_unknown_fields`, so a typo'd field is a load error rather than a silently
unclaimed one. It holds the run-free invariants: id prefix, unique ids, the
status vocabulary, a `core` on every `Contradiction`, `closes` wherever models
are given, `len(models) = k`, a `why` on every control and twin, one title and
owner per case, and `not_in_corpus` exactly for `fuzz_findings/` witnesses.
`every_witness_is_a_file_the_corpus_knows` checks every control's and twin's
file too. Each mutation was run and not banked, and each failed naming its row:

| mutation | failed with |
|---|---|
| `W1/branching-15`'s `wrong.k` 1 → 2 | `W1/branching-15 [wrong] ein solve -e … — an OPEN case changed answer …: k: recorded 2, got 1` |

### Found, and carried to a later stage

**`--dump-states`'s snapshot files do not load.** `ein saturate
<dir>/layers/layer_01_post.ein` answers `kb load error: duplicate relation
'is-a'`. The KB serialiser (`ein-render::dump::serialise::kb_to_ein_text`)
writes both of a relation's schema facts, `(relation is-a T T)` and
`(relation is-a)`, and the loader refuses the second. It writes no rules
either. This phase's README calls them *"root before and after each layer as
loadable `.ein`"*, and S1e2.1.5 plans to render each one *"with `ein render kb`
on the snapshot file, which loads as a program"*. Both premises are false.
S1e2.1.2 needs a loadable model file anyway, and takes the question up there.

**Fixed 2026-10-15 in S1e2.1.7**, on the user's instruction: the serialiser leaves the arity-1 companion to the loader, and every snapshot of either dump tree loads back to its own facts (`ein-render/tests/dump_states_load.rs`).
