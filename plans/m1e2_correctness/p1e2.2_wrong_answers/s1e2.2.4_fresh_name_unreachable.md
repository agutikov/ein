## The case

`hypgen::candidate_objects` (`hypgen.rs:659` at `71dd237`) builds the blind
enumerator's objects from `kb.names()`, a function of the KB's **facts**.
`alive₀` is taken once, at root's fixpoint. A constant that a rule `:assert`s
only inside a fork therefore enters the KB in a region the lattice never
revisits, and nothing is ever hypothesised about it.

| witness | settings | today | right |
|---|---|---|---|
| [`examples/ein-bugs/wrong-answers/fresh-name-default.ein`](../../../examples/ein-bugs/wrong-answers/fresh-name-default.ein): the banked file minus its `(config …)` line | **default** | `Solution k = 1`, exhausted, over a model with **no `q` fact** | `Solution k = 1`, `{(q A Z), (q B Z)}` |

| [`ein-bugs/alive-set-fresh-name-declared.ein`](../../../examples/ein-bugs/alive-set-fresh-name-declared.ein): plus `(seen Z)` | — | `Solution k = 1`, `{(p Z Z),(q A Z),(q B Z)}` | control, right |

**The banked fixture is confounded.** Delete its `spawn` rule, so that no
fresh name exists at all ([`examples/ein-bugs/wrong-answers/fresh-name-nospawn.ein`](../../../examples/ein-bugs/wrong-answers/fresh-name-nospawn.ein)),
and it still answers `Contradiction k = 0, exhausted`. That is W1 at layer 0
under its `lookahead false`. Its header attributes the `k = 0` to ST-M1 alone,
and that sentence is corrected here. The isolated case is the default-lookahead
variant.

**Reach:** two corpus programs break the invariant harmlessly
(`ein-bugs/mixed-type-hypothesis.ein` drives the hrule rung;
`tests/stdlib/algebra/07_schroder.ein` fires before `alive₀`). The `warn`
event S1e.3.3 shipped (`invariant.rs`) narrates every breach at load.

## The three candidates (Q-M1e.21, priced 2026-08-31)

| | what | cost |
|---|---|---|
| **(a) refuse at load** | a rule whose `:assert` names a constant no fact does is a load error | refuses both corpus programs, one of them a working stdlib test. It also decides *may a rule name a fresh object?* in the negative before M2 has asked |
| **(b) seed the pool** | `candidate_objects` unions the rules' `:assert` constants into `kb.names()` | the smallest change, and it answers the fixture right. It widens the blind enumerator on every program with such a constant (a search change and a golden change), and is correct only if the static constant set is the **whole** of what a rule can introduce. `alive_invariant.rs`'s dynamic sweep confirms that today, and a `(?R ?a ?b)` head binding an integer would break it |
| **(c) leave it, and say so** | what shipped | the wrong answer stays |

(c) is not available to a milestone whose acceptance is *no wrong answer at
default settings*. Between (a) and (b) the recommendation is **(b), with (a)'s
check kept for the residue**. Seed the pool from the static constant set, and
make a program whose rule can introduce a constant the static set cannot
predict a load error. That is the integer-binding head the question names, and
no corpus program has one. Then the invariant is a property of the engine plus
a refusal, rather than a precondition on the rule library.

**Ruled 2026-10-16: (b).** The user: *"rules are part of root, so rules can't
assert new names"*. A constant a rule's `:assert` names is a name of the
program, so the universe has to include it, and its absence from the
candidates is an engine bug. (a)'s premise, that such a name is *fresh*, is
gone. The residue (a) would refuse, a head that binds a constant no static set
predicts, is still to be priced here
([Q-M1e2.7 § The third answer](../open_questions.md#the-third-answer-2026-10-16)).
