## The case

The id-order sweep (`ein-render/tests/id_order_invariance.rs`, which re-runs a
file under a permuted interner) on the two fuzz findings, 2026-10-14:

```
unsat-core-id-space.ein [solve[default]] seed 1
    plain:    CORE 1 [(r1 o4 o5)]
    permuted: CORE 2 [(r1 o1 o5) (r1 o4 o1)]
d3-unsat-core.ein [trace[answer]] seed 15839   (EIN_ID_SEEDS=3)
    plain:    … (unsat core: 4 facts).
    permuted: … (unsat core: 6 facts).
```

The same program reports a different core, of a different **size**, when only
the ids its names were interned under change. Ids are not part of the
program. [`corpus/fuzz_findings/README.md`](../../../corpus/fuzz_findings/README.md)
says `d3-unsat-core` *"is green under a permuted id space"*, which is true at
seed 1 only.

This is a different defect from [W10](s1e2.2.11_alt_cap_core.md). There the
store's **retention** order decides; here the search's **tie-break** among
candidates, or its traversal order over ids, does. The size difference (1 vs
2, 4 vs 6) says it is not only a tie-break among equal-size cores: the minimum
is not always found.

**The mechanism.** Root holds `(r1 o4 o5)`. The program's one rule, `fire-2`,
derives `(false)` from a two-step `r1` chain, or from any `(r1 …)` together
with any **stored** `(not (r1 …))`. `{(r1 o1 o4)}` makes a chain with the root
fact, so it is correctly dead in the cube. The search refutes it and writes
`(not (r1 o1 o4))` into root: the kill cache by default, the singleton writeback
under `-L`. The rule's second disjunct reads that negative together with
`(r1 o4 o5)`, and root dies. In the one run where nothing writes the negative,
`-K` with the lookahead on, the count is the cube's maximal line.

### The ruling that already covers it: Q-M1e.7 A

[Q-M1e.7](../../../docs/history/m1e_review_processing/open_questions.md#q-m1e7--the-read-out-prints-the-solution-kb-and-calls-it-a-model)

|---|---|
| ruling A (2026-08-28) and the file's own `:expect` | one model, `{(p A), (p B)}` |

them is right, and which one depends on which lattice R is over.

### The options for the discussion

1. **Keep A, and make the oracle agree with it.** A node's state includes the
   negation of every candidate whose addition kills it. That is: saturate
   root + C + `{(not h) : C ∪ {h} dead}`, computed from the top layer down,
   since a node's status then depends on its supersets'. It keeps both rulings.
   It does not change the lattice, only what a node holds. It makes `-K` and
   `-L` the incomplete runs here, which the engine then has to fix (Q-M1e.8's
   fix (ii)). On `complete-records-stale.ein` it puts `{(q A)}` out of R and
   gives A's one model. Its cost: the oracle is no longer *saturation alone*,
   and an unhypothesised candidate reads as false at every node where it cannot
   be added. That is a closed-world reading per node, and it should be stated
   as one.
2. **Revise A for the region reading.** A search-time write never feeds a
   rule. The negatives still prune the search, but rule matching does not see
   them. The oracle stays as it is, the `-K` run is the right answer on both
   files, and the register's row and `complete-records-stale.ein`'s `:expect`
   move.
3. **Refuse or flag a rule that reads a stored negative of a hypothesised
   relation.** It reads something only the search or option 1 writes, so the
   question never arises. Both files would be refused.

**The question reaches the stdlib.** The two witnesses are fuzz-shaped, but
the stdlib reads stored negatives of a hypothesised relation in its own
rules. `total` and `surjective` (`algebra.ein:294`, `:302`) refute when
`(forall … (not (?R …)))` holds. The domain-elimination rules
(`elim.ein:62`, `:73`) and two in `bijection.ein` (`:114`, `:126`) match on
`(not (?R …))`. `symmetric-negative` and `compose-negative-*` propagate it.
Those rules were written to read negatives the search learns, so:

- **option 3** would refuse the stdlib;
- **option 2** changes what every bijective puzzle's refutations rest on;
- **option 1** is the reading the stdlib already assumes.

That weighs toward 1. The plan does not decide it. Option 1 keeps a ruling the
user gave with its reasons, and option 2 is the reading the oracle was built
on. The choice decides what R's nodes are, so the answer also goes into
[S1e2.1a.3](../p1e2.1a_the_solution_region/s1e2.1a.3_the_definition.md)'s
definition page.

## The fix

1. Find which: is `explain.rs`'s search exact, so that the size difference

   lexicographic on the rendered facts, never on ids. The same rule as
