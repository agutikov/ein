## Context

The plan's Stage B has one instruction above its four sub-items: *avoid
mixing solving and formalization*. The neural component converts text into
an executable theory, and everything else — whether the theory is
consistent, whether it has one model, what its answer is — is the kernel's.
This stage writes that division down as a contract before a prompt exists,
so that the prompts, the grammars, the passes and the record are all
derived from one page rather than the page being reverse-engineered from
them later. The old plan had no such page: its contract was spread over
six stage files and three `docs/decisions/` documents that were never
written.

Four things the contract fixes, one per sub-item of the plan:

- **B1 — the task.** Input: a problem statement, EN or RU (the user is
  bilingual and the seed set will have both). Output: **one `.ein` file the
  kernel loads with no preprocessing** — ontology, theory, instance, query,
  in that order, flat, as [ein-lang](../../../docs/kernel/ir/03-ein-lang/README.md)
  defines it. The decomposition is fixed, not optional (the phase README
  says why); whether an *additional* intermediate representation helps is
  G8's question, not this page's.
- **B2 — source vs generated.** *The formalizer may restructure information
  from the source but must not invent problem-specific facts.* Five
  categories, each form in exactly one.
- **B3 — what the model knows.** Listed, versioned, hashed; nothing hidden;
  no benchmark solutions.
- **B4 — prompt versioning.** Every prompt is an experimental variable with
  a hash in the record; a changed prompt is a new experiment id.

The contract is a *document*; the things that enforce it are the per-pass
grammars ([S2.2.3](s2.2.3_gbnf.md)), the record ([S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md))
and the faithfulness judge ([S2.4.4](../p2.4_loop/s2.4.4_faithfulness.md)).
[S2.1.3](../p2.1_kernel_as_instrumentation/s2.1.3_boundary.md) fixes the
language the loop is written in; the paths below assume its recommendation —
a Python harness under `einaf/` driving the `ein` binary.

## Acceptance

- `docs/einaf/contract.md` exists — the loop's first documentation page —
  and states B1–B4 in the form below, with the five provenance categories,
  the marking rule, the knowledge list and the record fields.
- Every prompt template written in [S2.2.4](s2.2.4_passes.md) cites the
  contract section it implements, and no prompt contains text the contract
  does not list under B3.
- The five categories partition the forms of every seed-set gold program:
  a script assigns each form to exactly one category and reports zero
  unassigned.
- The reading list is committed with one line per entry saying which
  question it informs; two hours, stopped on the clock.

## Tasks

### Task T2.2.1.1 — The contract page

`docs/einaf/contract.md`. One page. Input and output as above, then the
four-part output with one example of each part drawn from
[`examples/zebra2.ein`](../../../examples/zebra2.ein), which is the
hand-written program the formalizer is meant to reproduce:

```ein
;; ontology — relations with signatures; the rendering template is optional
(relation nation-loc Nationality House :why "the {?1} lives in {?2}")
;; theory — selected, not written: the activator instantiates std.bijection
(import std.bijection :symbols (bijective-properties bijective-setup typecheck-setup))
(bijective nation-loc)
;; instance — every fact quotes the sentence it came from
(nation-loc Norwegian House-1 :source "The Norwegian lives in the first house.")
;; query — the goal variables, named from the question
(query :goal (and (drink-loc Water ?h_water) (nation-loc ?who_water ?h_water)) :goal-text "…")
```

The rule the page states about the order: the kernel does not care, the
passes do — the theory pass reads the ontology, the facts grammar is
rendered from the ontology's instances, and the query pass reads all three.

### Task T2.2.1.2 — The five categories and their marking

| category | what it is | example | marked by |
|---|---|---|---|
| **source-derived fact** | a fact the text states | `(nation-loc Norwegian House-1 :source "…")` | `:source "<span>"` — exists in ein-lang, layers the fact as a *fact* by the engine's own provenance rule, and is **mandatory**: a fact without one is a contract violation, not a style issue |
| **generic theory (stdlib)** | an import and the activators that instantiate it | `(import std.bijection …)`, `(bijective pet-loc)` | the form itself: an `import` of `std.*`, or a fact whose head is a property the catalogue lists |
| **generated auxiliary relation** | a relation the text does not name, introduced to state something it does | `(relation adjacent House House)` where the text only says *next to* | the sidecar |
| **generated inference rule** | a `rule` / `hrule` form the formalizer wrote because the catalogue had no property for it | a temporal composition rule for the family the stdlib lacks | the sidecar, plus the theory pass's log line saying which property it needed |
| **generated assumption** | a fact the text does not state and the formalizer added to make the theory work | `(color-loc Red House-3)` with no sentence behind it | the sidecar — and a faithfulness event the moment it appears |

**The marking decision.** `:source` stays the first category's mark; for
the other four the recommendation is a **sidecar in the record, keyed by
the form's canonical text** — `ein-ir`'s canonical dump gives every form
one string — so the program stays a plain kernel input and ein-lang gains
no keyword. The alternative, a reserved `:origin` keyword on the form, is
taken only if [S2.1.1 T2.1.1.2](../p2.1_kernel_as_instrumentation/s2.1.1_census.md)
finds that the parser already accepts an unknown keyword on a fact *and*
the faithfulness judge turns out to need the category inside the program
rather than beside it. The hand encodings' `:source "condition (2)"` is a
citation, not a span; the contract requires the **span** — the sentence,
or a character range into the input — because [S2.4.4](../p2.4_loop/s2.4.4_faithfulness.md)
checks that it exists in the text.

### Task T2.2.1.3 — What the model receives (B3)

The list, in the order it is assembled into the system prompt, each item
with its version:

1. **The ein-lang specification** — four pages at a named commit:
   [`00_ebnf.md`](../../../docs/kernel/ir/03-ein-lang/00_ebnf.md) (what
   parses), [`01_grammar.md`](../../../docs/kernel/ir/03-ein-lang/01_grammar.md)
   (the forms and what each declarator means),
   [`02_patterns.md`](../../../docs/kernel/ir/03-ein-lang/02_patterns.md)
   (the pattern sub-language, for the rare synthesised rule),
   [`07_stdlib_api.md`](../../../docs/kernel/ir/03-ein-lang/07_stdlib_api.md).
   Whole pages are too long for a local model's context; the task writes
   the *excerpt* per pass and hashes the excerpt, which is what B4 records.
2. **The stdlib catalogue** — generated from [`stdlib/`](../../../stdlib/README.md)
   by a script, one line per module (`std.bijection — closed-world bijection
   inference, signature-driven`) and one per property (`bijective R —
   functional ∧ injective ∧ total ∧ surjective, each argument a slot`), with
   the manifest SHA at the top. Generated, so it cannot drift from the
   library; hashed, so the record knows which catalogue the model saw. G9
   ([P2.6](../p2.6_ablations/README.md)) swaps this item for *none* and
   *minimal*.
3. **Few-shot examples** — the Zebra smoke test (text → program, the
   canonical one) and hand-written micro-examples, one per family of
   [S2.3.1](../p2.3_benchmark/s2.3.1_families_and_seed_set.md), each three
   to five sentences. **Never a benchmark instance**: Zebra is excluded from
   every split ([S2.3.4](../p2.3_benchmark/s2.3.4_splits.md)) and the
   micro-examples are written, not drawn.
4. **The problem statement.**
5. **Prior diagnostics, if iterative** — the `ein-feedback/1` object
   rendered at the run's feedback level ([S2.4.3](../p2.4_loop/s2.4.3_feedback_ladder.md)),
   and under *repair* the current theory. Absent in one-shot.

What the model does **not** receive is listed too: no benchmark answers,
no gold programs beyond the few-shot set, no kernel output other than the
feedback object, no human edits between iterations.

### Task T2.2.1.4 — The record fields (B4)

Stated here, stored by [S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md):
`model` (name), `model_sha256` (the GGUF file), `server_image` (image
digest), `system_prompt_sha256`, `pass_prompt_sha256` (one per pass),
`spec_commit` (the Ein commit the excerpts were cut at), `catalogue_sha256`,
`stdlib_manifest_sha256`, `generation` (`temperature`, `top_p`, `seed`,
`max_tokens`, `grammar_sha256` per call), `ein_commit`, `ein_version`
(the five lines of `ein --version`). A prompt edit changes a hash; a
changed hash is a new experiment id; there is no third state.

  already cites: Wu et al. 2022 (*Autoformalization with Large Language
  Models*, the 25.3 % figure), *Process-Driven Autoformalization in Lean 4*
  (compiler feedback as the signal — the nearest published relative of
  this loop), Lean Workbook (compilation + back-translation + NLI as the

  (NL → reasoning / planning / KR formalisms as one task — the licence to
  call NL → Ein autoformalization at all); informs the contract's framing
  and [M5](../../m5_presentation/README.md) § 3.
- **Benchmarks** — [F13](../../followups/f13_puzzles_beyond_zebra/ideas.md)'s
