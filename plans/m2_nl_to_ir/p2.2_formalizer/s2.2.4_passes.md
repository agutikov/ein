## Context

The old S2.4.1 split extraction into two passes — ontology, then facts
parameterised by it — because one pass over a whole puzzle was too much
load and because an ontology audited first keeps facts from referencing
atoms that do not exist. Both reasons hold. What the old plan did not have
is the pass that makes the program *solvable*: it emitted relations and
facts and **no activators**, so the kernel would have loaded a well-typed
program with no theory and sat idle — the gap [F7 B](../../followups/f7_rule_induction.md#connection-to-m2)
named as being on M2's critical path. This stage has four passes, and the
third is the one that was missing.

```text
text ──► ontology pass ──► theory pass ──► instance pass ──► query pass ──► one .ein
          relations +       imports +       facts with       (query …)
          types/instances   activators      :source spans
          grammars/         grammars/       grammars/        grammars/
          ontology.gbnf     theory.gbnf     facts.gbnf.in    query.gbnf
```

The theory pass is where the user's *three neural actions*
([F13](../../followups/f13_puzzles_beyond_zebra/ideas.md)) become three
*priced* moves: **reinterpretation** is a new ontology or instance pass;
**theory selection** is an activator from the catalogue — cheap, checked,
the default; **theory synthesis** is a `rule` form — permitted only after
the pass has stated, in its log, which property it needed and failed to
find in the catalogue, so every synthesised rule carries the reason it
exists. [F12](../../followups/f12_rules_and_relations/ideas.md)'s
*select, do not invent* is enforced by that ordering rather than by a
prompt asking nicely.

[S2.1.3](../p2.1_kernel_as_instrumentation/s2.1.3_boundary.md) fixes the
language; the passes are `einaf/passes/*.py` and the prompts are text
under `einaf/prompts/`.

## Acceptance

On the Zebra smoke text, one shot, the pinned model:

- the ontology pass yields the six types the hand encoding has — `House`,
  `Color`, `Nationality`, `Pet`, `Cigarette`, `Drink` — with their members
  and the five `*-loc` relations plus the spatial ones, as `is-a` facts and
  `relation` forms;
- the theory pass yields `(import std.bijection …)` and a `(bijective …)`
  activator per `*-loc` relation (or the `std.slots` formulation — either
  is the same theory, and the test accepts both), plus the spatial
  properties (`(symmetric next-to)`, `(includes right-of next-to)`), and
  **no `rule` form**;
- the instance pass yields ≥ 15 facts — one per condition — each with a
  `:source` span that exists verbatim in the input;
- the assembled program loads: `ein solve` exits 0 and the feedback object
  has no `invalid` outcome.

And on the seed set, the same four measurements per puzzle, in a record.

## Tasks

### Task T2.2.4.1 — Prompt templates

`einaf/prompts/{ontology,theory,facts,query}.tmpl`, `string.Template`
substitution, each citing the contract section it implements and each
carrying only what B3 lists: the spec excerpt for its pass, the catalogue
(theory pass only), the few-shot example for its pass, the text. The old
`ontology.tmpl` and `facts.tmpl` survive with their wording — *read this
text; list every entity type, instance and relation* / *given this text and
this ontology, extract every fact as a form; quote the originating sentence
in `:source`* — and two are new: `theory.tmpl` (*given this ontology and
this catalogue, state which properties each relation has, as activator
facts; if a property you need is not in the catalogue, say which, then and
only then write a rule*) and `query.tmpl` (*what does the text ask? name
one goal variable per asked-for entity*). The few-shot example is Zebra's
first three conditions for every pass, as before.

### Task T2.2.4.2 — The ontology pass

`einaf/passes/ontology.py::extract_ontology(text, llm) -> Forms`. One
call under `grammars/ontology.gbnf`, seed fixed; the reply is parsed by
calling the binary to dump it canonically, and a reply that does not parse
is a grammar bug, not a repair case. Output: `relation` forms with
signatures and `is-a` facts for types and members, in the unified model
([`03_ein_model.md`](../../../docs/kernel/ir/01-ein-graph/03_ein_model.md)
— no `type` / `instance` keywords, `is-a` all the way up to `T`). Q9's
escape hatch: `--ontology PATH` skips this pass and loads a hand-written
one; Q9's option C, the *library of standard ontologies*, is gone as a
thing of its own — what was library-shaped about it was the theory, and
the theory pass reads the stdlib catalogue instead.

### Task T2.2.4.3 — The theory pass

`einaf/passes/theory.py::select_theory(ontology, catalogue, llm) -> Forms`.
One call under `grammars/theory.gbnf` rendered with the catalogue's
property names, with the `rule`-forms alternative **disabled** in the
grammar. The reply is activator facts and `import` forms. Then, if the
reply contains the pass's *missing-property* marker (a reserved line the
prompt asks for: `;; needs: <property> for <relation>`), a second call
under the grammar with `rule` forms **enabled**, the marker's text in the
prompt, and the synthesised forms logged under the *generated inference
rule* category with the marker as their reason ([S2.2.1 T2.2.1.2](s2.2.1_contract.md)).
Two calls, so that synthesis is a recorded event with a cause, never a
default. The catalogue is [S2.2.1 T2.2.1.3](s2.2.1_contract.md)'s item 2;
on the families the stdlib has no theory for (object tracking, temporal —
[P2.3](../p2.3_benchmark/README.md)) the second call is expected and its
rate per family is a reported number.

### Task T2.2.4.4 — The instance pass

`einaf/passes/facts.py::extract_facts(text, ontology, llm) -> Forms`.
The grammar is `grammars/facts.gbnf.in` rendered with the ontology's
relation names and instance atoms, so an undeclared atom is unemittable.
**Sentence-by-sentence** is the default, not the option it was: one call
per sentence (split on the text's own boundaries, recorded), which makes
every `:source` span the sentence by construction, keeps each call's
context small, and gives the faithfulness judge one span per fact. The
whole-text mode stays as a flag for the G6-style question of whether
context helps. A fact with no `:source` cannot be emitted — the grammar
makes the keyword mandatory — and a span that is not a substring of the
input is rejected by the pass before assembly, as a contract violation
counted in the record.

### Task T2.2.4.5 — The query pass

`einaf/passes/query.py::extract_query(text, ontology, llm) -> Form`.
One call under `grammars/query.gbnf`: a `(query :goal (and …) :goal-text "…")`
with one variable per entity the question asks for, named from the
question (`?who_water`, `?h_zebra`), and the `:goal-text` template the
renderer will print the headline through. For external instances whose
answer is a letter or `True / False / Unknown`
([S2.3.3](../p2.3_benchmark/s2.3.3_external_benchmarks.md)) the pass
emits the goal the adapter's extraction contract expects.

### Task T2.2.4.6 — Assembly

`einaf/passes/assemble.py::assemble(ontology, theory, facts, query) -> str`:
the four parts concatenated in order, a `;;` header naming the record id,
dumped canonically by the binary, and the sidecar of
[S2.2.1 T2.2.1.2](s2.2.1_contract.md) written beside it with every form's
category. The program is a plain kernel input with nothing the kernel does
not read.

### Task T2.2.4.7 — Tests

`einaf/tests/passes/`: the acceptance's four measurements on the Zebra
text (integration, skipped without `LLAMA_HOST`), plus offline tests on
recorded replies — a captured `LlmInvocation` per pass replayed through
the parser, the assembler and the sidecar writer — so the pipeline's
plumbing is tested on every gate run without a model.

## Notes

- Bilingual: the same four prompts carry an RU few-shot example when the
  input is RU (detected trivially, recorded); the passes do not translate.
- The old plan's *two passes, then audit ontology coverage* is preserved
  as a check between the ontology and instance passes: every relation and
  atom the instance pass could emit is one the ontology declared, which
  the rendered grammar guarantees and a test re-asserts anyway.
- What the kernel reports about the theory — a `bijective` that makes the
  puzzle unsatisfiable, a `transitive` that was needed and absent — is the
  loop's business ([P2.4](../p2.4_loop/README.md)); this stage produces a
  theory once and hands it over.
