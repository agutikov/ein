## Context

**The ruling.** The model runs inside EinAf's process, through a Rust binding to llama.cpp: no server, no
container and no HTTP between the harness and the model
([Q-M2.14](../open_questions/model/Q-M2.14-what-runs-the-model.md)). The model is `qwen3.5:4b`, a GGUF file pinned by
its SHA, an experimental constant for the whole of Level C; *another suitable model* is another value of the
record's model field, taken when an experiment asks for one. What the ruling buys, and the plan uses: the sampler
chain with the grammar in it, the seed and every parameter as fields of the record; thinking on or off a call; a
grammar that begins where the thinking ends; each token's log-probability; the context kept between the turns of
one loop; the chat template as a file of the record.

**The host**, as [`host.md`](../analysis/host.md) found it, a fact about one machine on one day which this stage
takes again before it leans on it:

- an RTX 4060 Laptop GPU with 8 GB; the package `llama-cpp 0.9.0` with `llama-server`, the libraries
  `libllama.so.0`, `libllama-common.so.0` and `libggml.so.0`, the headers `llama.h` and `llama-cpp.h`, and the CUDA
  backend of `ggml`; a program can link it, and it knows the architecture `qwen35`;
- the model's file in ollama's system store, readable by the user, 2.47 GiB; ollama is where the file was pulled
  to and is no runtime of the plan;
- through `llama-server` the whole model on the device (2 771 MiB at a context of 4 096 tokens, without the
  vision projector), about 66 tokens a second, thinking on by default, a GBNF grammar honoured against the
  prompt, each token's log-probability returned, a declared function called; and **a grammar over the whole
  output of a thinking model took the thinking too**;
- four bindings on crates.io, none tried: `llama-cpp-2`, `llama-cpp-4`, `llama_cpp`, `llama-cpp-bindings`.

Read in the host's `llama.h` at this re-plan: `llama_sampler_init_grammar` takes a grammar's text and its root;
`llama_sampler_init_grammar_lazy_patterns` is a grammar that starts at a trigger, a pattern or a token; the model
parameters have `vocab_only`; `llama_model_chat_template` returns the template the file carries; and
`llama_chat_apply_template` says of itself that it uses no Jinja parser and knows a fixed list of templates. The
package installs no header for `libllama-common`. So what a binding over that header gives for the chat template
and its thinking switch is not settled by the header, and T2.2.2.3 settles it.

**The stage has two halves.** The first builds the runtime and pins the model. The second is the cheapest early
measurement of the milestone: **does the model write loadable Ein with no grammar?** The user,
[Q-M2.13](../open_questions/einaf/Q-M2.13-who-calls-the-kernel.md): the model *"most probably not aware about this
language … newertheless ein semantic is very simalar to Datalog, syntax is Lisp/SMT style, so writing ein
program may be not impossible without GBNF"*. That is a hypothesis the plan measures, not a premise, and it is
measured here, before a grammar exists, because its answer says what a grammar is for. Its first item is the
user's own: *"first experiment would be with original zebra problem and with working zerba program as example -
test for dummies"* ([the user's notes](README.md#formalization-in-steps-the-users-notes-on-the-whole-phase)), the
floor under everything the probe measures after it.

## Tasks

### Task T2.2.2.1 — The binding, chosen and built

For each candidate, in this order, stopping at the first that passes:

1. **It loads the model.** Whether it builds a llama.cpp of its own (which commit) or links the host's
   `libllama.so.0`, the llama.cpp it gets has to know the architecture `qwen35`. A binding that does not load the
   file is out, whatever else it offers.
2. **It runs on the GPU**, the whole model on the device, by its CUDA build or by the host's `ggml` backend.
3. **It gives the control the ruling lists**: a sampler chain the caller builds, with a grammar in it and the lazy
   start; the seed; each token's log-probability; a sequence's state kept between calls; tokenisation with the
   special tokens; the template's text from the file.
4. **What it costs to build**: the toolchain it needs (`cmake`, a C++ compiler, the CUDA toolkit) and how long a
   clean build is on this machine.

The choice is recorded with the result of every candidate tried. **The runtime is a Cargo feature of `einaf`**, off by
default: the gate step builds and tests EinAf without it, on a runner that has neither CUDA nor the model's file,
and an experiment builds with it. How to build with the feature and how a run is given the model's path is a
section of `docs/einaf/`.

### Task T2.2.2.2 — The model's file

There is no download script and no manifest of files: the file is on the host, and a record names it by its SHA.

- The stage hashes the file (the store names a blob by its SHA; the stage does not take the name's word) and
  reads its header: architecture, parameter count, quantization, trained context length, the chat template, the
  special tokens.
- A run is given the file's path, by an option or a variable of `einaf`; the path is never the model's identity.
- The vision projector is not loaded.
- Two programs want the same 8 GB ([`host.md`](../analysis/host.md#what-still-needs-the-users-hand)): a run that
  counts on the device's memory needs ollama's copy unloaded first, and the envelope records the device's free
  memory at load.

### Task T2.2.2.3 — The runtime's interface

One trait, a module of `einaf/src/`, and three implementations: the binding; **replay**, which answers from a
record and is what the offline tests use; and `llama-server`, written only if the fallback is taken. The shape,
as a sketch the stage may change:

```rust
pub struct Request {
    pub messages: Vec<Message>,          // rendered through the model's own template
    pub tools: Vec<ToolDecl>,            // empty in the filter; the tool arm's, S2.4.6
    pub thinking: bool,
    pub grammar: Option<Grammar>,        // text, root, and where it begins: S2.2.3
    pub sampler: Vec<Sampler>,           // the chain, in order, each with its parameters
    pub seed: u32,
    pub max_tokens: u32,
    pub logprobs: Option<u32>,           // how many alternatives a token
    pub keep: Option<SequenceId>,        // continue a kept context
}

pub struct Generation {
    pub thinking: String,                // what the model wrote before its answer
    pub answer: String,
    pub tokens: Vec<TokenId>,            // every generated token, thinking included
    pub counts: Counts,                  // prompt, thinking, answer
    pub stop: Stop,                      // end of turn, max tokens, a stop string
    pub logprobs: Option<Vec<TokenLogprobs>>,
    pub envelope: Envelope,
}
```

- **Typed failures**, each a value: the file does not load; the prompt does not fit the context (with the two
  lengths); the grammar's text does not parse (`llama_sampler_init_grammar` returns null); the grammar leaves no
  token (a dead end, which is a bug of the grammar and is never retried). Reaching `max_tokens` is a `Stop`, not
  a failure. There is no transport, so there is no retry policy.
- **The chat template.** The stage settles how the template the file carries is rendered with the thinking
  switch and a declared function: by the binding, if it wraps llama.cpp's own renderer, or by a Jinja renderer in
  EinAf over the template's text. Either way the template is a file of the record and the rendered prompt's
  token ids are what the comparison of T2.2.2.5 checks.
- **Thinking** is on or off a call. A generation keeps the thinking apart from the answer, and counts the tokens
  of each: the budget of an arm is generated tokens, thinking included (the frame's default 6).
- **A kept context**: the stage shows that a second call on a kept sequence pays for the new tokens only. The
  loop's use of it is [P2.4](../p2.4_loop/README.md)'s.
- **What the tool arm needs** ([S2.4.6](../p2.4_loop/s2.4.6_ein_as_a_tool.md)): the template rendered with a
  function declared, and the answer with the model's call in it as the model wrote it. The stage checks that the
  runtime gives both, with the function of the host probe, `ein_solve(program)`, and builds nothing of the tool.

### Task T2.2.2.4 — The envelope

What every call returns and every record keeps ([S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md) has the
layout; the fields are this stage's):

| field | what |
|---|---|
| the model | the file's SHA-256; from its header, the architecture, the parameter count, the quantization |
| the runtime | the binding's crate and version; the llama.cpp it built or linked, by version and commit; the backend and how many layers are on the device |
| the context | its length in tokens; the device's free memory at load |
| the template | the hash of the template's text, which is a file of the record; thinking on or off |
| the prompt | the hash of the rendered prompt's token ids, and their count |
| the sampler | the chain in order, each sampler with its parameters; the seed |
| the grammar | the hash of its text; its root; where it began (the first token, or a trigger) |
| the generation | the generated token ids; the counts of thinking and answer tokens; why it stopped; the wall time of the prompt's evaluation and of the generation |

The model's own defaults (`temperature 1`, `top_k 20`, `top_p 0.95`, `presence_penalty 1.5`,
[`host.md`](../analysis/host.md#the-model)) are one chain; greedy decoding is another. This phase's own runs are
greedy, so that one run is the whole distribution and a difference between two runs is a difference of inputs.
Which chain the arms run with is [S2.5.2](../p2.5_harness/s2.5.2_baselines.md)'s, whose default is the model's
own; the one shot is then run under it unchanged.

### Task T2.2.2.5 — Tests, and the reference

**Offline, in EinAf's gate step**, with the feature off: the replay implementation; the envelope written and read
back; each typed failure from a recorded cause.

**By hand, with the model, each with its record:**

1. **The host probe again, through the binding**: the eight requests of
   [`host.md`](../analysis/host.md#what-the-model-does-through-llama-server-a-probe), which `llama-server`
   answered. The grammar is honoured against the prompt; thinking is off where asked; the log-probabilities come
   back; and a grammar from the first token with thinking on is shown to take the thinking, as it did there.
2. **The reference.** For a fixed set of requests, `llama-server` of the host's package is started on the same
   file with the same context, and each request is sent once, greedy, with the same seed and grammar. The
   comparison is of the rendered prompt's tokens and of the generated text. A difference is explained (another
   llama.cpp under the binding, another template rendering) or it is a bug of the runtime.
3. **Repeatability**: one request several times, the number fixed before the run; the token ids are equal, or the
   record says where they differ.
4. **Throughput and memory**: tokens a second and device memory at the contexts the phase's prompts need,
   through [`utils/bench_env.sh`](../../../utils/bench_env.sh) so that the machine's state is on the record, on
   AC power.

**The fallback.** If no binding loads the model, or one loads it and a control of T2.2.2.1's list is missing that
a later stage cannot do without, the runtime is the `llama-server` implementation of the trait over the loopback
interface (the frame's default 5). The stage then records which control is lost, and shows it: the fallback
changes how [Q-M2.14](../open_questions/model/Q-M2.14-what-runs-the-model.md) is met, and that is the user's to see.

### Task T2.2.2.6 — The probe: Ein with no grammar

A probe with a record, not the benchmark. Everything below is fixed and written into the record before the first
generation.

**The items**, three kinds, the first run first:

- **The first experiment, the user's** ([the user's notes](README.md#formalization-in-steps-the-users-notes-on-the-whole-phase)):
  *"original zebra problem and with working zerba program as example - test for dummies"*. The item is the Zebra
  text, [`nl2smt/puzzles/zebra.txt`](../../../nl2smt/puzzles/zebra.txt); the prompt's one example is a working
  Zebra program beside that text, the target shape [S2.2.0a](s2.2.0a_zebra_formulations.md) settled,
  [`examples/zebra3.1.ein`](../../../examples/zebra3.1.ein) by default, run by the kernel before the probe; and the prompt carries the excerpt of Ein's syntax
  and semantics, as every prompt does ([S2.2.1](s2.2.1_contract.md), T2.2.1.3). The model writes the whole program
  in one call. The item is shown its own program, so the family rule below yields to it, by the user's word: it is
  the floor of the probe, labelled so, and none of its numbers is a measurement of formalization or enters a
  table. Reported: whether the output parses and loads, its outcome and the sentence it printed, and how far the
  program is from its example (copied whole, changed where, broken where).
- **A whole program over the library.** A few small texts, each with a reference program the kernel answers;
  the first is the worked example of [S2.2.1](s2.2.1_contract.md), which this re-plan ran. And the sixteen word
  problems of [`examples/word_problems/`](../../../examples/word_problems/README.md), an item's text the
  comment at the head of its file, written over the library alone: the calculator's requests and whatever rule
  the model needs. The examples are a few such programs the stage writes. **This is the main arms' condition**:
  the model is shown the library and no family's module ([S2.2.4](s2.2.4_passes.md), T2.2.4.8).
- **A theory given.** The same sixteen, with the vocabulary of the word theory in the prompt (that README's
  tables of what a problem writes and what a quantity is) and the corpus's own programs as the examples, each a
  text beside its program; the model writes the imports, the facts with their `:source`, the question as a fact,
  the query. This is the widest condition of the library ablation
  ([S2.6.4](../p2.6_ablations/s2.6.4_representation_ablations.md)) and no arm's: the probe takes it because the
  corpus has sixteen worked pairs of it, and the question here is whether the model writes loadable Ein.

**An item is never shown an example of its own text family**, the first experiment aside; the families (the
problems about a transfer, about two kinds, about boxes, and so on) are fixed before the run.

**The conditions:** thinking off and thinking on, each with the examples. A third, a description of the form in
a paragraph and no example, is added if the stage has the room: it is what the model's knowledge of Datalog and
of Lisp gives alone.

**The reading of an output:** *whole*, the answer is the program; and *fenced*, the first fenced block where the
answer has one. Both are reported.

**What is measured**, per item and condition, through `einaf::kernel` and never through the binary:

1. whether the text parses (the library's `ein_ir::parse`), and where it does not, every error with its place;
2. whether the program loads (`ein_ir::load`, the item's directory as the base, so that the word theory's modules
   are found; a `:why` required, as by default);
3. **the kinds of error**, by the kinds [S2.1.2](../../../docs/ein/user/04-reference/07-diagnostics.md)
   gave them, and each kind with what would have prevented it: any grammar (a paren, a string where none goes, a
   keyword a form does not take); a grammar that knows the program's names; the catalogue (a selection misspelt);
   or nothing a grammar can do (a refusal of meaning, such as
   [a conclusion's variable nothing binds](../../../docs/ein/user/04-reference/07-diagnostics.md#213-a-conclusions-variable-nothing-binds)).

For a program that loads, the kernel is asked through EinAf's bounded kernel call
([S2.1.3](../../../docs/einaf/03-feedback.md#1-the-bounded-call), T2.1.3.2b), and its reply and the
line it prints are kept in the record. **The bound is not optional here**: nothing in a solve stops a
saturation that has no fixpoint ([S2.2.5](s2.2.5_from_text.md) has the run), and these are the first programs a
model wrote. A call the bound stops is *not decided*, and how many were is reported. What a loaded program
answers is not reported as an accuracy: the items are few, and they are the material prompts are developed on.

**What the report is for.** [Q-M2.6](../open_questions/formalizer/Q-M2.6-one-gbnf-or-many.md): the third measure says which
errors one grammar removes and which only a grammar restricted to a step could. The tool arm, B6: its first call
is this setting, and [S2.4.6](../p2.4_loop/s2.4.6_ein_as_a_tool.md) reads the load rate as what a tool's first
reply will be. [P2.6](../p2.6_ablations/README.md): the filter with its grammar off is this probe's setting on
the benchmark.

## Risks

- **No binding passes.** Then the fallback, which keeps the grammar, the seed and the log-probabilities (the host
  probe saw each) and has to show whether it keeps a context between calls and a per-call sampler chain.
- **A binding that builds its own llama.cpp is another llama.cpp than the reference's.** The comparison of
  T2.2.2.5 can then differ for a reason that is no bug; the envelope names both versions so that the difference
  has a name.
- **The template is where the thinking switch and a declared function live**, and the header's own renderer knows
  no Jinja. If neither the binding nor a renderer in EinAf reproduces what `llama-server` renders, thinking cannot
  be turned off a call, and the arms that need it off (B0, B2 to B5) have no runtime but the fallback.
- **The first experiment shows the model its own answer.** Copying the example passes it, which is why it is
  the floor and not a result: what it can show is a model that cannot write Ein even then, or one that changes a
  program it was given whole. Its record says which, and no table reads it.
- **The probe's examples teach the test.** Sixteen problems are near one another, and under *a theory given* they
  share the theory too; the family rule keeps a twin out of an item's prompt and no more. The report says so,
  names the condition of every number, and carries none into a table of the benchmark.
- **A driver or library upgrade between runs** moves a number: [`host.md`](../analysis/host.md#the-machine) found
  the kernel module and the user-space libraries of the GPU at two versions. The envelope's runtime fields and
  `bench_env.sh`'s state are how a later reader knows.

### What was built

- **The runtime**, `einaf::model` ([`einaf/src/model/`](../../../einaf/src/model/mod.rs)): one trait, `Runtime`, a
  request in and a `Generation` (thinking apart from the answer, log-probabilities where asked, the envelope) or a
  typed `Failure` out; **the binding**, `einaf::model::llama::Llama`, behind the features `llama` (CPU) and `cuda`
  (GPU); **replay**, `einaf::model::replay::Replay`, always built, which answers a request from a record by its
  digest; **the chat template rendered in EinAf**, `einaf::model::template`, with `minijinja` over the template's own
  text (T2.2.2.3). The `llama-server` implementation is not written: the fallback was not taken.
- **The kernel's new entry**, `einaf::kernel::parse`: a parse with no load, every error a finding with its kind and
  place. `einaf::kernel` stays the one module that calls Ein's library.
- **The probe**, `einaf::probe`: the plan (items, families, conditions, every request whole), the two readings, the
  judgement through `einaf::kernel` (parse, the bounded call at root and `--single` under a 30-second clock, the forms
  set against a reference), and what would have prevented each kind of error.
- **The prompts**, versioned files under [`einaf/prompts/`](../../../einaf/prompts/): `ein-excerpt.v1.md`, the
  excerpt of Ein's syntax and semantics every prompt holds (about 3 000 of the model's tokens: § 1 words, § 2 forms,
  § 3 facts and relations, § 4 rules, § 5 the answer, § 6 the hypothesis mechanism, § 7 the library in brief, § 8
  what the kernel refuses, four programs, each loaded by a test); `ein-paragraph.v1.md`; `word-theory.v1.md`;
  `step1.v1.md`.
- **The command**, `einaf`: `render`, `generate`, `grammar`, `model`, `probe plan`, `probe run` (with `--model` or
  `--replay`), the experiments' one command each.
- **The page**, [`docs/einaf/05-model.md`](../../../docs/einaf/05-model.md): building with the feature, giving a run
  the model, the request, the envelope, the template, a grammar and where it begins, a kept context, the failures,
  replay, the commands, what holds it. `docs/einaf/README.md` lists it.
- **The tests** (EinAf's gate step, no model): `einaf/tests/model.rs` (replay field for field, `not-recorded`, the
  envelope read back and its prompt rendered offline, each typed failure from its recorded cause, a probe line

### Defaults taken

1. **The binding is `llama-cpp-2` 0.1.161**, the first candidate, which passed every check; the other three were not

2. **The runtime's features are `llama` (the binding, CPU) and `cuda` (`llama` with the CUDA backend)**, off by default;

3. **The chat template is rendered by EinAf**, `minijinja` over the template the file carries, with `trim_blocks`,

4. **A token's log-probability is the model's**, from its logits before the grammar and the chain (log-softmax over the
   whole vocabulary), with the top N alternatives.
5. **The grammar is applied before the chain, by itself**, so that a grammar that leaves no token is the failure
   `grammar-dead-end`, and where a lazy grammar began is the first token it constrained (`grammar.began_at`).
6. **A kept context is continued only where the prompt begins with every token it holds**; any other prompt is
   evaluated whole, the model's recurrent layers keeping no state that can be cut back.
7. **The envelope's prompt digest is of the token ids one a line in decimal**, beside the rendered text's; the
