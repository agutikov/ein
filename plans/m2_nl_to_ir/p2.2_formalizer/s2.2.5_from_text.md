## Context

**The command is `einaf from-text`**, EinAf's, one shot: a text becomes a program in the user's three steps (the
facts and a partial ontology, then the complete ontology and a partial theory, then the complete theory,
[the user's notes](README.md#formalization-in-steps-the-users-notes-on-the-whole-phase)), each step's program
judged at root and kept, the kernel is asked of the complete program, and the short answer is printed with the
run's record. There is no repair here and no generation of a step a second time. Its output on
the benchmark is baseline B2 ([S2.5.2](../p2.5_harness/s2.5.2_baselines.md)), and the filter calls the same
function as its GENERATE state ([S2.4.1](../p2.4_loop/s2.4.1_state_machine.md)). What the plan of August chained
it to, `ein solve -e --feedback`, never existed in that form: the kernel is linked, and its reply is a value.

**The answer**, by the user's ruling: *"don't run M1p now, use as much of existing ein NL features, e.g. query
:goal-text, for numbers and other compound facts use additional external formatters, they will be later starting
point for M1p"*. What Ein has, checked in the tree and on the corpus:

- **The filled line is a library value.** A query's `:goal-text` is filled per row of its answer, and
  `ein_infer::read_out::Class` holds, for each projection class, `rows` (each a list of a variable's name and
  its value) and `rendered` (each row through the `:goal-text`)
  ([`04-api.md` § 2.5](../../../docs/ein/ein.rs/04-api.md#25-read)). The read-out prints it in `“…”`; no key of
  `ein-summary/2` holds it. So EinAf does not have to build the line: it has to get a formatted value into it.
- **A value is its Ein text.** A row's value is a `String`, the value as Ein writes it, in the spelling the main
  file gives its names. [`bob1.ein`](../../../examples/word_problems/bob1.ein) answers
  *“(amount Bob apples t1): (n z 3)”*, [`more.ein`](../../../examples/word_problems/more.ein) *“Alice has (n z 7)
  more apples than Bob”*, [`boxes13.ein`](../../../examples/word_problems/boxes13.ein) *“with need read as
  pack-all: (n z 5) boxes, and z apples left unpacked”*, and
  [`kinds_full.ein`](../../../examples/word_problems/kinds_full.ein) prints one quantity as `(words.amount Alice
  apples now)`, by its full name, beside `(together Bob Alice apples now)`. One numeral has three texts by the
  form of the import that brought it: `(n z 5)`, `(d.n ar.z 5)`, `(std.math.decimal.n std.math.arith.z 5)`
  ([`04-stdlib/` § Importing a module](../../../docs/ein/user/04-reference/04-stdlib/README.md#importing-a-module)).
- **A line is printed per row and for nothing else.** A class where the goal has no row prints none, and neither
  does an empty R. *No*, *unknown* and *not enough information* are printed only where the theory
  derives a fact that says so, as the word theory's [`gaps.ein`](../../../examples/word_problems/gaps.ein) does
  ([P2.3 § Risks](../p2.3_benchmark/README.md#risks)).
- **An explanation is the kernel's trace**: a firing with its rule's `:why` filled, a given premise with its
  `:source` ([natural language, § 3](../../../docs/ein/user/03-syntax-and-semantics/14-natural-language.md#3-a-fact-in-english-the-fallback-ladder)).

**The form of the answer is every arm's, and it is a sentence** (the user's ruling, [Q-M2.12](../open_questions/answer/Q-M2.12-what-prints-the-answer.md): *"a sentence,
like zebra's “The Norwegian drinks water in House-1; the Japanese owns zebra in House-5”"*). Each arm is given
the same answer line, which asks for a sentence or two in the problem's words, and is scored by what its sentence
states, the values the gold sentence binds, not by equality of two sentences
([the frame's default 7](../README.md#the-defaults-the-re-plan-took);
[S2.5.2](../p2.5_harness/s2.5.2_baselines.md), [S2.5.3](../p2.5_harness/s2.5.3_metrics.md)). So the answer
query's `:goal-text` is that sentence ([the contract](s2.2.1_contract.md)), and what this stage prints is the
line with its values formatted: in *Bob has (n z 3) apples* the numeral becomes *3*.

**Nothing in a solve stops a saturation that has no fixpoint.** A program of one rule that builds a fact out of
the fact it matched, `(num ?x)` concluding `(num (s ?x))` over `(num zero)`, run at this re-plan under
`ein solve -T 1` three ways (a bare solve with `--region-budget 1000`, `--single`, `--no-search`), was still
running each time when it was killed after five seconds; `ein saturate --max-steps 50` stops it at fifty
firings. [S2.4.1](../p2.4_loop/s2.4.1_state_machine.md) says why. A model will write such programs, so **the
one shot runs the kernel through EinAf's bounded kernel call**, `einaf::kernel`'s, which sets the kernel's own
clock and limit, made to reach inside a saturation by S2.1.2
([S2.1.3](../../../docs/einaf/03-feedback.md#1-the-bounded-call), T2.1.3.2b; the frame's default 16). A call it stops is *not decided*. This stage does not design that call.

**The metadata of a run is in the record, not in the program.** The program is a plain input of the kernel.

## Tasks

### Task T2.2.5.1 — The command, and the function under it

The one shot is a function of the library: a text and a configuration in; the program, the findings of the
contract's check, the feedback objects, the answer and the envelopes out. `einaf from-text` is its command for
one text. `einaf run` ([S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md)) and the filter's GENERATE call the
same function. The options, as a sketch:

```text
einaf from-text PATH
  [--model PATH]          the model's file (S2.2.2)
  [--mode steps|whole]    the formalizer's mode (S2.2.4): the three steps, or the whole program
                          in one call; default steps
  [--no-grammar]          the grammar off: the probe's and the ablation's setting
  [--module-dir DIR]      a directory of theory modules the program may import: Q9's escape hatch,
                          the widest condition of the library ablation, and no part of the main arms
  [--out PATH]            write the program
  [--explain PATH]        write the kernel's trace of the answer, as markdown
  [--record DIR]          the record (default: a new one under einaf/experiments/)
  [--seed N]              recorded
  [--replay DIR]          take the generations from a record: no model is loaded
```

What it does, in order: formalize in the three steps ([S2.2.4](s2.2.4_passes.md)), each step's program assembled
in synthesis order, checked, and judged at root through `einaf::kernel`'s bounded call, the model not shown that
judgement before the next step (the steps' second design question; showing it is
[P2.6](../p2.6_ablations/README.md)'s arm); then, of the complete program, run the contract's check; hand it to
the bounded call with the questions below; read the feedback objects; print the outcome and the answer; write the
record.

- **The questions asked** are the least the answer needs: whether R is one state, and, where the reply lists two
  states and the answer query's classes are therefore a lower bound, the description of R, so that the classes
  are over the part of R the query names. [S2.4.1](../p2.4_loop/s2.4.1_state_machine.md)'s plan of questions
  takes this over when it exists. The three readings of *certified* are taken of the recorded program
  afterwards, as a derived file of the record ([S2.5.3](../p2.5_harness/s2.5.3_metrics.md)); no reading is
  called certified here ([Q-M2.10](../open_questions/answer/Q-M2.10-what-does-ein-certifies-a-unique-model-mean-on-r.md)).
- **The bounds** are recorded: the kernel's own (the region budget, the limit, the deadline) and the two of
  EinAf's kernel call.
- **Nothing outside `einaf::kernel` calls the engine's crates**
  ([S2.1.3](../../../docs/einaf/README.md#what-it-depends-on)'s acceptance). What this file names of
  them (`Class::rendered`, `render_why`, the trace) is what `einaf::kernel` reads or wraps, and this stage adds
  to it what the feedback object does not yet carry.

### Task T2.2.5.2 — The record, per run

In [S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md)'s layout, and nothing beside it: the configuration with
every field of [the contract's B4](s2.2.1_contract.md); a line a call of the model, the envelope and the raw
output; for each step, its output as the model wrote it, the program assembled up to it and its judgement at root
(the feedback object, and the check's findings that apply to it); the complete program as the model wrote it; a
line a question asked of the kernel, the feedback object; and the answer's line, which this stage defines:

| in the answer's line | what |
|---|---|
| the kernel's lines | each row of the answer query through its `:goal-text`, as the kernel filled it |
| the formatted lines | the same rows with EinAf's formatters over the values: the answer that is scored |
| the fixed text | where there is one, which, and the outcome it was chosen by |
| where the answer came from | the program's own `:goal-text`, or EinAf's fixed text |
| the alternatives | where the answer query has two classes or more, each class's lines |

Two things the layout has no line for and this stage asks of S2.5.1: **the sidecar** of
[S2.2.1](s2.2.1_contract.md) (the category of each form with the step that wrote it, and the findings of the
contract's check, by step), a file beside each program; and the trace, where `--explain` asked for it. The old acceptance, *a saved program can be
reproduced months later*, becomes: `--replay` on a record gives the same program and the same answer, and a test
does so on a captured record.

### Task T2.2.5.3 — The answer: the line, the fixed texts, the formatters

**What is printed** is chosen by the answer rule of [S2.5.3](../p2.5_harness/s2.5.3_metrics.md), which is a
parameter of the evaluation and that stage's default; this stage prints by it and words what it prints. The
answer query is the one [the contract](s2.2.1_contract.md) names.

| the kernel found | `einaf from-text` prints | whose words | an answer |
|---|---|---|---|
| a state in R, and the answer query has one class, with a row, over a complete set | each row through the `:goal-text`, its values formatted | the program's `:goal-text`; a value's text is EinAf's | yes |
| a state in R, and two classes or more | **The statements do not determine the answer.** Beneath it, each class's lines, as alternatives | EinAf's; the alternatives are the program's | yes: *ambiguous* |
| a state in R, and one class with no row | **The statements do not determine the answer.** | EinAf's | yes: *ambiguous* |
| *inconsistent* | **The statements contradict each other.** | EinAf's | yes: *unsatisfiable* |
| *incomplete* | **No answer: the program is incomplete.** Beneath it, what is owed, in the kernel's sentences | EinAf's; the kernel's beneath | no |
| *not decided* | **No answer: not decided.** Beneath it, what stopped the run | EinAf's | no |
| *flagged* | **No answer is claimed: the program is not monotone.** Beneath it, the kernel's warning and what it printed | EinAf's; the kernel's beneath | no |
| *invalid* | **No answer: the program was refused.** Beneath it, the diagnostics, each with its kind and place | EinAf's; the kernel's beneath | no |

- **The text is chosen by the answer query's classes, not by the kernel's word alone.** `boxes12.ein` is
  `Ambiguity`, two states, and its answer query has one class: it prints its own answer, the readings agreeing.
  Where the classes are over the two states one question listed and not over a complete set, the description is
  asked (T2.2.5.1), and if that is not decided the line is the *not decided* one.
- **The fixed texts are EinAf's, not Ein's, and never the model's.** They are chosen by the kernel's values and
  written once, as constants of `einaf/src/`. The first two are answers: the same strings are the ones
  [S2.5.2](../p2.5_harness/s2.5.2_baselines.md)'s answer line lets every arm give, and the gold short answer of
  an instance whose class is *ambiguous* or *unsatisfiable*
  ([P2.3](../p2.3_benchmark/README.md#defaults-taken-at-the-re-plan), its default 4). The other four are lines of
  the command and are scored as no answer. Whether *incomplete* is scored as the unsatisfiable text instead is
  S2.5.3's rule, under which both are reported.
- **This is the one place where the answer is not the Ein program's own output**
  ([the frame's default 15](../README.md#the-defaults-the-re-plan-took)), against
  [Q-M2.12](../open_questions/answer/Q-M2.12-what-prints-the-answer.md)'s *produced by ein program NL output*. It is a
  default the user may correct. What would remove it is a program that derives a fact for each such case and
  prints it, as the word theory's `gaps` module does for a quantity the problem does not state; an empty R has no
  state to print from, so *contradict* cannot be the program's own line at all.
- **The wording** is this stage's to settle with one check: each text reads as an answer to any question of the
  benchmark's families (*who*, *how many*, *which*, *can*), since one string serves all.

**How a formatted value gets into the answer: the template is filled again, the kernel's line is not edited.**
The feedback object gives the answer query's `:goal-text`, its rows and the kernel's own line. EinAf formats each
value of a row and fills the template by the kernel's rule: a reference `{?v}` the row binds is replaced by the
value, and one nothing binds is left as written. Editing the rendered line instead would mean finding a value's
text inside a line, and a value's text is not unique there: zero prints as `z`, and `boxes13.ein`'s line holds
`(n z 5)` and a bare `z` together. A row keeps each value apart, under its variable. With no formatter applied
the two routes give the same bytes, which is the first acceptance test, and the record keeps both lines. The
kernel's own filler is `ein_core::render_why`; `einaf::kernel` calls the crates only through its bounded call
([S2.1.3](../../../docs/einaf/03-feedback.md#1-the-bounded-call)), so whether the fill is that function
there or a filler of EinAf's held to it by the test is the stage's.

**The formatters.** One a kind of value, each a function from a term to a text:

1. **A decimal numeral**, `z` or `(n PREFIX DIGIT)`
   ([Q-M1f.361](../../../docs/decisions/stdlib/math/decimal/Q-M1f.361-a-natural-number-is-a-numeral-of-digit-names.md)),
   to its digits. A term that is headed like a numeral and is not one prints as written.
2. **A fact that stands as a value**, by cases that are data: a relation, a count of arguments and a template
   over the arguments, one file a theory. The first file is the word theory's quantities (`amount`, `together`,
   `apart`, `needed`, `each-of`, `rest-of` and the others its README lists), for a canonical program that prints
   one. A value with no case prints as written: no words are invented for a relation EinAf has no case for,
   which is Ein's own rule for a fact
   ([natural language, § 3](../../../docs/ein/user/03-syntax-and-semantics/14-natural-language.md#3-a-fact-in-english-the-fallback-ladder)).
3. **The other numerals** (an integer, a rational, a binary numeral), each added when a family prints one. The
   kinds the benchmark's families print are a list [S2.3.1](../p2.3_benchmark/s2.3.1_families_and_seed_set.md)
   hands over; it comes after this stage in work order, so adding a kind is built to be an addition: a formatter,
   its cases, its tests.

- **A formatter reads a term, and the term comes from text.** The stage writes the reader of a value's text, and
  resolves a printed name to its full name from the program's imports, so that a formatter matches
  `std.math.decimal.n` whatever the file calls it. If `einaf::kernel` can hand over a row's values as the
  library's own values instead, that is the better input, and the stage says which it took.
- **Written to be [M1p](../../m1p_ein_to_natural_language/README.md)'s starting point**, as the ruling asks: a
  formatter is a kind of value's and nothing else's; its cases are data beside it; its tests are beside it; it
  reads the term alone; and it knows nothing of the model, the loop, the record or the benchmark, which the
  module's own build holds. The questions
  [P1p.1](../../m1p_ein_to_natural_language/p1p.1_custom_formatting/README.md) leaves open (who says how a value
  is written, what a format may read, its other direction) are M1p's: EinAf's choices here are defaults of an
  application, and nothing of Ein reads them.
- **Where else they apply**: the feedback ladder's wording
  ([S2.4.3](../p2.4_loop/s2.4.3_feedback_ladder.md)) and what a tool's call returns
  ([S2.4.6](../p2.4_loop/s2.4.6_ein_as_a_tool.md)) send a value that does not read as text through them. The
  trace `--explain` writes is the kernel's and is not formatted: giving every line of reasoning its words is
  M1p's subject, not an answer's.

### Task T2.2.5.5 — The word problems, one shot

The sixteen problems of [`examples/word_problems/`](../../../examples/word_problems/README.md), each from its
text, **the model shown the library alone**, which is the main arms' condition ([S2.2.4](s2.2.4_passes.md),
T2.2.4.8): a problem is written over the calculator, with whatever rule the model needs. No item is shown an
example of its own text family. One record. The table, per problem: whether the output parsed, whether it
loaded, the outcome, the findings of the contract's check, the answer query's classes, the answer printed, and
the answer that directory's README states, compared by S2.5.3's reader. The same sixteen with that directory as
the module directory, the widest condition of the library ablation, are a second record, labelled so.

The shape of such a program, run at this re-plan:

```lisp
;; Bob has 5 apples. He gave 2 to Alice. How many apples does Bob have?
(import std.math.decimal-arith :symbols (sub diff-of))
(import std.math.decimal :symbols (n))
(import std.math.arith :symbols (z))

(relation has Person Kind Number :why "a {?3} has a {?5} of a {?4}")
(has Bob apples (n z 5) :source "Bob has 5 apples.")
(sub (n z 5) (n z 2)    :source "He gave 2 to Alice.")

(solve :no-search)
(query :goal (diff-of (n z 5) (n z 2) ?n ?r) :goal-text "Bob has {?n} apples")
```

`ein solve --single` answers `Solution`, the static check monotone (run at the re-plan with the `:goal-text`
`"{?n}"`, where the line was *“(n z 3)”*; the sentence is the ruling's), and the first formatter makes the line
*Bob has 3 apples*, which states what the gold answer states. The re-plan's first writing of the goal was
`(diff-of (n z 5) (n z 2) ?n)`: three arguments where the calculator's answer has four. That program loaded, the
word was `Solution`, and the read-out said *the goal has no row: undetermined here*: a relation is overloaded by
its count ([E-12](../evaluation/language/E-12-an-undeclared-relation-and-a-form-of-a-declared-relation-at.md)), nothing the kernel printed named the slip, and the answer rule reads
the program as *ambiguous*. The contract's check is what sees it ([S2.2.4](s2.2.4_passes.md), T2.2.4.6).

- **The kernel's word is not the problem's class.** `gap.ein` answers `Solution` and its right answer is *not
  enough information*; `boxes12.ein` answers `Ambiguity` and has one answer
  ([E-14](../evaluation/answer/E-14-the-kernels-word-is-not-the-problems-class.md)). So the table shows the answer query's classes beside the outcome, and reads
  correctness off the answer.
- **The hard ones are where synthesis is measured.** A problem whose right answer is *not enough information*,
  or that turns on a word with two readings, is answered in the corpus by the family's own modules. With the
  library alone the model has to write that reasoning or miss it, and which it did is the table's finding.
- **These are the part of the seed set that exists when the phase runs**: the second domain's. The anchors of the
  eight families are [S2.3.1](../p2.3_benchmark/s2.3.1_families_and_seed_set.md)'s, after this phase in work
  order, and the one-shot run over the benchmark is the Level B run
  ([S2.3.4](../p2.3_benchmark/s2.3.4_splits.md)).
- The table is labelled *word problems, one shot*, and is not called a result: prompts were developed on these
  problems.

### Task T2.2.5.6 — What the stage found of Ein

To [the evaluation of Ein](../evaluation/README.md), each entry with its program and its command. This re-plan met

## Risks

- **The answer's template is the model's.** A `:goal-text` can hold a name of its own beside its references, which
  answers without the kernel, or name a variable nothing binds, which prints as written. The check reports both
  ([S2.2.4](s2.2.4_passes.md)), and [S2.4.4](../p2.4_loop/s2.4.4_faithfulness.md)'s mechanical judge notes the
  first.
- **A sentence is the model's own wording.** The `:goal-text` is free in its words and held in its values, so
  two right programs print two sentences; the score reads what a sentence states
  ([S2.5.3](../p2.5_harness/s2.5.3_metrics.md)), and a sentence that says the right value of the wrong thing is
  that rule's to catch, with the gold claim the kernel checks beside it.
- **A short answer is not guaranteed short.** A value with no case prints as its term, and a model's own nested
  facts have no case. The count of answers that still show a term is reported, and the contract asks for a goal
  whose variables bind names and numerals.
- **One fixed string for every kind of question** may read badly as an answer to some. It is scored as a string,
  the same for every arm, so its wording moves no comparison; it is the user's to correct all the same.
- **Formatters that drift from what M1p will want.** M1p's questions are open, and nothing of Ein depends on
  EinAf's choices: what M1p takes is the cases and the tests, which are data.
- **The questions asked decide the cost** ([E-17](../evaluation/bounds/E-17-what-a-run-costs-depends-on-the-question-asked-of-it.md)): a description of an under-determined
  program can run to the budget. The one shot asks for it only where the classes would otherwise be a lower
  bound, and a description the budget stops leaves the answer *not decided*.
