## Context

The old P2.2 — a `llama-server` container and a thin client, the pattern
lifted from acva — survives the reshape intact except for two words: the
client is no longer "Python *this time* instead of C++" because ein was
Python (it is Python because [S2.1.3](../p2.1_kernel_as_instrumentation/s2.1.3_boundary.md)
says the harness is; paths below assume that), and the model is no longer
a *product choice with a fallback* but an **experimental constant**. Stage
D's comparison is *same model, similar budget, different feedback*; one
model is pinned by file SHA for the whole of Level C, and a second model is
a replication arm, run once, reported apart.

Why a separate process, unchanged from the old plan: a warm cache that
survives harness restarts; the harness never blocks on inference; models
swap by one `.env` line; and reproducibility is a container digest plus a
model file SHA, both in the record, rather than a Python environment. Why
`llama-server` and not `ollama`, settled in
[Q25](../open_questions.md#q25--what-language-is-the-frontend-written-in):
GBNF is the mechanism and ollama's API exposes only JSON-schema `format`.
acva's `packaging/compose/docker-compose.yml` (out of tree) runs the
official `ghcr.io/ggml-org/llama.cpp:server-cuda` image with the GGUF
directory mounted read-only and the model named from `.env`; that file is
the template.

## Acceptance

- `docker compose -f packaging/compose/llm.yml up -d` starts `llama-server`
  with a pinned image digest and a pinned model file; `/health` passes
  within 30 s on the dev workstation.
- `einaf llm smoke "Hello"` returns a constrained greeting under the
  smallest grammar in `grammars/`, and the invocation envelope it prints
  has every field of [S2.2.1 T2.2.1.4](s2.2.1_contract.md).
- Unit tests green offline against a mocked server; integration tests
  skip, not fail, without `LLAMA_HOST`.
- One model pinned for Level C by SHA-256, chosen by a measurement on the
  seed set and recorded beside [Q23](../open_questions.md#q23--local-model-choice);
  the hosted replication arm decided beside
  [Q-M2.2](../open_questions.md#q-m22--must-the-model-be-local).

## Tasks

### Task T2.2.2.1 — The Compose service

`packaging/compose/llm.yml`, lifted from acva's `llama` service and trimmed:

```yaml
services:
  llama-server:
    image: ghcr.io/ggml-org/llama.cpp:server-cuda@sha256:<digest>
    container_name: einaf-llama
    ports:
      - "127.0.0.1:${LLAMA_PORT:-9080}:8080"
    volumes:
      - ${EINAF_MODELS_DIR:?set in .env}/llama.cpp:/models:ro
      - ${EINAF_GRAMMARS_DIR:-./grammars}:/grammars:ro
    deploy:
      resources: { reservations: { devices: [ { driver: nvidia, count: 1, capabilities: [gpu] } ] } }
    healthcheck:
      test: ["CMD", "curl", "-fsS", "http://127.0.0.1:8080/health"]
      interval: 5s
      timeout: 2s
      retries: 12
      start_period: 30s
    command: ["--host", "0.0.0.0", "--port", "8080",
              "--model", "/models/${EINAF_LLM_MODEL:?set in .env}",
              "--ctx-size", "8192", "--n-gpu-layers", "999", "--threads", "4",
              "--metrics"]
```

`.env.example` documents `EINAF_MODELS_DIR`, `EINAF_GRAMMARS_DIR`,
`EINAF_LLM_MODEL` (a file name under `$EINAF_MODELS_DIR/llama.cpp/`),
`LLAMA_PORT`. The image is pinned **by digest**, not by tag: the tag moves
and the record needs the digest anyway. `--ctx-size` is a recorded
parameter, because the B3 prompt (spec excerpts + catalogue + few-shot +
problem) has to fit it and the record has to say what fit.

### Task T2.2.2.2 — The model script and its manifest

`scripts/get-model.sh <url> <sha256>` downloads into
`$EINAF_MODELS_DIR/llama.cpp/`, verifies the SHA-256, refuses to overwrite
a verified file, and appends to `models/manifest.json` — name, URL, SHA,
size, date — so several candidate models coexist locally without
confusion and the record can name one by SHA. The old plan had the SHA
live in a decision document; it lives in the manifest and in
[Q23](../open_questions.md#q23--local-model-choice)'s entry, which is where
a verdict lands now.

### Task T2.2.2.3 — The client

`einaf/llm/client.py`. Two flavours, as before — plain chat for
inspection, constrained for the passes — and a small dependency surface:
`httpx` for HTTP, dataclasses for the types, no orchestration framework.

```python
@dataclass(frozen=True, slots=True)
class LlmRequest:
    messages:    list[dict[str, str]]
    grammar:     str | None = None      # GBNF text; llama-server's `grammar` field
    max_tokens:  int = 2048
    temperature: float = 0.0            # deterministic per seed for the passes
    seed:        int | None = None

@dataclass(frozen=True, slots=True)
class LlmResponse:
    text: str; usage: dict[str, int]; model: str; seed: int; timing: TimingInfo

class LlmClient:
    def __init__(self, base_url: str, timeout: float = 120.0): ...
    def complete(self, req: LlmRequest) -> LlmInvocation: ...
    def props(self) -> dict: ...        # GET /props — the server identity
```

POST to `/v1/chat/completions`, the `grammar` field passed as llama-server
expects it at the pinned image's version (the task checks the field name
against that version's docs and pins the check as a test). Typed failures:
`LlmTimeout`, `LlmContextOverflow`, `LlmGrammarReject` (the grammar could
not produce output — a logic bug, **never retried**), `LlmServerError`
(5xx). Retry policy: three attempts with exponential backoff on timeout and
5xx; none on overflow or reject, which are surfaced to the pass with the
prompt length in the message.

### Task T2.2.2.4 — The invocation envelope

Every call returns an `LlmInvocation`, which is the record's first field
([S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md)):

```python
@dataclass(frozen=True, slots=True)
class LlmInvocation:
    model_sha256: str          # from models/manifest.json, matched to /props' model path
    server_image: str          # the image digest, from the Compose file
    server_id:    str          # llama-server's startup identity, from /props
    grammar_sha256: str | None
    prompt_sha256: str         # of the rendered messages
    request:  LlmRequest
    response: LlmResponse
```

The old plan attached this to the IR as a `:llm-source` field in the
trace; it does not — the program stays a plain kernel input
([S2.2.5](s2.2.5_from_text.md)) and the envelope lives in the record.

### Task T2.2.2.5 — Tests

`einaf/tests/llm/`: a mocked `httpx` transport returning canned responses
exercises retry, parse and the typed failures offline; an integration test
marked to skip without `LLAMA_HOST` round-trips `grammars/greeting.gbnf` —
`root ::= "(greeting \"" [a-z]+ "\")"` — and asserts that only grammatical
output is produced across ten seeds.

### Task T2.2.2.6 — The model, measured: Q23 and Q-M2.2

Three candidates — Qwen3-30B-Instruct (the old primary), Phi-4 14B (the
old fallback), and one more the task picks from the current llama.cpp
leaderboards for structured output — each run one-shot on the seed set
([S2.3.1](../p2.3_benchmark/s2.3.1_families_and_seed_set.md)) through the
passes of [S2.2.4](s2.2.4_passes.md) with the same prompts and grammars,
three seeds, reporting parse rate, load rate, answer accuracy, tokens/s
under the full grammar, context needed, and — because the contract admits
RU input — the same columns on the RU half of the seed set. **One** model
is pinned by SHA for Level C on those columns, with the reading written
before the run (accuracy first, tokens/s as the tie-break, RU as a
reported column not a gate). The verdict lands beside
[Q23](../open_questions.md#q23--local-model-choice).

[Q-M2.2](../open_questions.md#q-m22--must-the-model-be-local)'s
recommendation is taken as written: local is the primary condition; a
hosted model is a **replication arm** with a second client (`einaf/llm/hosted.py`,
same `LlmRequest`, no `grammar` — the grammar's work falls to the loader,
which is F1), run once at the end of Level C on `val` with the same
prompts, reported as a separate table whose caveats (no GBNF, a version
the provider can retire, a different token accounting) sit where the
numbers are. The two are never in one table.

## Notes

- `ollama` is recorded as *not an option* in Q25; this stage does not
  re-open it.
- The old plan's `docs/llm-infra.md` lifecycle page (start, logs, stop,
  swap model) is still wanted; it is a section of `docs/einaf/` rather than
  a top-level page, beside the contract.
- CPU-only fallback: the image tag `server` (no CUDA) works with the same

  show; it is for the smoke test on a machine without a GPU, not for a
  table.
