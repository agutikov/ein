# S2.5.1 — The experiment record and the canonical workflow

**Phase:** [P2.5](README.md) (Baselines, metrics, records: Stages D, H, N)
**Depends on:** [S2.1.1](../p2.1_kernel_as_instrumentation/s2.1.1_tree_and_outcomes.md): `einaf/` exists and has
its gate step; [S2.1.3](../p2.1_kernel_as_instrumentation/s2.1.3_feedback_object.md): the feedback object is what
a kernel line holds; [S2.2.2](../p2.2_formalizer/s2.2.2_model_runtime.md): the envelope is what a generation line
holds. **Runs before the phase it belongs to**: the record is in use from P2.2's first run, the probe of
[S2.2.2](../p2.2_formalizer/s2.2.2_model_runtime.md)
([README § Order](README.md#order)).
**Research plan:** [`EinAf.md` § Stage N](../EinAf.md#stage-n--reproducibility);
[B4](../EinAf.md#b4-establish-prompt-versioning) (*prompt changes are experimental changes*).

## Context

Stage N is the research plan's last stage but three and this milestone's first deliverable after the tree, for a
reason the project already works by: a time is read only with the machine state it was taken in, and the corpus's
`cost_ms` is a measured claim, checked in both directions. Applied to an experiment with a model: a number without
the model's file by its SHA, the prompt's hash, the seed, the kernel's commit and the split's digest is a demo
that happened once.

So the record is the **unit of evidence**. A table is a view over records, a plot is a view over records, and a
sentence of the paper cites a record's id. Nothing of this milestone exists only in a terminal's scrollback.

**Where.** `einaf/experiments/`, a folder of EinAf's tree
([Q-M2.8](../open_questions.md#q-m28--where-does-einaf-live);
[README § Where EinAf's things are](../README.md#where-einafs-things-are)). The research plan's example,
`docs/experiments/`, is not taken: a record is data (lines of JSON, programs, compressed event streams) that
prose is generated from. The old plan sent the milestone's measurement documents to `docs/history/` at the close;
that directory is gone ([`audit_p2.5_p2.6.md`](../analysis/audit_p2.5_p2.6.md) § C.2), so a table and its reading
stay with the records, under `einaf/experiments/reports/`, and a page that explains them is a page of
`docs/einaf/`. Records are dated measurements by nature; the rules of Ein's own prose (no date, no measurement)
are Ein's and do not reach `einaf/` (the ledger's reading of Q-M2.8).

**What one record is.**

```text
einaf/experiments/
  README.md                    the index, a line a record: id, date, what it is evidence for,
                               split and digest, the repository's commit, status
  store/<sha256>               every prompt, grammar and chat template a record used, by content
                               hash; written at run time, never edited
  reports/<name>/              tables, plots and readings, each naming its record ids
  exp-0042/
    README.md                  written BEFORE the run, the pre-registration: what the record is
                               evidence for, and the reading each outcome has
    config.json                einaf-record/1: what was run (below)
    machine.json               the machine as the run found it (T2.5.1.7)
    instances.jsonl            the instance ids, with the split and its digest
    generations.jsonl          every call of the model: S2.2.2's envelope, the raw output whole
    programs/<instance>/<seed>-<n>.ein   every program the model wrote, as written: kernel input;
                               beside each, the contract's sidecar (the category of each form and
                               the findings of the contract's check: S2.2.1), and a trace where
                               one was asked for
    kernel.jsonl               every question asked of the kernel: the feedback object (it says
                               what was asked and the work), and whose episode and step it was
    transitions.jsonl          the transcript, a line a step: a transition of the filter
                               (S2.4.1) or a turn of the tool's episode (S2.4.6)
    answers.jsonl              per instance and seed: the answer as given and where it came
                               from: the model's last message, or for an arm with a program the
                               answer's line S2.2.5 defines (the kernel's sentences, the formatted
                               ones, the fixed text, the alternatives)
    events/…                   ein-events/1, only where a feedback level reads it
    readings.jsonl             derived: each reading of *certified* and the gold claim's verdict
    kernel_cost.jsonl          derived: the kernel's own wall and peak memory, by replay (S2.5.3)
    metrics.json               derived: einaf-metrics/1, by `einaf evaluate`
```

**Taken and derived.** `einaf run` writes the taken files once and nothing rewrites them. A derived file is a
function of the taken files, and for two of the three of the kernel at the record's commit; it is rewritten only
by the command that owns it, which writes the commit it ran at into the file. A reading of *certified* is derived
on purpose: what it means is open
([Q-M2.10](../open_questions.md#q-m210--what-does-ein-certifies-a-unique-model-mean-on-r)), and a reading the
user asks for later is taken of the recorded programs with no new call of the model.

`config.json` names, and a missing field is a rejected record:

```json
{ "schema": "einaf-record/1", "id": "exp-0042",
  "arm": "B5", "arrangement": "filter", "level": "F8", "strategy": "repair",
  "thinking": false, "grammar": "sha256:…",
  "budget": {"generated_tokens": 0, "iterations": 0, "tool_calls": null},
  "repository": {"commit": "…", "dirty": false},
  "kernel": {"stdlib_manifest_sha256": "…", "stdlib_from": "checkout",
             "config": {"lattice-sanity-check": false, "record-alternative-justifications": true},
             "questions": ["…"], "region_budget": 1048576, "region_limit": 16, "deadline_s": null,
             "worker": {"wall_s": 0, "memory_bytes": 0}, "jobs": 1, "allocator": "…"},
  "model": {"name": "qwen3.5:4b", "file_sha256": "…", "binding": "…", "llama_cpp": "…", "backend": "…",
            "context": 0, "chat_template": "sha256:…"},
  "sampler": {"chain": ["…"], "seeds": [1, 2, 3], "max_tokens": 0},
  "prompts": {"…": "sha256:…"},
  "benchmark": {"version": "…", "split": "val", "split_digest": "…", "opens_test": null} }
```

The zeros and the ellipses stand for values a run fills; no number above is a choice of this file but the two
defaults of the kernel's bounds, which are the kernel's.

**The kernel's fields, each as the tree has it** ([`audit_p2.5_p2.6.md`](../analysis/audit_p2.5_p2.6.md) § B.1):

| field | where it comes from |
|---|---|
| `repository.commit`, `dirty` | **git, not the kernel**: `ein --version` prints five lines and none is a commit, and the crates compile none in. EinAf links `ein.rs/` by path in one repository, so one commit names the kernel, the library and EinAf; it is the commit EinAf was built at, with whether `ein.rs/`, `stdlib/` or `einaf/` differed from it |
| `stdlib_manifest_sha256`, `stdlib_from` | the SHA-256 of `MANIFEST.sha256` as the linked `ein-ir` resolves it (`$EIN_STDLIB`, the checkout, the embedded copy: `ein_ir::stdlib`), which is what `ein --version`'s `stdlib` line prints, and which of the three answered. The load tests that the manifest is there, not that it matches the files; the gate holds the manifest to the files at a commit, so the SHA names the library of a clean build of a gated commit |
| `config` | the resolved config, **two flags** ([`06-config.md`](../../../docs/ein/user/04-reference/06-config.md) § 2). Neither changes R; `record-alternative-justifications` may change which core a dead node reports, which is what one feedback level renders, so it is pinned |
| `questions` | which questions the arrangement asks each program (a bare solve, `--single`, a line, `--count`): [S2.4.1](../p2.4_loop/s2.4.1_state_machine.md)'s choice, and more than one where a feedback level reads what one question does not fill (a dead root's core is filled under a description and is `null` under `--single`). A field here because **the work and what is known depend on it**: on `examples/zebra2.ein`, `--single` and a description do different numbers of saturations and fill different keys ([`audit_p2.5_p2.6.md`](../analysis/audit_p2.5_p2.6.md) § B.2, § B.4). Each line of `kernel.jsonl` says what was asked of it, as `ein-summary/2`'s `asked` block does |
| `region_budget`, `region_limit` | the kernel's bounds that stop a run **with an answer**: facts beyond root summed over every saturation (the default is the kernel's, 2^20), and the largest cube a flagged program gets. A run that reaches one says what it established; where its question was not decided by then, the outcome is *not decided* |
| `deadline_s` | the kernel's own clock, `-T`, where a run sets it: past it the run is an error and no answer, for the library as for the binary, which then writes no summary. It is checked between a route's steps and does not stop a saturation that does not end ([S2.4.1](../p2.4_loop/s2.4.1_state_machine.md) has the probe) |
| `worker` | the two bounds EinAf itself holds a kernel call to, a wall clock and a memory size, since the kernel runs in a worker process of EinAf's that the parent can stop ([README § The defaults](../README.md#the-defaults-the-re-plan-took), 16; [S2.1.3](../p2.1_kernel_as_instrumentation/s2.1.3_feedback_object.md) builds it). A call stopped by either is *not decided*, by a diagnostic of EinAf's own. Both are machine-dependent, so what they stop is recorded as stopped by them and never read as another outcome |
| `jobs` | the kernel's threads; the same read-out at any count |
| `allocator` | EinAf's build's: the `ein` binary links snmalloc and a library links none ([`04-api.md`](../../../docs/ein/ein.rs/04-api.md) § 5), so a wall or a peak taken in EinAf's worker is not the `ein` binary's |

**The kernel says no time and no memory.** `ein-summary/2`, the events and the answer's files carry neither; the
`-t` table is text on stdout. EinAf takes both itself, in the worker: its clock stands around the load and around
each question, apart (`ein solve examples/zebra2.ein --single -t` shows the load taking more of the wall than the
route), and the worker's peak resident memory is the kernel's alone, the worker holding no model. Those are a
run's figures, taken with whatever else the machine was doing; the controlled ones are
[S2.5.3](s2.5.3_metrics.md)'s replay.

**The model's fields are [S2.2.2](../p2.2_formalizer/s2.2.2_model_runtime.md)'s envelope**, the part of it that
is constant over a run: the model's file by its SHA, the binding and the llama.cpp it links, the backend, the
context size, the sampler chain with the grammar's place in it, the seeds, the chat template by hash, thinking on
or off. A field S2.2.2 adds to the envelope is a field here. The model runs in EinAf's process
([Q-M2.14](../open_questions.md#q-m214--what-runs-the-model)): there is no server and no image whose digest a
record could name, and the model's file is not in the repository.

## Acceptance

- `einaf/experiments/` exists with its index, the store and the layout above; `einaf run` creates a record and
  refuses to write into an existing one.
- `einaf evaluate <record>` writes `metrics.json` from the record's files and nothing else, and is deterministic:
  two evaluations of one record are byte-identical. A record with a missing `config.json` field is rejected with
  the field named.
- `einaf report` over two identical records gives identical tables, and every table carries a footer with the
  record ids and the digests of their `config.json`.
- A record names its kernel: the repository's commit, the library's manifest SHA with where it was found, the
  resolved config, the questions, the bounds. `einaf run` refuses a build whose tree differed from its commit
  unless told to, and then the record says `dirty`; `einaf report` puts no dirty record and no two commits in one
  table without a flag that prints the fact in the caption.
- The first record is the probe of [S2.2.2](../p2.2_formalizer/s2.2.2_model_runtime.md), and the runs of
  [S2.2.5](../p2.2_formalizer/s2.2.5_from_text.md) follow it; ids are allocated in order and never reused.
- The tests are in EinAf's gate step and need no model.

## Tasks

### Task T2.5.1.1 — The layout and `einaf-record/1`

The directory and the `config.json` schema above, with the versioning rule
[`05-events.md`](../../../docs/ein/ein.rs/05-events.md) states for the event protocol: an added optional field
keeps the number, a removed or renamed field moves it, and `einaf evaluate` refuses a schema it does not know.
`kernel.jsonl`'s line is the feedback object of
[S2.1.3](../p2.1_kernel_as_instrumentation/s2.1.3_feedback_object.md), which says what was asked, the outcome and
the work (`saturations`, `facts`, `layers`), with what is the record's beside it: the episode and the step the
call belongs to, the load's wall apart from the question's, and the worker's peak memory. The stage begins by
reading the object as S2.1.3 built it and the envelope as S2.2.2 built it, and adds to neither what one of them
already holds.

### Task T2.5.1.2 — `einaf run`: allocation, pre-registration, immutability

Ids are `exp-NNNN`, in order, allocated by adding the index line. So **the index line and the pre-registration
`README.md` exist before the first call of the model**, and a run that was never pre-registered has no id. A
record is written once: `run` refuses an existing directory, a second run is a new id, and the index line of an
abandoned run says `abandoned` and stays.

**The lock on `test` is honoured here** ([S2.3.4](../p2.3_benchmark/s2.3.4_splits.md) states it; the frame's
default 17 has the two openings): `run` reads the `test` split only when the run names it and gives a reason,
which is `benchmark.opens_test` in the record and a mark on its index line; `report` lists every record that
opened `test`.

### Task T2.5.1.3 — `einaf evaluate` and `einaf report`: records only

`evaluate` reads a record and writes `metrics.json` ([S2.5.3](s2.5.3_metrics.md) owns the definitions). It calls
neither the model nor the kernel: what the kernel says of a program is in the record already, taken or derived.
`report` reads one or more records and writes tables and plots under `einaf/experiments/reports/<name>/`, each
with its footer. Its only inputs are records, so **a number that cannot be traced to a record is in no table**:
there is no way to hand it one. The main table, the ablations' tables and the curves of
[P2.7](../p2.7_failure_scaling_generalization/README.md) are all `report` calls named in their stage files.

### Task T2.5.1.4 — The kernel a record names

[Q-M2.1](../open_questions.md#q-m21--when-is-the-kernel-frozen) is ruled (the kernel is the one M1f left), so
the stage decides nothing of it and builds what the ruling leaves: the `repository` and `kernel` blocks, taken as
the table above says, and the two refusals of the acceptance. The kernel changes inside this milestone in one
place, the diagnostics' machine surface
([S2.1.2](../p2.1_kernel_as_instrumentation/s2.1.2_diagnostics_surface.md)), which changes no answer; a record
taken before it and one taken after it differ in their commit, and a table that would mix them says so in its
caption. An iteration of Ein between two levels
([Q-M2.15](../open_questions.md#q-m215--where-does-m2-stop-for-the-next-iteration-of-ein)) is the case the rule
is for: the arms run again on the new commit before any ablation is compared with them.

### Task T2.5.1.5 — Size and git

The stage measures before it fixes: the sizes of a feedback object, an envelope and an event stream as EinAf
writes them, on the seed set, per question. What the kernel's own surfaces weigh is known
([`audit_p2.5_p2.6.md`](../analysis/audit_p2.5_p2.6.md) § A.2, § B.1): a `--single` summary of a Zebra-size
program is kilobytes, a description of an ambiguous one is past a megabyte, and an event stream of one solve is
megabytes to tens of megabytes. So `kernel.jsonl` is small only where the question is; events are written only
for a level that reads them, compressed; and a call that records events is not a call whose wall is a number of
H4 (the stream multiplies the wall, by the same audit section).

The policy, the plan's own thresholds kept as defaults: a file over 1 MiB is compressed; a file over 10 MiB is
not committed, goes under `einaf/experiments/blobs/` (ignored by git) and is named in its record by SHA-256 and
size. Everything else is committed: the records are the evidence, and Stage Q's layer 4, *raw results, not just
charts*, is the repository with the blobs as a release asset. Whether `programs/` stays a file a program or is
packed is decided by the count the seed set gives.

### Task T2.5.1.6 — Tests

In EinAf's gate step, none needing the model: round trip (a fixture record evaluates to a known `metrics.json`,
twice, byte-identical); rejection (each required field removed in turn, and the evaluator names it); the report's
determinism (two copies of one record, one table); allocation (a second `run` into `exp-0001` is refused); the
two refusals of a dirty or mixed table.

### Task T2.5.1.7 — The machine

`machine.json`, taken by EinAf at the start of a run: what
[`utils/bench_env.sh`](../../../utils/bench_env.sh) prints of the CPU side (the processor, the cores the process
may run on, the governor, the power source, the load) and what that script has no line for: the GPU, its memory
free and taken, the driver, and the backend the binding loaded. A record taken on battery says so, and no wall
clock of such a record is put in a table. The host's two programs that want the same device memory
([`analysis/host.md`](../analysis/host.md)) are why the free memory is a field.

### Task T2.5.1.8 — What the record found of Ein

The stage is the first to ask the kernel to identify itself to a program that links it. What it finds goes to
[the evaluation of Ein](../ein_evaluation.md) under the user's five words, each with the command or the file
that shows it. Known at the re-plan, to be checked first: no surface states the commit; the library's manifest is
tested for presence, not for content; no surface carries a time or memory; a binding row's value reaches a
caller as text (`ein_infer::read_out::Row`).

## Notes

- The store holds the texts and a record holds their hashes, so editing a working copy in `einaf/prompts/` or
  generating a grammar again cannot change what a past record used.
- A line of `generations.jsonl` is the whole envelope with the response's text, thinking included: the raw output
  the research plan insists on releasing.
- `unknown_derived`, the old schema's last field, is gone: the kernel says for itself when a run stopped before
  it decided ([`analysis/` § 2](../analysis/README.md#2-what-the-kernel-says-today-where-the-plan-expects-the-walk)).
  So are `server_image_digest` (there is no server) and `max_enterings` (the walk's bound, retired).
