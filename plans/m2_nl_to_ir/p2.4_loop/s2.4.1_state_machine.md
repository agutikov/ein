# S2.4.1 — The filter's state machine and the transition log

**Phase:** [P2.4](README.md) (The loop — Stages E, F)
**Depends on:** [S2.1.1](../p2.1_kernel_as_instrumentation/s2.1.1_tree_and_outcomes.md), the outcome function;
[S2.1.2](../p2.1_kernel_as_instrumentation/s2.1.2_diagnostics_surface.md), after which a refusal and an abort are
values; [S2.1.3](../p2.1_kernel_as_instrumentation/s2.1.3_feedback_object.md), the feedback object, which is all
the machine reads of the kernel, and the bounded kernel call of `einaf::kernel`, which is the only way the
machine reaches it; [S2.2.5](../p2.2_formalizer/s2.2.5_from_text.md), GENERATE, the one-shot
formalizer called as a function; [S2.2.2](../p2.2_formalizer/s2.2.2_model_runtime.md), the model's runtime, for
the context an episode keeps.
**Research plan:** [`EinAf.md` § Stage E](../EinAf.md#stage-e--build-the-iterative-formalization-loop),
[E1](../EinAf.md#e1-define-the-state-machine), [E4](../EinAf.md#e4-termination-policy).
**Decides:** [Q-M2.4](../open_questions.md#q-m24--is-the-fixed-point-syntactic-or-semantic).

## Context

This is **the filter**: the arrangement in which the harness decides that Ein runs, on every generation, and the
model *"is forced to write ein code and can not avoid it"*
([Q-M2.13](../open_questions.md#q-m213--who-calls-the-kernel)). It is arms B2 to B5 of
[the frame](../README.md#the-arms): B2 is this machine with no repair, B3 to B5 the same at F0, F2 and F8. The
other arrangement, the tool, is [S2.4.6](s2.4.6_ein_as_a_tool.md) and shares everything below but the machine.

The loop is an instrument before it is a system. E1 says *every transition must be logged*, and the stage takes
that as the definition: **a run is its transcript**, a sequence of transition records a reader replays without
the model, every generation stored beside the record that consumed it. Nothing here is tuned; what is decided is
the vocabulary every later table is written in.

**What the machine reads.** One type, `einaf::kernel::Feedback` (S2.1.3), one object a question asked. EinAf
links the engine, so there is no exit code and no stderr to read: the old plan's *never from exit code 2* has no
object left ([`audit_p2.4.md`](../analysis/audit_p2.4.md) § A.1, item 4). An edge is taken on the object's
outcome and on the query's own axis, and on nothing else.

### The states and the edges

| state | what it does | next |
|---|---|---|
| GENERATE | S2.2.5's one shot: the text becomes a program `T₀`. Thinking is off and the whole output is held to Ein, by the harness, which accepts nothing else, and by the grammar of [S2.2.3](../p2.2_formalizer/s2.2.3_gbnf.md) unless the run's `grammar` parameter is off | CHECK |
| CHECK | parse and load `Tᵢ` | *invalid*: REPAIR; else ASK |
| ASK | the questions of § The questions asked of the kernel, each one feedback object | by outcome, below |
| REPAIR | [S2.4.2](s2.4.2_repair.md): the feedback rendered at the run's level ([S2.4.3](s2.4.3_feedback_ladder.md)), under the run's strategy, becomes `Tᵢ₊₁` | CHECK |
| ANSWER | the final program is asked the questions the record's readings need; the episode's answer and the final record are written | stop |

The research plan's ANALYZE and SOLVE are one state here: the kernel does not analyse and then solve, it answers
a question, and which question is the next section's.

An edge for each of [the seven outcomes](../README.md#the-outcomes), in the order S2.1.1's function reads them:

| outcome | edge | what ends a run that stays on it |
|---|---|---|
| **invalid** | REPAIR, with the diagnostics | the same diagnostics twice: *unrecoverable invalidity* |
| **flagged** | REPAIR, with the sites. Read before any word: a flagged program is answered, with a word under `--single`, and nothing is claimed of it ([Q-M1f.564](../../../docs/decisions/answer/Q-M1f.564-a-non-monotone-program-loads-with-a-warning.md)). **Never ANSWER as *one***, and never certified ([Q-M2.11](../open_questions.md#q-m211--what-is-a-flagged-program-to-the-loop)) | a budget; the final outcome is then *flagged* |
| **not decided** | ANSWER, as *not decided*: a solver budget is a termination condition and not a repair edge. Never read as one of the others | it ends the run |
| **inconsistent** | REPAIR | a fixed point: the text may contradict itself, and the faithful reply to the core is to change nothing |
| **incomplete** | REPAIR, with what is owed | a fixed point, or a budget |
| **several** | REPAIR | a fixed point: on an instance whose gold class is ambiguous this is the right end |
| **one** | ANSWER where the answer query has a class with a row; REPAIR where its class has no row (*the goal has no row*: the program has one state and answers nothing). Which query is the answer query is the contract's ([S2.2.1](../p2.2_formalizer/s2.2.1_contract.md)) | — |

*One* and *several* have two readings, over all of R and over its maximal line, and the machine takes its edge
under **the reading the run names** (`stop_on`: `all` by default, `maximal` the other value). A loop that stops
on one reading selects its final programs by it, so the reading is a parameter of the run and not a constant of
the machine: the experiment [Q-M2.10](../open_questions.md#q-m210--what-does-ein-certifies-a-unique-model-mean-on-r)
waits for runs under each. A third value, *the answer query's classes agree over a complete set*, would stop on
a program of several states and one answer (`examples/word_problems/boxes12.ein`); it needs a description an
iteration, and is offered only if T2.4.1.5's table shows the seed set can pay for one.

**The kernel passes a program** where its outcome is *one* under `stop_on` and its answer query has a class with
a row. **The filter's answer** is then what the program prints: each row of that class through the query's
`:goal-text`, with EinAf's formatters over the values that do not read as text
([Q-M2.12](../open_questions.md#q-m212--what-prints-the-answer)). Where an episode ends on a program the kernel
does not pass, its answer is a fixed short text that names the outcome, EinAf's own and never the model's, or no
answer; [S2.2.5](../p2.2_formalizer/s2.2.5_from_text.md) words the texts, and which outcome gets which, and what
is scored, is the answer rule of [S2.5.3](../p2.5_harness/s2.5.3_metrics.md). The machine writes the outcome,
the answer query's classes and the text into the final record and decides nothing of the scoring.

The fixed-point rows are the E3 point made structural: asked to repair, a faithful formalizer that finds nothing
in the text to add returns its program unchanged (S2.4.2 admits that reply), the machine sees the same program
twice, and the outcome standing is the episode's. It ends in *several* by fixed point and not in *one* by
invention.

### The questions asked of the kernel

The old stage asked one, `ein solve -e`, which is retired; today each question does the least work it needs, and
the choice decides both the cost and what is known ([the analysis](../analysis/README.md#5-what-the-standing-rules-now-ask-that-the-plan-does-not-answer),
item 4; [`audit_p2.4.md`](../analysis/audit_p2.4.md) § B.0 and § B.2).

| question | what it establishes | what it costs |
|---|---|---|
| root alone (`--no-search`) | root's standing: dead, owing (each instance through its rule's `:why`) or in R; H's size and what wrote it; the static check's finding and its sites | root's saturation |
| `--single`, all of R | one of four words, or none where a budget stopped it; under `Ambiguity` two states; each query's classes over the states listed | the least of the searching questions: `ein solve examples/zebra2.ein --single` is 7 saturations against 120 described |
| `--single`, the maximal line | the word over the maximal line, which reads past a program that owes nothing | more than all of R where the program is under-determined: 108 saturations against 39 on `examples/zebra2-minus-15.ein` |
| a description, or `--count` | `k_s`, `k_c` and whether R was exhausted; under a description a dead root's core and an owing R's frontier | on an under-determined program it runs to the facts budget after every state is found (the same variant: all 32 states, `exhausted` false) |

**The default plan, per iteration:**

1. **Root alone, first.** It decides *flagged* with no search: a flagged program is answered by the cube, which
   the machine has no use for, since it repairs on the sites. It decides *inconsistent* where root is dead, every
   node being dead with it. And it says what wrote H before anything is searched: a program that names no writer
   of hypotheses gets the blind enumerator ([`audit_p2.4.md`](../analysis/audit_p2.4.md) § D: 83 candidates on
   a ten-line probe).
2. **A dead root is described**, where the run's level shows a core: `--single` takes none
   ([Q-M1f.29](../../../docs/decisions/read-out/Q-M1f.29-a-question-that-prints-no-core-writes-a-dead.md)), and a
   dead root's description reads root alone (one saturation on `examples/ein-bugs/zebra2-bad.ein`).
3. **Otherwise `--single`**, over the part of R `stop_on` names.

**At ANSWER, once, of the final program:** `--single` over all of R, `--single` over the maximal line, and a
description, under a facts budget of its own. They are the three readings
[S2.5.3](../p2.5_harness/s2.5.3_metrics.md) computes both conditional probabilities under, and the description is
also where the answer query's classes are over the set the query names, which that stage's answer rule reads.
Each is one feedback object in the final record, and none is rendered into a prompt. `--count` takes R's two
counts by the same route and reads no state; it gives no classes, so it is not the default. A flagged final
program is asked `--single` alone, and what the kernel printed is recorded as a flagged program's.

Every question of one iteration runs on one load: the program is parsed and loaded once and each question asked
of a copy, as the engine's own corpus sweeps do. The kernel's work is recorded beside the token budget and is not
traded against it ([the frame's default 6](../README.md#the-defaults-the-re-plan-took)).

### The transition record

One record an edge, appended to the episode's transcript, which is a file of the experiment record
([S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md)):

| field | what |
|---|---|
| `run`, `i`, `state`, `outcome`, `next`, `reason` | the episode, the iteration, the edge taken and the predicate that chose it |
| `level`, `strategy`, `readings`, `history`, `stop_on`, `grammar` | the run's parameters, as this edge used them |
| `prompt` | the prompt's hash; the template and its parts are the record's |
| `generation` | the model's raw output, stored whole |
| `program` | the program's text, and its two identities (below) |
| `feedback` | one object a question asked, in the order asked |
| `tokens` | generated; prompt tokens evaluated anew; prompt tokens reused from the kept context |
| `wall` | the model's and the kernel's, measured by EinAf: no surface of Ein carries a time |
| `faithfulness` | [S2.4.4](s2.4.4_faithfulness.md)'s events for this program and this repair |

What names the kernel, the library and the model is the experiment record's and the feedback object's, and is
not repeated here.

### Two identities, and Q-M2.4

E4 detects a cycle *by canonicalized program hashes*; the user's own note asks for semantic stabilisation,
`Cl(Tᵢ₊₁, Pᵢ₊₁) = Cl(Tᵢ, Pᵢ)` ([F13](../../followups/f13_puzzles_beyond_zebra/ideas.md)). The old stage took
three digests from keys of the summary that do not exist
([`audit_p2.4.md`](../analysis/audit_p2.4.md) § A.2, items 12, 13 and 17). What there is today:

- **The syntactic identity** is the SHA-256 of `ein_ir::dump_canonical` over the program's parsed forms, which
  the feedback object carries (S2.1.3). It is a function of the library that no command prints. It normalises
  layout and comments, and neither the order of the forms nor a name. Of a generation that does not parse it is
  the generation's own bytes.
- **The semantic identity has to be chosen**, and this stage chooses it. Three candidates, from fine to coarse:

  | candidate | what is compared | what it calls different that a reader would not |
  |---|---|---|
  | root's fixpoint | every fact root holds, as sorted text | nearly everything: the fixpoint holds the declarations, every activator as a fact of its rule's name, root's `open` facts and facts under module full names ([`audit_p2.4.md`](../analysis/audit_p2.4.md) § B.2), so a renamed rule or a redundant activator is a new state |
  | **the answer** | what the run's question established: the outcome, the states listed as their facts over the candidates' relations, each query's classes | a renamed relation |
  | the printed answer | each query's classes alone | nothing a reader of the answer sees; it calls equal two programs whose states differ outside the goal |

  The second is the default. It is the part the question asked establishes of the answer as
  [`03-transformations.md` § 1](../../../docs/ein/reasoning/03-rule-evolution/03-transformations.md#1-a-transformation-and-what-it-preserves)
  defines it (R, each state, the two counts, what root holds and owes, each query's classes), which that page
  shows unchanged under an import written another way and, on a monotone program order-free at the boundary,
  under another written order.
- **Identity is the list, never its digest**
  ([`06-solution-semantics.md` § 1.5](../../../docs/ein/reasoning/02-kb-evolution/06-solution-semantics.md#15-commitment-node-state):
  *a digest of a state may label it for a reader and never decides that two states are one*). The machine keeps
  the sorted lists and compares them; the digest in the record is a label. The engine's own state key is a list
  of ids of one arena, so two programs are compared by their facts' text.
- **Not the container's digest**: `.einb` is a private cache format and never an interchange one, which the
  ledger's entry still offers and the old stage already refused.

**The default answer to Q-M2.4**, the ledger's recommendation re-aimed: the syntactic identity is the first check
and catches the literal resubmission; the semantic identity is what the run stops on; both are logged on every
transition. A transition whose syntactic identity moved and whose semantic one did not is a **cosmetic repair**,
a count H3 reports, because it measures how much of what the model calls repair the kernel calls nothing.
T2.4.1.7 decides it on fixtures, and `stop_identity` stays a parameter of the run.

### Termination, as predicates over the transcript

E4's seven, each decidable from the records and the run's configuration:

| condition | predicate |
|---|---|
| verified success | the kernel passes the program: the outcome is *one* under `stop_on`, and the answer query has a class with a row |
| unrecoverable invalidity | *invalid* with the same diagnostics, by kind and place, twice in a row; or `n_reject` generations in a row that hold no program (empty, or cut at the token limit) |
| iteration budget | `i ≥ max_iterations`: a parameter, which G7 sweeps. Its default, 3, is the old plan's number and no finding |
| token budget | the episode's generated tokens reach the arm's budget ([S2.5.2](../p2.5_harness/s2.5.2_baselines.md) sets it) |
| solver resource budget | the outcome is *not decided*: the facts budget, the limit of a flagged program's cube, the clock, or a call that did not return (below) |
| repeated identical theory | the syntactic identity of `Tᵢ` is an earlier one's of the episode; the immediately earlier one is the *unchanged* reply |
| repair cycle | the semantic identity of `Tᵢ` is an earlier one's |

### A kernel call that does not return

**Nothing in `ein solve` stops a saturation that has no fixpoint.** The facts budget counts facts beyond root,
between a route's steps; the clock is *checked before each step of work* (`ein solve --help`); and a saturation,
root's or a node's, is one step. The reasoning's own page says so:
[*termination is assumed, not given*](../../../docs/ein/reasoning/02-kb-evolution/02-saturation.md), since a rule
may build a fact out of a fact. A program of one such rule, `(num z)` and `(num ?x)` concluding `(num (s ?x))`,
taken at this re-plan, one run each: `ein solve FILE --no-search -T 1` was still running at 3.5 s with about
2.4 GB resident, and `--single -T 2 --region-budget 1000` ran until it was killed at 20 s. What does stop it is a
cap on firings: `ein saturate FILE --max-steps 1000` stopped after 1 000 firings and said so, and the library's
saturator takes the same cap (`Saturator::saturate`'s `max_steps`), which no route passes on. A model that writes
a successor, a count or a path by recursion over nested terms writes this program.

So every kernel call of EinAf is bounded, and **the bounded call is `einaf::kernel`'s**, built in P2.1 beside
the feedback object ([S2.1.3](../p2.1_kernel_as_instrumentation/s2.1.3_feedback_object.md)): the machine here
and the tool ([S2.4.6](s2.4.6_ein_as_a_tool.md)) reach the kernel through it and by no other way. What the two
need of it:

- **it returns, whatever the program**: within a wall-clock bound and a memory bound that are parameters of the
  run and fields of the record ([S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md));
- **a call a bound stopped is a feedback object**, written by EinAf: the outcome *not decided*, with a
  diagnostic of EinAf's own that says which bound, told apart from the kernel's own three ways of not deciding
  (the facts budget, the limit, the clock). It is never read as another outcome;
- **one call an iteration**: the program loaded once and the iteration's questions asked of it, each answer one
  object.

What this re-plan proposes for it, P2.1's to take or change: the kernel runs in **a worker process of EinAf's
own**, the `einaf` binary in a worker's mode, which links the crates, and which its parent kills at either
bound; what crosses the process boundary is EinAf's own type in S2.1.3's serialisation, so nothing the kernel
printed is read. A cap on root's firings, through the library's saturator before any question is asked, is a
first guard that depends on no machine; a node's saturation inside a route takes no cap, so the process's
bounds stay. A clock that reaches inside a saturation would be a change to Ein that no ruling asks for, and is
an entry of [the evaluation](../ein_evaluation.md).

## Tasks

- **T2.4.1.1 — The machine.** `einaf::filter` (a default name: `loop` is a Rust keyword): the states; the edge
  function, pure, from a state, the iteration's feedback objects and the configuration to the next state and the
  predicate that chose it; the runner that calls GENERATE and REPAIR and the bounded kernel call. The level, the
  strategy and `readings` are configuration handed to the renderer and the prompt, and the edge function reads
  none of them.
- **T2.4.1.2 — The transition record and the two identities.** The record's type and its append; the syntactic
  identity from the feedback object; the semantic identity as a sorted list with its digest, by T2.4.1.7's
  definition. A page of `docs/einaf/` states the record field by field.
- **T2.4.1.3 — Termination.** The seven predicates as one function over the transcript and the configuration;
  the reason written into the final record; the cosmetic-repair count; every bound a run was under (the facts
  budget, the limit, the clock, the bounded call's two) echoed into the record, so that a transcript says what
  stopped it and what could have.
- **T2.4.1.4 — Replay and the fixtures.** A replayer that returns stored generations by episode and iteration,
  and a second one that returns canned programs: a sequence for each of the seven outcomes and each of the seven
  termination conditions. The corpus has a program for six outcomes as they stand
  (`examples/broken/unclosed_paren.ein`, `examples/ein-bugs/zebra2-bad.ein`, `tests/region/04_owing.ein`,
  `examples/zebra2-minus-15.ein`, `examples/zebra2.ein`, `examples/lattice/04_obligation_trigger_hole.ein`) and
  *not decided* is `zebra2` under a facts budget of 1. The sequences EinAf writes itself: two texts with one
  answer (an import written another way), a two-program oscillation, a program whose saturation does not end, a
  program with one state whose query has no row. All run in EinAf's step of the gate, with no model.
- **T2.4.1.5 — The questions, chosen by measurement.** Over the seed set's canonical programs and three variants
  of each (a clue dropped, a contradiction added, the theory's activators removed, so that the blind enumerator
  answers): what each question of the table costs in saturations, facts and wall clock, and what it establishes.
  The default plan is confirmed or changed on that table, and the table goes into the stage's record. **Check
  first** that a dead root's description reads root alone on a flagged program too, and what the final
  description costs under a small facts budget on a program whose H the blind enumerator wrote.
- **T2.4.1.6 — The machine on the bounded call.** The bounded call is P2.1's; this task is the loop's side of
  it. **Check first** that what P2.1 built gives the three things above, and add inside `einaf::kernel` what it
  does not (one load for an iteration's questions is the likeliest). The fixture is the one-rule program above:
  the machine ends *not decided* within the bound, names the bound in its final record, and EinAf's step of the
  gate does not hang. A second fixture stops at the cap on root's firings, if P2.1 took that guard.
- **T2.4.1.7 — Q-M2.4, decided.** On fixture pairs that should and should not be one program to the loop (an
  import written three ways; the facts in another order; a rule renamed; a relation renamed; an activator the
  others imply; one clue changed), which of the three candidates calls each pair equal, and what each costs to
  take. The decision is written beside the question in [the ledger](../open_questions.md), with the table, and
  the ledger's sentence that offers `.einb` goes.
- **T2.4.1.8 — The evaluation.** Into [the evaluation of Ein](../ein_evaluation.md): what each question cost on
  generated programs against hand-written ones; an outcome the machine could not take an edge on without a
  second question; the saturation nothing in `ein solve` stops, with the probe, and what the application had
  to build because of it; what of an answer's identity the library handed over and what EinAf rebuilt from
  facts' text.

## Acceptance

- The states and the edges are a function of the feedback objects and the configuration: no edge reads text the
  kernel printed.
- Every edge writes one record with every field of the table; a run's transcript replays from its stored
  generations, with the model replaced by the replayer, to the same transitions and the same identities.
- Each of the seven outcomes takes its edge on its fixture, and each of the seven termination conditions is
  reached by a fixture run whose final record names it. The flagged fixture is never an ANSWER as *one*, at any
  level and under either value of `stop_on`.
- The program whose saturation does not end is *not decided* within the bounded call's bound, and the final
  record names the bound.
- The final record of an episode holds the three readings' objects, or says of each why it was not asked, and
  the episode's answer: what the program printed where the kernel passed it, a fixed text or none where it did
  not.
- The two identities agree with their definitions on T2.4.1.7's pairs, and are stable across job counts.
- T2.4.1.5's table exists, and the plan the machine runs is the one it supports.

## Risks

- **A process a call is a cost, and a second way for the kernel's answer to reach EinAf.** If P2.1 takes the
  worker, the object that crosses is the one S2.1.3 already serialises for the record, and its round trip is
  that stage's test; if the cost shows in a sweep, a worker is kept alive across the questions of one episode
  and still killed on a bound. A bound that is a clock or a memory size is the host's, so what it stops is
  recorded as stopped by it and is no finding about the program.
- **`--single` over all of R tells a program that owes nothing *several*.** A formalizer that writes every clue
  and no theory of what must be filled has ∅ and its partial commitments in R
  (`examples/features/11_expect_ambiguity.ein`: two full seatings, `k_s` 7), and is sent to REPAIR on a
  difference between ∅ and one guess. That is the reading the user has not ruled on; the run's `stop_on` and the
  three final readings are what keep it measurable, and what it does to the loop is an entry of the evaluation.
- **The semantic identity misses a rename.** A repair that renames a relation has the same answer up to the
  renaming and a different list. The stage does not search for the renaming; such a repair is counted as a
  change, and T2.4.1.7 records how often the fixtures and the seed runs meet one.
- **A flagged program found in flight.** A program the static check passes can be found not monotone while it is
  searched, at a state that holds a hypothesis root does not
  ([Q-M1f.574](../../../docs/decisions/answer/Q-M1f.574-a-hypothesis-first-held-above-root-makes-its.md)): root
  alone does not see it. S2.1.1's function reads it off the answer, and the edge is *flagged*'s.
- **An episode that ends at a fixed point on *inconsistent* may be a formalizer that gave up.** The machine
  cannot tell a contradictory text from a contradictory formalization; the canonical judge can
  ([S2.4.4](s2.4.4_faithfulness.md)), and the record carries both.
