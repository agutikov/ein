## Context

The loop is an instrument before it is a system: the plan's E1 says *every
transition must be logged*, and this stage takes that as the definition —
**a run is its transcript**, a sequence of transition records that a reader
can replay without the model, because every generation the model produced is
stored beside the record that consumed it. Nothing in the stage is tuned;
what is decided here is the vocabulary every later table is written in.

### The states, on this kernel

The plan's ANALYZE and SOLVE are one process on Ein — `ein solve -e` saturates,
searches and certifies in one run — so CHECK is the parse / load / compile
half of the feedback object and SOLVE is the rest:

| state | input | outcome (from `ein-feedback/1`) | next |
|---|---|---|---|
| GENERATE | text, prior feedback if any | a program `Tᵢ` | CHECK |
| CHECK | `Tᵢ` | `verdict.outcome = invalid` — a `diagnostics[]` entry of kind `syntax_error` / `undefined_symbol` / `type_error` / `arity_mismatch` / `other` | REPAIR |
| | | loads and compiles | SOLVE |
| SOLVE | `Tᵢ`, `ein solve -e --feedback` | `unique ∧ search_complete`, `query.status = answered` | ANSWER |
| | | `inconsistent` (with `unsat_core`) · `multiple_models` (`k > 1`) · `unknown` with `search_limit` (the `-m` cap — the theory may be too loose) · `unique` but `query.status = absent` (the goal names nothing the model contains) | REPAIR |
| | | `unknown` with `resource_limit` (`Aborted`: `--max-time` / `--max-enterings`) | ANSWER, as *unknown* — a solver budget is a termination condition, not a repair edge |
| REPAIR | text, `Tᵢ`, the feedback rendered at the run's level, the strategy | `Tᵢ₊₁` | CHECK |
| ANSWER | the last feedback object | the answer *is the verdict*: bindings for `unique`; the binding set for `multiple_models`; the core for `inconsistent`; nothing for `unknown` | stop |

The last row is the E3 point made structural: on a benchmark instance whose
gold verdict is *ambiguous*, the correct transcript ends in ANSWER with
`multiple_models` **by fixed point** — the formalizer, asked to repair, finds
nothing in the text that constrains the difference and returns the theory
unchanged ([S2.4.2](s2.4.2_repair.md) admits that reply) — not in `unique`
by invention. `unknown` is derived, not read
([P2.1 § The sixth outcome](../p2.1_kernel_as_instrumentation/README.md#the-sixth-outcome-today)),
and the two kinds the derivation distinguishes take different edges:
`search_limit` is a reason to tighten the theory, `resource_limit` is a
reason to stop.

### The transition record

One JSON object per edge, appended to `transitions.jsonl` in the experiment
directory ([S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md)):

```json
{"run": "exp-0042/inst-0137", "i": 2, "state": "REPAIR", "outcome": "program", "next": "CHECK",
 "level": "F5", "strategy": "repair",
 "prompt_sha": "…", "generation": "generations/0137-2.txt", "program": "theories/0137-2.ein",
 "program_sha": "…",      "state_digest": "…",      "models_digest": "…",
 "feedback": "solver/0137-1.json",
 "tokens_in": 1843, "tokens_out": 412, "wall_ms": 9120, "ein_wall_ms": 31,
 "ein_commit": "…", "stdlib_sha": "…", "faithfulness": []}
```

Three digests, and where each comes from — none of them a new kernel
computation:

- **`program_sha`** — the syntactic identity: SHA-256 of the canonical dump
  (`ein_ir::dump_canonical`), carried in the feedback object's `source` by
  the producer, which runs in Rust and has the AST.
- **`state_digest`** — the semantic identity: SHA-256 over the summary's
  `root.facts`, which `ein-summary/1` already emits as *the KB's facts as
  sorted s-expressions* — exactly what [`defined_behaviour.md`](../../../docs/kernel/defined_behaviour.md)
  § 2.4 pins as canonical state identity, *the sorted fact list itself, never
  a hash*. The loop hashes that list because it stores the list too. The
  alternative, `ein kb save --saturate` and the `.einb`'s BLAKE3 digest, is
  rejected for this purpose: the container's bytes depend on the id remap,
  which [Q-M1a.22](../../../docs/history/m1a_rust/open_questions.md) promises
  only *answer*-identity for, so two equal states could carry two digests.
- **`models_digest`** — SHA-256 over `verdict.solutions[].facts`, sorted by
  model already; equal digests mean the same model set.

### Termination, as predicates over the transcript

The plan's seven conditions (E4), each decidable from the records above
and the config's budgets — never from the process exit code, which is 2 for
a budget abort *and* for a usage error:

| condition | predicate |
|---|---|
| verified success | `outcome = unique ∧ search_complete ∧ query.status = answered` |
| unrecoverable invalidity | `invalid` with the same `(kind, location)` twice in a row, or the model returned an empty / grammar-rejected generation `n_reject` times (config, default 2) |
| iteration budget | `i ≥ max_iterations` (config; default **3** — the old S2.4.2's "≤ 3 attempts", now a parameter G7 sweeps) |
| token budget | `Σ tokens_in + tokens_out ≥ max_tokens` (config; the matched-budget rule of [S2.5.2](../p2.5_harness/s2.5.2_baselines.md) sets it per condition) |
| solver resource budget | `outcome = unknown ∧ diagnostics ∋ resource_limit` — `--max-time` / `--max-enterings` are config too, and the feedback object says which fired |
| repeated identical theory | `program_sha(i) ∈ {program_sha(j) : j < i}` |
| repair cycle | `state_digest(i) ∈ {state_digest(j) : j < i}` |

**This stage decides [Q-M2.4](../open_questions.md#q-m24--is-the-fixed-point-syntactic-or-semantic)
as its recommendation says:** the syntactic hash is the cheap first check,
the semantic digest is the stop criterion, both are logged, and a transition
whose `program_sha` changed while its `state_digest` did not is counted as
a **cosmetic repair** — a number H3 reports, because it measures how much of
what the model calls repair the kernel calls nothing. The same-state case
covers both the plan's *repeated theory* and the user's
`Cl(Tᵢ₊₁, Pᵢ₊₁) = Cl(Tᵢ, Pᵢ)` ([F13](../../followups/f13_puzzles_beyond_zebra/ideas.md)):
a repair that leaves the closure where it was has reached the fixed point,
and the verdict standing at that point is the answer.

## Acceptance

- The states and edges above implemented in `einaf/loop/machine.py` as a
  function of the feedback object and the config; no edge reads stdout,
  stderr or an exit code.
- Every edge writes one transition record with every field above; a run's
  transcript replays (same transitions, same digests) from the stored
  generations with the model replaced by a replayer.
- Each of the seven termination conditions is reached by at least one
  fixture run under a mocked LLM that returns canned programs, and the
  transcript names the condition.
- The three digests agree with their definitions on the seed set:
  `program_sha` equals the producer's; `state_digest` over two textually
  different programs with the same closure is equal; `models_digest` on
  `examples/zebra2-minus-15.ein` is stable across `--jobs 1` and `--jobs 8`.

## Tasks

### Task T2.4.1.1 — The machine

`einaf/loop/machine.py`: the state enum, the edge function
`next(state, feedback, config) → (outcome, next_state, reason)`, and the
runner that calls GENERATE / REPAIR (from [S2.2.5](../p2.2_formalizer/s2.2.5_from_text.md)
and [S2.4.2](s2.4.2_repair.md)) and SOLVE (`ein solve -e --feedback`, with
the budgets from config). The level and the strategy are config, passed
through to the renderer ([S2.4.3](s2.4.3_feedback_ladder.md)) and the
prompt, never consulted by the machine itself.

### Task T2.4.1.2 — The transition record and the three digests

`einaf/loop/transcript.py`: the schema, the append, the digests.
`program_sha` read from the feedback object; `state_digest` and
`models_digest` computed from the summary the producer consumed — which
the feedback object must carry or reference: **this stage asks S2.1.2 for
one field**, `digests {program, state, models}`, so the harness does not
reopen the summary; until it exists, the harness reads `summary.json`
beside the feedback file.

### Task T2.4.1.3 — Termination

`einaf/loop/stop.py`: the seven predicates as one function over the
transcript and the config; the reason written into the final record; the
cosmetic-repair counter. The solver budgets (`--max-time`,
`--max-enterings`, `--max-set-size`) are config and are echoed into the
record's `ein_args`, so a transcript says what cap it ran under.

### Task T2.4.1.4 — Replay and the fixtures

`einaf/loop/replay.py`: a model stub that returns stored generations by
`(run, i)`; a second stub that returns canned programs from
`einaf/tests/fixtures/loop/` — one program sequence per termination
condition, including a pair of textually different programs with one
closure (for the cosmetic-repair case) and a two-program oscillation (for
the cycle). `einaf/tests/test_machine.py` runs all seven.

## Notes

- The iteration budget's default of 3 is the old plan's number and is a
  parameter, not a finding; [P2.6](../p2.6_ablations/README.md) G7 is where
  it becomes a curve.
- `unknown` from `search_limit` taking the REPAIR edge is a judgement: a
  theory whose lattice is too large to exhaust at `-m 5` is usually missing
  a constraint the text states. When it is not — the instance is genuinely
  under-determined and large — the loop spends its iterations and ends as
  *unknown*, which is the honest answer and a failure-taxonomy row
  ([P2.7](../p2.7_failure_scaling_generalization/README.md), *solver
  limitation*), not a wrong one. The day [M1d](../../../docs/history/m1d_satisfiability/README.md)
  gives the engine a word for this state, the predicate reads it instead
  ([Q-M2.1](../open_questions.md#q-m21--when-is-the-kernel-frozen)).
