## Context

The level of feedback is **the experimental variable** of the milestone, so the ladder is built as an
instrument: a level is a pure function from an iteration's feedback objects and its program to text, with no
state and no access to the model. A level is then a parameter of a run, an ablation is two runs, and a rendering
can be recomputed from a record without running Ein again.

**One renderer, two readers.** The filter puts the text into the next prompt ([S2.4.2](s2.4.2_repair.md)); the
tool returns it as its function's result ([S2.4.6](s2.4.6_ein_as_a_tool.md)). At one level both get the same
text of the same object.

**This is where the kernel's diagnostics are judged as feedback**, the milestone's second main idea
([the frame](../README.md#the-two-main-ideas-the-user-2026-11-25)): for each thing a model gets wrong, what the
kernel says of it, in what form, and what EinAf had to compute because the kernel does not. The old stage took
most rungs for *projections of what the engine already emits*; level by level that is partly true and partly not
([the analysis](../analysis/README.md#p24--the-loop-audit); [`audit_p2.4.md`](../analysis/audit_p2.4.md) § B.1
has each cell with its evidence).

### Blocks and levels

A **block** is one kind of content; a **level** is a set of blocks. The research plan does not say whether F4
contains F3, and its ablations need pairs that differ in one thing (G3 the verdict with and without the core, G4
with and without provenance, G5 a count against a difference), so the unit that is built is the block.

| block | what it shows | of the feedback object |
|---|---|---|
| `diagnostics` | each diagnostic with its kind, its place and its message; a load's notes; a flagged program's sites; the findings of the contract's check that a level shows, marked as EinAf's | `diagnostics`, `flagged` |
| `verdict` | the outcome and the part of R it is of; where root stands (in R, owing, dead); the query's own axis | `outcome`, `asked`, `queries`, `owed` |
| `counts` | the states listed and whether they are all; how many candidates H has and what wrote them; how many instances root owes; a query's classes | `states`, `queries`, `owed`, `work` |
| `difference` | under *several*: how two states differ | `states`, `queries` |
| `core` | under *inconsistent*: the core, its sources and the rules that refuted; under *incomplete*: what is owed | `core`, `owed` |
| `dependency` | what the goal's relations depend on, and what has no path to them | `dependencies`, added by this stage |
| `provenance` | the chain of each fact the two blocks above named | `provenance`, added by this stage |

| level | blocks |
|---|---|
| **F0** | none: one fixed sentence, the same for every outcome |
| **F1** | `diagnostics` |
| **F2** | F1 and `verdict` |
| **F3** | F2 and `counts` |
| **F4** | F3 and `difference` |
| **F5** | F3 and `core` |
| **F6** | F3 and `dependency` |
| **F7** | F4 and F5, and `provenance` |
| **F8** | every block, under a size cap |

Any set of blocks is a value of the run's parameter; the nine names are the default sets.

**Three things the kernel says have no rung in the research plan**
([`audit_p2.4.md`](../analysis/audit_p2.4.md) § B.1, F8's row), and each is given one: **what is owed** stands
in `core`, as the reason an empty R is empty of the owing kind, beside the reason it is empty of the dead kind;
**a flagged program's sites** are static findings about the program's rules and stand in `diagnostics`
([Q-M2.11](../open_questions/answer/Q-M2.11-what-is-a-flagged-program-to-the-loop.md): *fed back as a diagnostic at the
feedback levels that carry one*), the word *flagged* in `verdict`; **who wrote H** (a rule that concludes
`(open F)`, a written `open` fact, an obligation activated at root, or the blind enumerator) stands in `counts`.

### Level by level

**F0, *try again*.** One sentence. It does not say whether the program loaded.

**F1, syntactic.** The research plan's list is *undefined relation, type mismatch, arity mismatch*.

- *The kernel supplies*: a parse error, every error recovery reached with its line, column, notes and ranked
  repairs (a value of the library today); a load refusal, one of
  [`07-diagnostics.md`](../../../docs/ein/user/04-reference/07-diagnostics.md) § 2's, a string today and after
  S2.1.2 a value with a kind, a place where the loader has one, and the normative message; a load's notes; the
  static check's sites, each with its rule, what it reads and what is at stake.
- *The kernel does not supply the plan's three, by decision*: a fact over an undeclared relation loads; Ein has
  no types ([Q-M1f.372](../../../docs/decisions/language/Q-M1f.372-ein-has-no-types-a-declarations-slot-names-are.md));
  a declared relation at another count is another relation
  ([Q-M1f.447](../../../docs/decisions/language/Q-M1f.447-a-relation-is-overloaded-by-its-count-of.md)). And it
  is silent on what a formalizer most often gets wrong in selecting a theory: an activator under a name the file
  does not list is the file's own fact and inert; an activator at another count than its rule's parameters
  activates nothing; a negation beside its fact is alive unless the program imports `std.contradiction`
  ([the evaluation](../evaluation/README.md), E-11, E-12, E-18).
- *EinAf has the residue already, and this stage decides who sees it.* The formalization contract is stricter
  than Ein, and its check is EinAf's ([S2.2.4](../p2.2_formalizer/s2.2.4_passes.md), T2.2.4.6): it reports, and
  refuses nothing, a selection that is not active, a fact of a relation nobody declares, a form at a count its
  relation is not declared at, a number written as a name, a `:goal-text` reference nothing binds. That stage
  leaves to this one whether a level shows them. **The default: `diagnostics` shows them, marked as EinAf's in
  the object and in the text, under a parameter of the run** (`check_shown`), so that F1 with it off is what Ein
  says for itself and the pair is a measurement of the evaluation. Two of the check's findings are not shown
  there: *a `:source` that is no sentence of the input* is the faithfulness judge's finding and is never fed
  back ([S2.4.4](s2.4.4_faithfulness.md)); *the writer of H* is the kernel's own report and stands in `counts`.
- *Where the parse errors are.* With its grammar on, the filter writes no program that fails to parse
  ([S2.2.3](../p2.2_formalizer/s2.2.3_gbnf.md)), so its F1 is the loader's refusals, the sites and the check. A
  parse error is the tool's daily reply, and the filter's with its grammar off.

**F2, the verdict.** *The kernel supplies* the outcome, of a named part of R (S2.1.1), root's standing, and the
query's axis: whether the goal has a row, and whether the classes agree. One word of the old plan's four
(`unique`, `inconsistent`, `multiple_models`, `unknown`) is now seven, and a sentence each, in a file of
`einaf/prompts/`.

**F3, cardinality.** The plan's example is *4 valid models remain, the query has 3 possible bindings*. Under
`--single`, the default question, the kernel does not count: it says *two states or more*. `k_s` and `k_c` exist
under a description or `--count`, and which of them *models* means depends on the program (the states of R or
its maximal line: [`audit_p2.4.md`](../analysis/audit_p2.4.md) § B.0, item 1). The block says what the
iteration's questions established, names the part of R, and says *or more* of a lower bound. A count that needs
a wider question is asked only where the run's `count_question` says so (none by default; `-n N` and `--count`
are its other values).

**F4, the difference of two states.** *The kernel supplies* two states under `Ambiguity`, each as its facts over
the candidates' relations, and each query's classes with the states that give them. **Nothing computes a
difference of two states**: `ein test --diff` compares a claim with what was found. *EinAf computes*:

- **the pair**: by default the two states `--single` lists, at no further cost. The old rule (*the pair whose
  difference, restricted to what the goal reaches, is smallest*) needs more states than `--single` lists; it is
  the parameter's other value, over an `-n N` listing, and is taken only if T2.4.3.2's measurement says the pair
  matters;
- **the difference**: the facts of one list and not the other, and, per query, the rows each state gives;
- **the case that is no difference between two answers**: where root is in R the two states are ∅ and one guess,
  and the block says what the `∅` row says, that the program as written owes nothing, in place of a difference of
  one hypothesis;
- **the wording**. A fact reads as Ein lets it read
  ([`14-natural-language.md` § 3](../../../docs/ein/user/03-syntax-and-semantics/14-natural-language.md#3-a-fact-in-english-the-fallback-ladder)):
  a stated fact by its `:source`; a derived fact by its rule's `:why`, filled with its first recorded
  justification's bindings; a candidate by the `:why` of the hypothesis rule that proposed it, where one did;
  otherwise as written. A value that does not read as text goes through
  [S2.2.5](../p2.2_formalizer/s2.2.5_from_text.md)'s formatters. No sentence is invented for a relation, and
  nothing waits for [M1p](../../m1p_ein_to_natural_language/README.md)
  ([Q-M2.12](../open_questions/answer/Q-M2.12-what-prints-the-answer.md)). The old stage rendered a fact through its
  relation's declaration and tested the wording against the engine's table: a fact takes no text from the
  declaration ([Q-M1f.58](../../../docs/decisions/read-out/Q-M1f.58-a-fact-reads-in-english-in-the-trace.md))
  and the engine prints a state as s-expressions, so both are gone.

The block shows the difference and never the two states whole: two states leak less than thirty-two, and a
difference less than two.

**F5, the core, and what is owed.** *The kernel supplies*, for a dead root and **under a description only**: the
core's facts, the `:source` of each that carries one (beside the core, in its order, after S2.1.2), the rules
that refuted, and the status of the core's search. *EinAf computes* the wording, which keeps what the pages say
a core is ([`audit_p2.4.md`](../analysis/audit_p2.4.md) § C.1, § C.6):

- *these statements together lead to a contradiction*, and never *the only*, *the smallest* or *all*: a core is
  not subset-minimal, is taken over the derivations recorded, and its search has a budget; where the status says
  the search was cut, the block says a smaller set may exist;
- **a core is an explanation**: two iterations may get two cores for one defect, since it may move with the
  order the rules are written in ([Q-M1f.6](../../../docs/decisions/answer/Q-M1f.6-a-core-is-an-explanation.md);
  [F22](../../followups/f22_exact_core_past_the_cap.md) is the canonical core, not started);
- **an empty core is a core**: `[]` says the refutation rests on no fact (a rule that matches nothing and
  concludes `(false)`), and is rendered as that, with the rule. The old stage read it as a truncated search,
  which no longer exists;
- a fact written with a `:rule` or a `:using` has no premises and leaves every core
  ([F24](../../followups/f24_written_provenance.md)); whether a formalizer may write either is the contract's.

For an owing root the same block lists what is owed, each instance in the sentence its obligation rule's `:why`
gives it. The frontier of an empty R of the owing kind is a description's too, and is asked only where the run's
level shows it.

**F6, dependency.** The plan's example: *the query depends on nationality, on house, and has no path to pet*.
*The kernel supplies* partial counterparts, each its own thing: what a state owes; the relations H leaves out,
with why no writer proposes them; the saturation rules' dependency graph, an edge from each relation a compiled
plan reads to each it writes (`ein_infer::strata`), which is a function of the library, on no command's output,
and outside the library's contract ([`04-api.md` § 6](../../../docs/ein/ein.rs/04-api.md#6-what-is-not-the-contract)).
Reachability from a goal does not exist. *EinAf computes*, inside `einaf::kernel`, where the engine's crates are
read:

- **the graph**, over the compiled plans of a saturated root: the engine's edges, and the same for the
  obligation rules (what a trigger reads to the relation owed) and the hypothesis rules (what they read to what
  they propose), which the engine's function leaves out. A rule with a relation for a parameter has edges only
  as an activator instantiates it, which is why the graph is of plans and not of the source;
- **reachability** backwards from the relations the goal names;
- **three findings**, each EinAf's own and marked so: a relation the goal names that nothing states, derives or
  proposes; a stated fact of a relation the goal does not reach and no plan reads; a declared relation that is
  neither stated, derived nor proposed. Each carries its caveat in its wording (*no rule read it*, not *it is
  irrelevant*): an activator is a fact too, and a firing's absences are reads.

Stratification, well-foundedness and the structure of H (`ein render h-space`) are not part of it.

**F7, provenance.** *The kernel supplies*, as values of the library: each fact's recorded justifications; root's
firings; and the derivation of a listed state from its first minimal commitment, which the trace writes with each
step's rule, the rule's `:why` filled and each premise's `:source`. The event stream carries the same firings to
a caller of the binary and multiplies the wall clock ([the evaluation](../evaluation/README.md), E-19); EinAf reads
the values. *EinAf computes* the chain of each fact the `difference` or the `core` block named, to a depth that
is a parameter. Its limits are the kernel's ([`audit_p2.4.md`](../analysis/audit_p2.4.md) § B.1, F7's row): a
firing's premises omit the absences it read and its activator; an obligation rule and a hypothesis rule never
fire; a fact's first recorded justification is an explanation; and **the chain rebuilt from first firings is not
the derivation a core rests on**, so for a core the block shows the rules that refuted, as the kernel gives
them, and rebuilds nothing.

**F8, the combined diagnostic.** Every block, in the order verdict, diagnostics, counts, core or difference,
dependency, provenance, under a cap in tokens that is a parameter (G6 varies it); what is cut first is the
provenance, then the dependency. *The system should not assume F8 is best*, and nothing here does.

### The defect catalogue

The ladder is tested, and the kernel judged, on **defects planted in programs that are right**: a canonical
program of the seed set, and the same with one defect of a known kind. For each defect the catalogue holds the
feedback objects of the iteration's questions and every level's rendering. The first list, to be grown from what
P2.2's one-shot runs show a model gets wrong:

| the defect | what the kernel says of it today, to be confirmed on each fixture |
|---|---|
| an unclosed form; a keyword a form does not take; a rule with no `:why` | *invalid* |
| a clue dropped | *several* |
| a contradictory clue added | *inconsistent* |
| two names swapped in one fact | to be taken: *inconsistent*, or *one* with another answer |
| a relation misspelt in one fact; an argument dropped | nothing from the kernel: a finding of the contract's check |
| an activator written under a name the file does not list; an activator's hierarchy facts left out | nothing from the kernel: a finding of the contract's check, or *several* |
| the theory's activators left out altogether | *several*, with H the blind enumerator's |
| `std.contradiction` not imported where a negation should kill | *one* or *several*, where *inconsistent* was meant |
| a closed-world reading written with `absent` over a relation a commitment can fill | *flagged* |
| a rule that builds a fact out of the fact it matched | nothing: the saturation has no fixpoint and `ein solve` does not stop it. *Not decided*, by the bounded call ([S2.4.1](s2.4.1_state_machine.md)) |
| the query left out; a query whose goal has no row | *one*, and no answer |

## Tasks

- **T2.4.3.1 — The blocks of F0 to F3.** The block and level types and the one function that renders a set of
  blocks; `diagnostics`, `verdict` and `counts`; the sentences, in `einaf/prompts/`, hashed with the prompt;
  `check_shown`, and the mark that keeps a finding of the contract's check apart from a diagnostic of the
  kernel's, in the object and in the text. **Check first** over the benchmark's canonical programs that the
  check finds nothing a level would show: a finding there is the check's fault or the contract's.
- **T2.4.3.2 — F4: the pair and the difference.** The difference of two fact lists and of two states' rows; the
  ∅ case; the wording, through the program's own texts and S2.2.5's formatters. **A measurement, in the record**:
  on the seed's clue-dropped variants, which relations the rendered difference names against the dropped clue's
  relations, for the default pair and for the smallest-difference pair. On `examples/zebra2-minus-15.ein` the
  smallest differences among its 32 states are over `pet-loc` alone and not the dropped clue's relations
  ([`audit_p2.4.md`](../analysis/audit_p2.4.md) § A.5, item 33), so the old acceptance line is a question and
  this is where it is answered.
- **T2.4.3.3 — F5: the core and what is owed.** The wording with its caveats; the empty core; the status; the
  owed instances. **Check first** what the library gives a core's sources as before and after S2.1.2, and that a
  dead root's description costs root's saturation.
- **T2.4.3.4 — F6: the relation graph.** In `einaf::kernel`: the graph over the plans, reachability, the three
  findings, written into the object's `dependencies`. **Check first** that the plans of obligation and
  hypothesis rules can be read as the saturation rules' are (the engine's function filters to the saturation
  rules), and record what was read that the library's contract does not name. The drift check is against the
  engine's own edges for the saturation rules, on every corpus program the sweep reads; the old check against
  `fire` events could not hold, since two kinds of rule appear in no `fire` line
  ([`audit_p2.4.md`](../analysis/audit_p2.4.md) § A.4, item 31).
- **T2.4.3.5 — F7 and F8.** The chains, from the library's values, with the depth and a label for the
  commitment a state's chain is under; what a state's chain is read from (the trace's own derivation, or the
  state loaded as its program and its commitment and saturated), decided by what it costs; F8's order, cap and
  cutting rule, and its rendering under three caps.
- **T2.4.3.6 — The defect catalogue.** The planted defects as fixtures of EinAf, each with its feedback objects
  and every level's rendering. Renderings of monotone programs are banked and reviewed for wording; of a flagged
  program only that it is flagged and where; a property test holds, over the corpus, that every level renders
  every object, that F0 is one text, and that a rendering names no fact, rule or count its objects do not hold.
- **T2.4.3.7 — The kernel's diagnostics, judged as feedback.** A table, defect by block: whether the kernel
  supplied the content as a value, as text, or not at all; whether it localises (a place, a rule, a fact, a
  sentence); whether two runs of one defect say the same; its size in tokens; and the defects of which the
  kernel says nothing at any level. The table is the stage's record, and each row that is a strength, a
  weakness, a gap, a bug or a limit of Ein is an entry of [the evaluation of Ein](../evaluation/README.md), or a
  line on an entry that is there (E-11, E-12, E-16, E-18, E-19, E-24, E-28 are this stage's ground). An answer
  that is wrong by Ein's own rules goes to [the wrong-answer register](../../wrong_answers/README.md) as well.

## Acceptance

- Nine levels, each a set of blocks, each block a pure function of stored feedback objects and the program: a
  level is re-rendered from a record with no call of the kernel.
- The filter's prompt and the tool's result carry the same text for one object at one level.
- Every defect of the catalogue has its objects and its nine renderings, and T2.4.3.6's property test holds.
- F1 with `check_shown` off shows only what the kernel said; with it on, each shown finding of the contract's
  check is marked as EinAf's, and no rendering holds a finding of the faithfulness judge.
- F4 on `examples/zebra2-minus-15.ein` renders the difference of the two states `--single` lists, with no state
  shown whole; T2.4.3.2's measurement is recorded.
- F5 on `examples/ein-bugs/zebra2-bad.ein` renders the core's three facts, with the source of the one that
  carries one and as written the two that carry none (a declaration and a membership fact); a program whose
  refutation rests on no fact renders an empty core as one, and a cut search says so.
- F6 says of a fixture whose goal names a relation nothing states, derives or proposes that nothing does; says
  nothing of `examples/zebra2.ein`; and its edges for the saturation rules are the engine's.
- F7 reaches stated facts within the depth on a root fact and on a state's fact, and shows the rules that
  refuted for a core.
- T2.4.3.7's table exists and the evaluation holds its entries.

## Risks

- **The renderers are where the answer could leak** (F4, F7). The faithfulness judge reads every repair at every
  level ([S2.4.4](s2.4.4_faithfulness.md)), and G5 reports the hallucination rate beside the repair rate.
- **The wording is a variable nobody named.** Two phrasings of one block are two treatments. The sentences are
  files, hashed into the record, and are changed only as a new prompt version.
- **F6 reads what the library does not promise.** The plans and their reads and writes are `pub` and not the
  contract, so a kernel commit can move them; the record names the commit, and the drift check fails first.
- **The contract's check, shown, is EinAf telling the model what Ein would not.** It makes the feedback stricter
  than the language, and a table that mixes the two cannot say what the kernel contributed. The mark and the
  parameter keep them apart; the main table's arms say which they ran with
  ([S2.5.2](../p2.5_harness/s2.5.2_baselines.md)).
- **One defect, two explanations.** A core that moves between two iterations can read as progress. The diff does
  not count core membership ([S2.4.2](s2.4.2_repair.md)), and T2.4.3.7 records how often a core moved.
- **The object grows with the question.** A description of an under-determined program is megabytes
  ([the analysis](../analysis/README.md#p25-and-p26--records-baselines-metrics-ablations-audit)); a block reads
  what its question's object holds, and no block asks for a description the run's plan did not.
