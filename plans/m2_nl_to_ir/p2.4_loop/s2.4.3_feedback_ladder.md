## Context

The level of feedback is **the experimental variable** of the milestone, so
the ladder is built the way an instrument is: nine renderers, one object,
each renderer a pure function `(feedback, program[, events]) → text`, with
no state and no access to the model. A level is then a config value, an
ablation is two runs, and a rendering can be banked as a golden and diffed
the way the engine's own renderings are.

Most rungs are projections of what the engine already emits; two are new
computations and both live **outside the kernel**, reading its outputs:

| level | shows | source | new |
|---|---|---|---|
| **F0** | *try again* | — | the empty renderer |
| **F1** | `undefined_symbol` / `type_error` / `arity_mismatch` / `syntax_error`, with the location and the pinned message | `diagnostics[]` | nothing beyond the object |
| **F2** | one word: `unique` / `inconsistent` / `multiple_models` / `unknown` | `verdict.outcome`, `search_complete` | the mapping P2.1 made |
| **F3** | *k models remain; the query's variable `?x` has n distinct bindings* | `verdict.k`, `models[].goal_bindings` | counting |
| **F4** | two representative models and their relevant difference | `models[]` — sorted fact lists | **new**: the pair, the difference, the restriction, the rendering |
| **F5** | the unsat core as the sentences it quotes | `unsat_core` — given facts, each with its `:source` | the rendering, with the caveat |
| **F6** | *`?owner` depends on `nationality` and `house`; no path to `pet`* | **nothing in the engine** — no crate computes a relation-dependency graph | **new**: a static relation graph over the expanded program |
| **F7** | derivation chains for the facts F4 / F5 named | `ein-events/1` — `fire` lines carry `rule`, `bindings`, `premises`, `derived` | reassembly, depth-limited |
| **F8** | the union, under a size cap | all of the above | the cap G6 varies |

### F4 — the difference, not the models

Two models leak less than thirty-two and a *difference* leaks less than
two. The renderer picks **the pair whose symmetric difference, restricted
to the relations reachable from the query (F6's graph), is the smallest
non-empty one** — ties broken by the models' sorted order — so the rendered
difference is the most localised one the model set admits. The facts in it
are rendered through the program's own `:why` templates: the templates are
declared in the program ([`zebra2.ein`](../../../examples/zebra2.ein)'s
`(relation … :why "{?1} … {?2}")`), the harness substitutes positional
arguments itself, and a golden test checks that the harness's wording of a
fact equals the engine's wording in `ein solve`'s table on the same
fixture, so the loop and the human read the same sentence.

### F5 — the core, and what it is not

`unsat_core` is *the smallest set of given facts from which one recorded
contradiction follows* — a minimum-cardinality frontier over recorded
derivations, **not** a subset-minimal MUS
([glossary](../../../docs/kernel/glossary.md)). The renderer says *these
statements jointly imply a contradiction*, quotes each fact's `:source`, and
never says *the only* or *all*. A `Contradiction` with an **empty** core is
not rendered at F5 at all: it is the `-m`-cap case
([Q-M1d.6](../../m1d_satisfiability/open_questions.md#q-m1d6--may-contradiction-be-said-with-exhausted--false))
and the object already mapped it to `unknown`.

### F6 — the one analysis that is new

Nodes are relations; a rule contributes an edge from every relation its
`:match` mentions to every relation its `:assert` mentions; `hrule`s
contribute the same with a mark; the query's `:goal` names the roots.
Relation-polymorphic rules (the stdlib's T2 rules, parameterised by
relation variables) contribute edges only as **instantiated by the
activator facts present** — `(transitive left-of)` turns `std.algebra`'s
generic closure rule into an edge `left-of → left-of`. So the graph needs
the expanded program: the `import`ed `std.*` modules, the macros expanded,
the activators bound. The harness parses the stdlib files itself (they are
ein-lang text under [`stdlib/`](../../../stdlib/README.md), resolved by
`$EIN_STDLIB` → the checkout → the manifest the binary names) and
re-implements the binding step for the static graph. **Named risk:** that
is a slice of `ein-ir`'s expansion re-done outside it, and it can drift; the
mitigation is a test that, for every corpus entry, the set of rules the
graph instantiated equals the set of distinct `rule` names that appear in
the entry's `fire` events plus the rules that never fired — a check the
events give for free. The alternative — asking `ein` to dump the expanded
program — is one CLI flag away and is taken the day the drift test fails.

Reachability from the roots gives the four diagnostics the plan's A4
vocabulary has and the engine does not: `missing_dependency` (a goal
relation with no path to some relation the text mentions),
`unreachable_query` (a goal relation no rule reaches and no fact states),
`dead_relation` (a declared relation that is neither stated nor derivable),
`unused_fact` (a given fact that appears in no `fire` line's `premises`
over the run — with the stated caveat that a fact consumed only by the
search's candidate generation, or by an `(absent …)` guard, is not a
premise; the renderer says *no rule used it*, not *it is irrelevant*).

### F7 — chains from the log

For each fact F4 or F5 named: the `fire` whose `derived` is the fact, its
`premises`, recursively, to a depth cap (config, default 3); a given fact is
a leaf rendered by its `:source`. Facts derived under a commitment are found
under the `enter` that introduced it; the renderer labels the chain with the
commitment. This is what `--trace` renders for humans step by step; the
renderer is the machine-facing subset and cites the events protocol
([`events.md`](../../../docs/kernel/inference/events.md)) as its contract.

## Acceptance

- Nine renderers in `einaf/feedback/f0.py … f8.py`, each a pure function,
  each with a golden over the benchmark anchors banked under
  `einaf/tests/golden/feedback/<level>/` and diffed by the harness's tests.
- F4 on [`zebra2-minus-15.ein`](../../../examples/zebra2-minus-15.ein)
  (32 models): the chosen pair's difference names the relation(s) the
  deleted clue constrained and nothing else; the wording equals the
  engine's.
- F6 on a fixture whose query names a relation no rule reaches reports
  `unreachable_query`; on `zebra2.ein` it reports no diagnostic and its
  instantiated rule set equals the `fire` set plus the never-fired set.
- F5 never renders an empty core; F7's chains on `zebra2.ein`'s unsat
  fixture (`examples/ein-bugs/zebra2-bad.ein`) reach the given facts within
  the depth cap.
- F8's size cap is a parameter and the rendering under each of three caps
  is banked.

## Tasks

### Task T2.4.3.1 — F0–F3: the projections

`einaf/feedback/{f0,f1,f2,f3}.py`; the level enum and the dispatch
`render(level, feedback, program, events=None)`; the goldens.

### Task T2.4.3.2 — F4: the pair and the difference

`einaf/feedback/f4.py`: the symmetric difference of two sorted fact lists,
the restriction to F6's reachable set, the pair selection, the `:why`
substitution (`einaf/render/why.py`, shared with the demo), the equality
test against the engine's table wording.

### Task T2.4.3.3 — F5: the core as sentences

`einaf/feedback/f5.py`: the `:source` lookup, the fixed caveat sentence,
the empty-core guard.

### Task T2.4.3.4 — F6: the relation graph

`einaf/analysis/deps.py`: the expanded-program reader (imports, macros,
activator binding), the graph, reachability, the four diagnostics written
back into the feedback object's `dependencies` field (which S2.1.2 leaves
empty for this stage to fill); the drift test against `fire` events over
the corpus.

### Task T2.4.3.5 — F7 and F8

`einaf/feedback/f7.py`: the chain reassembly from `ein-events/1` with the
depth cap and the commitment label; `f8.py`: the union, the size cap, the
order (verdict, core or difference, dependency, provenance — the order the
plan's F8 object lists them in), the three banked caps.

## Notes

- **Nothing here changes the engine.** F6 and F4 are computations over the
  program and the summary; F7 over the event log. If F6's drift test fails
  repeatedly, the fix is a dump flag on `ein` (an additive CLI change, like
  `--feedback`), not a change to what the engine derives.
- The renderers are the place the answer could leak (F4, F7). The
  faithfulness judge ([S2.4.4](s2.4.4_faithfulness.md)) reads every repair
  regardless of level, and [P2.6](../p2.6_ablations/README.md) G5 reports
  the hallucination rate beside the repair rate for exactly this reason.
