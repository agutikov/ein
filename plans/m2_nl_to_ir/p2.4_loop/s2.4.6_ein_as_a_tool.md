## Context

The user, of the two roles Ein has in this milestone: *"On one hand ein works like a tool for LLM, on other hand
it works like filter of thoughts"*, and of the first: *"LLM can decide to use it on it's own, it is recommened
but optional"*. This stage builds that arrangement, **the tool**, arm B6 of [the frame](../README.md#the-arms):
the model reasons in text, one function is declared to it, and it calls the function when it likes, or never.
The filter ([S2.4.1](s2.4.1_state_machine.md)) is the same model and the same kernel with the decision on the
other side.

| | the filter | the tool |
|---|---|---|
| who decides that Ein runs | the harness, on every generation | the model |
| what the model writes | an Ein program and nothing else, thinking off | text, and a program where it calls |
| what holds the syntax | the harness and a grammar | nothing: *a parse error is what the tool returns* |
| the kernel's reply | rendered into the next prompt | the function's result, the same text at the same level |
| when it ends | the machine's termination | the model answers, or a budget |
| the answer | what the program prints | the model's last message |

**What the two share is everything but the machine**: the bounded kernel call and its bounds, the questions
asked of a program, the feedback object, the renderer and its levels, the judges, the record's vocabulary. So a
difference between B5 and B6 is a difference of arrangement, and the stage's work is to keep it so.

**The user's remark on the model is a hypothesis this stage tests in earnest**: a model not trained on Ein may
write it all the same, the semantics being near Datalog's and the syntax Lisp's and SMT-LIB's. S2.2.2 measures
it first, where it is cheapest. Here it is the whole arrangement: the model writes Ein *as it can*.

**Nothing of [M15](../../m15_mcp_server/README.md) starts by it.** The tool is a function the harness declares
to the model in its own process, where the model runs through a binding to llama.cpp
([Q-M2.14](../open_questions.md#q-m214--what-runs-the-model)). It is no server, speaks no protocol and is no
surface of Ein: nothing under `ein.rs/` or `docs/ein/` knows of it.

**What the host showed** ([`analysis/host.md`](../analysis/host.md), one run, through `llama-server`): asked to
use a declared function `ein_solve(program)` on a one-line program, the model returned a call with the program
as its argument and no text. `llama-server` applied the model's chat template and parsed the call; in EinAf's
process both are the runtime's or this stage's.

### An episode

One context from start to end, kept by the runtime:

1. **The prefix**: the instructions and the answer line, as B1 has them
   ([S2.5.2](../p2.5_harness/s2.5.2_baselines.md)); the function's declaration; the text of the problem.
2. **A turn of the model**: reasoning, and then a call or an answer. Thinking is as B1's
   ([S2.5.2](../p2.5_harness/s2.5.2_baselines.md) fixes it), so that B6 is B1 with the function offered.
3. **A call** goes through the bounded kernel call; its result is appended as the function's turn, and the
   model's next turn pays for the result's tokens only.
4. **An answer**, a turn with no call, ends the episode.

It ends also at the arm's budget of generated tokens, thinking included, and at `max_calls`, a parameter that is
a guard and not the budget. An episode cut by either before the model answered has no answer, as a chain of
thought cut before its first answer has none.

### The function

One function, one argument: `program`, a string, a whole Ein program as a file would hold it. The name is
`ein_solve`, as probed, unless S2.2.2 finds the model reads another better.

- **Its description is where the model learns Ein.** P2.2 leaves to this stage how much of what the filter's
  prompt holds the tool's description quotes. The default is all of it that is about Ein: the excerpt of the
  reference, the catalogue of the library and the examples ([S2.2.1](../p2.2_formalizer/s2.2.1_contract.md),
  T2.2.1.3), under the same hashes, and nothing of the contract's passes. B6 then knows of Ein what B5 knows, and
  B1 differs from B6 by the function and what describes it.
- **The model does not choose the question or the level.** Which questions the kernel is asked is S2.4.1's plan,
  and how much of the reply is shown is the run's level, the experimental variable.
- **A call is whole and stateless.** Each carries a complete program; the kernel keeps nothing between calls.
  A corrected program is sent again in full, and its tokens are generated tokens of the budget.
- **Imports** resolve as the kernel resolves them: `std.*` from the library, a local module from the run's
  directory, the same in both arrangements.
- **`:why` is required**, as the kernel requires it. A program with none is refused with the kernel's own line,
  and how often that is the refusal a model meets is a count of the record.

### What a call returns

Two parts, in this order, both from the call's feedback objects and nothing else:

1. **What the program printed**, where the kernel passed it ([S2.4.1](s2.4.1_state_machine.md): the outcome is
   *one* and the answer query has a row): each row through the query's `:goal-text`, a value that does not read
   as text through S2.2.5's formatters. Where the kernel did not pass the program, **one fixed line that says no
   answer was printed**, the same at every level. A flagged program is such a program: the kernel prints an
   answer for it and claims nothing of that answer, the tool does not hand it on, and the record keeps it
   ([Q-M2.11](../open_questions.md#q-m211--what-is-a-flagged-program-to-the-loop)).
2. **The feedback, at the run's level**: [S2.4.3](s2.4.3_feedback_ladder.md)'s rendering, the same text the
   filter's prompt would hold for the same objects. It says why no answer was printed, as far as the level
   allows. The tool's levels start at F1: the ruling says a parse error is what the tool returns, and F0 would
   withhold it. B6's level is F8 by default, as B5's is, and the level the tool replies at is an ablation
   ([P2.6](../p2.6_ablations/README.md)).

The filter's fixed texts for an outcome that is no answer ([S2.2.5](../p2.2_formalizer/s2.2.5_from_text.md)) are
not the tool's to give: here the answer is the model's, and the answer line tells it the two texts it may give
instead of an answer.

A call the harness could not read as a call (below) returns an error of the harness's own, in other words than
any of the kernel's, and is counted apart.

### The answer, and what the record says of it

The answer is the model's last message, reduced to a short text as B1's is. The episode's record holds, beside
its turns:

| field | what |
|---|---|
| `calls` | how many; of them how many the harness could read, how many parsed as Ein, how many loaded; each call's program, feedback objects, result and outcome |
| `skipped` | the model answered with no call |
| `last_run` | the last call's outcome and what it printed |
| `answer_from_ein` | whether the answer is, after the scoring's normalisation, what the last run printed: `equal`, `differs`, `nothing printed`, `no call`; and, where it differs, whether it is what an earlier run printed |
| `readings` | of the last call's program, which is the episode's final program ([S2.5.3](../p2.5_harness/s2.5.3_metrics.md)): the three questions the filter's ANSWER asks, asked once at the end and never shown to the model |
| `tokens` | generated, by kind: reasoning, programs, the answer; evaluated anew and reused, a turn |
| `faithfulness` | the judges' events, a call |

`answer_from_ein` and the token share that is Ein are what make the arm readable as *a chain of formal reasoning
in place of a chain of thought*: an episode that called once and answered something else was a chain of thought
with a detour.

## Tasks

- **T2.4.6.1 — The function and the call.** The declaration; the model's chat template with a function declared,
  kept as a file of the record ([Q-M2.14](../open_questions.md#q-m214--what-runs-the-model): *the chat template
  as a file of the record, not a server's default*); the reader of a call out of the model's output; the
  harness's own error for a call it cannot read. **Check first** what the binding S2.2.2 chose does of this
  (applying a template with tools, parsing a call) and what is left to EinAf, against what `llama-server` did in
  the host's probe on the same file.
- **T2.4.6.2 — Can the model quote a program?** A program holds double quotes in every `:why` and `:source`, and
  the native call carries it as one string argument. Before anything else runs with the model: on the seed's
  canonical programs, given to the model to pass through, the rate of calls the harness reads back to the same
  program. If the model cannot quote, the fallback is a fenced block read as a call, decided here with the
  number; the function stays one function with one argument either way.
- **T2.4.6.3 — The episode.** `einaf::tool`: the turns, the kept context, the three ends, over the same bounded
  call and the same questions as the filter. The context's limit, and what happens at it: an episode the context
  ended says so in its record.
- **T2.4.6.4 — The result.** The two parts; the fixed line; a result's cap, which is F8's; a test that for one
  set of objects the tool's second part is byte for byte the filter's prompt block.
- **T2.4.6.5 — The prompt.** `einaf/prompts/`: the instructions, in which *recommended* and *optional* are both
  said, in the user's sense; the function's description, with what it quotes of Ein; the answer line, S2.5.2's.
  Each is hashed into the record. The wording of the recommendation is a variable P2.6 may turn; the stage
  writes one and names it.
- **T2.4.6.6 — The record.** The episode's type and the fields above; the final readings; a page of
  `docs/einaf/`.
- **T2.4.6.7 — Replay and fixtures.** A replayer of stored episodes, and canned ones, in EinAf's step of the
  gate with no model: an answer with no call; a call whose program does not parse, then a corrected one, then an
  answer equal to what it printed; a call that returns *several* and an answer given all the same; a call the
  harness cannot read; a call whose program's saturation does not end; an episode cut by the budget; a call
  with a flagged program, whose result holds the fixed line and, at the level, the sites.
- **T2.4.6.8 — The judges on an episode.** [S2.4.4](s2.4.4_faithfulness.md)'s interface over every program a
  call carried and, in the metrics, the last call's. Nothing forces a `:source` here: the share of stated facts
  that carry one is reported first.
- **T2.4.6.9 — First runs, by hand.** The seed set once, with the model and a record: how often it calls, how
  many calls an episode, the outcomes of its calls, `answer_from_ein`, the token shares. Counts, and no table:
  the comparison is [S2.5.4](../p2.5_harness/s2.5.4_first_table.md)'s.
- **T2.4.6.10 — The evaluation.** Into [the evaluation of Ein](../ein_evaluation.md), from the arrangement in
  which nothing stands between a model and the kernel: which refusals a model writing Ein unaided meets, by
  kind, and which of the kernel's lines it could act on (a parse error's ranked repairs; a load refusal's *what
  to write instead*); the programs that loaded and answered something other than what their author meant, with
  no word from the kernel (E-11, E-12, E-13, E-18); what one call costs; and what the model had to be told of
  Ein that no page of Ein says in a form a prompt can hold.

## Acceptance

- Under the replayer, each canned episode of T2.4.6.7 ends as its fixture says, and its record holds every
  field: the episode with no call has `skipped`; the episode whose answer repeats its last run's print has
  `answer_from_ein` `equal`; the one that answers after a call that returned *several* has `nothing printed`; the
  call that does not return is *not decided* within the bounded call's bound, and the episode goes on.
- A program that does not parse gets the kernel's parse error back at every level the tool has; the harness's
  own error is never worded as the kernel's.
- For one set of feedback objects at one level, the tool's feedback part and the filter's prompt block are the
  same bytes.
- No part of a result holds a judge's finding or a reading asked for the record.
- An episode is priced in generated tokens, thinking included, with its calls counted; a replayed episode
  reproduces its record.
- T2.4.6.2's rate is taken and the call's form decided on it; T2.4.6.9's counts are in the stage's record.
- `grep -ri 'mcp'` over `einaf/` finds nothing, and nothing of M15's plan is changed by the stage.

## Risks

- **The model never calls.** *Optional* is the ruling, and a small model may answer from its own reasoning every
  time; B6 is then B1. That is a finding and `skipped` is its number. What the stage owes is that the
  recommendation was said, in a prompt whose hash is in the record; forcing the call is the filter.
- **The model cannot write Ein.** With no grammar and no training, every call may be refused. The record's
  counts of calls read, parsed and loaded say where it stops, and the filter with its grammar off
  ([P2.6](../p2.6_ablations/README.md)) is the same question asked from the other side.
- **B6 and B5 differ in three things at once**: who calls, thinking, the grammar. Each is a field of the record,
  and the two ablations of the frame (the filter with its grammar off; the filter after a chain of thought) are
  the steps between them. This stage adds no fourth difference: the same knowledge of Ein in the prompt, the
  same level, the same kernel bounds.
- **A whole program a call fills the context.** Programs sent again in full and results at F8 are long; an
  episode can end at the context's limit before the token budget. The record says which ended it, and the
  result's cap is the lever.
- **The result is the answer.** In the filter the model never sees what its program printed; here it is the
  first thing returned, and the model may copy it whatever the program rests on. That is the arrangement, and
  why the judges read every program and `answer_from_ein` is kept apart from correctness.
- **A model-written program runs under EinAf.** The bounded call is the guard, as in the filter; a program
  that reaches neither bound and still costs (a search over what the blind enumerator wrote) is bounded by the
  facts budget and by `--single` asking for two states.
