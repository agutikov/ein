## Context

Three ablations share one shape — *what the model is given to write from,
and what it is allowed to write* — and they are one stage because the
conditions compose: a decomposition variant (G8) under a minimal library
(G9) with a dependency parse in the prompt (the link-grammar arm) is one
config, and the record names all three axes.

**The link-grammar arm is the old P2.5, carried whole.** The user's open
question — *does feeding link-grammar output to the LLM enrich the input
usefully?* — was a phase of the old plan, with a runner, a serialiser, an
A/B and a pre-registered decision rule; what changes is only the metric
(constraint precision / recall on synthetic families, where the gold theory
is exact, plus answer accuracy — not IR-F1 on five puzzles) and the place
(an arm here, since G8 asks the same question about the *output* side). The
hypothesis is as plausible as it was: link-grammar exposes head / dependent
structure a model might use to disambiguate; it is equally plausible that an
instruction-tuned model already does that internally and the pre-pass is
noise. The point is to **measure, not assume**, and the default deployment
is *off* unless it measures a win. **The submodule is not registered**:
`git submodule add https://github.com/opencog/link-grammar.git nlp/link-grammar`
is the first task, and the two scratch scripts in [`nlp/`](../../../nlp/README.md)
(`xxx-link.py` is link-grammar over the English Zebra text) are the starting
point.

**G8 asks whether an explicit intermediate helps.** The plan's B1 allows a
decomposition — *entities, relations, constraints, query* — before the
program and says *evaluate whether this intermediate representation helps
rather than assuming that it does*. [S2.2.4](../p2.2_formalizer/s2.2.4_passes.md)'s
four passes are already a decomposition *in ein-lang*; the G8 variant is a
fifth pass in front of them that writes a plain JSON semantic model the four
passes are then conditioned on. The user's four oracle ablations
([F13](../../followups/f13_puzzles_beyond_zebra/ideas.md)) are the same
axis cut the other way — what the model is *given* of the gold program —
and they are the most informative conditions in the stage, because each one
switches off exactly one thing a failure could be blamed on:

| condition | what the model receives | what it writes | what it isolates |
|---|---|---|---|
| **NL + known theory** | `text.md` and the gold program's *theory* part (the `import`s and activators; for the two synthesis families, the canonical rules) | ontology, instance, query | semantic parsing, with theory selection taken out |
| **IR + unknown theory** | the gold program's ontology, instance and query — **no text** | the theory part only | theory selection / synthesis, with parsing taken out |
| **IR + known theory** | the whole gold program | nothing — the kernel alone | the kernel; 100 % by construction (it is `einaf bench check`), and the number that matters is its cost column |
| **NL + unknown theory** | `text.md` | everything | the full pipeline — B2 one-shot, B5 with the loop |

*Where the 18 % goes* is the question these four answer, in the user's
phrase, and the table is per family, because the two synthesis families
are expected to fail on the second row and nowhere else.

**G9 asks how much is the library.** Three conditions, each named by
manifest — the stdlib `MANIFEST.sha256` that `ein --version` prints, plus
the subset list: **none** (no `import` permitted; the model writes every
rule), **minimal** (`std.algebra` only — the signature and the property
closures), **full** (all seven modules, the catalogue as
[S2.2.1](../p2.2_formalizer/s2.2.1_contract.md) generates it). The
condition is enforced where it cannot be argued with: the theory grammar
([S2.2.3](../p2.2_formalizer/s2.2.3_gbnf.md)) lists the permitted `import`
targets, so a forbidden module is *unparseable*, not merely discouraged,
and the catalogue in the prompt lists the same set. This is the one
ablation that also reads on [F8](../../followups/f8_FCA_RCA_odis_tptp/ideas.md)'s
`C(n)` — how many distinct rule schemas the model writes under **none**,
across families, is the first point on that curve taken by a machine rather
than by hand.

### The pre-registered readings

Written here, before any run, in the old S2.5.2's form:

- **Link-grammar**: on the synthetic families at B2, three seeds,
  `F1_augmented − F1_baseline` over constraint precision / recall:
  `> 0.03` → ship as a default-on pre-pass; `< 0.0` → deprecate, code path
  removed; between → opt-in, `--link-grammar`, default off. Answer accuracy
  reported beside it and not part of the rule.
- **G8**: the decomposition variant must beat direct generation on
  constraint recall *and* not lose on faithfulness (the extra pass is one
  more place to invent); if it wins on recall and loses on faithfulness,
  the reading is *the intermediate helps coverage and hurts grounding* and
  the variant stays an option, not the default.
- **The oracle conditions**: the gap between *NL + known theory* and
  *NL + unknown theory* is the cost of theory selection; the gap between
  *IR + unknown theory* and 100 % is the cost of theory synthesis on the two
  families without a module. The reading is the pair of gaps per family;
  no threshold, because the numbers *are* the result.
- **G9**: if **full** ≈ **minimal**, the reusable theory beyond the
  signature is not what the performance comes from; if **none** ≈ **full**
  on the six stdlib families, the model is re-deriving the library and the
  library's value is cost, not accuracy — reported as tokens per solved
  instance. Either is a finding.

## Acceptance

- The submodule registered, built by `scripts/build-link-grammar.sh`, the
  install path recorded; the runner produces parseable output on the
  seed set's anchors; the serialiser's `(link-grammar …)` fragment round-trips
  through the parser; a clearly ambiguous sentence yields multiple linkages.
- The four conditions of the oracle table and the three of G9 are configs in
  [S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md)'s schema; the G9
  condition is enforced by the grammar and visible in the record by manifest
  SHA and subset.
- Every arm run on `val`, three seeds, under the budget rule; tables from
  records; each read by its pre-registered rule.
- [Q11](../open_questions.md#q11--link-grammar-value) resolved beside its
  entry, with the per-family numbers; the code state matches the verdict
  (shipped, opt-in, or removed — if removed, `nlp/` stays as the historical
  reference and the submodule reference goes with the code path).

## Tasks

### Task T2.6.4.1 — Register and build link-grammar

`git submodule add https://github.com/opencog/link-grammar.git nlp/link-grammar`;
`scripts/build-link-grammar.sh` wrapping the submodule's build to an
importable `linkgrammar` binding in a build directory; the install path and
the version in the record's config.

### Task T2.6.4.2 — Runner and serialiser

`einaf/nlp/link_grammar.py`: `parse_sentence(text) → linkages + scores`;
`to_fragment(linkages, k=2..3)` → the informational `(link-grammar :sentence
"…" :linkages ((linkage 0 :links ((subj Norwegian lives) (det "the"
Norwegian) (obj House-1 lives) (pos House-1 first))) …))` form — *context
for the prompt, never a constraint*; the augmented facts-pass template
`facts-with-link-grammar.tmpl`. Tests: the old S2.5.1's three — a Zebra
sentence parses; the fragment round-trips; *the bank is by the river* yields
several linkages.

### Task T2.6.4.3 — The decomposition variant

The fifth pass: `text → semantic.json` (`entities`, `relations` with
signatures, `constraints` as NL spans paired with relation mentions,
`query`), under its own grammar, recorded as a generation; the four passes
conditioned on it by prompt. One config flag: `--decompose`.

### Task T2.6.4.4 — The oracle conditions

Four configs, each defined by which parts of `gold.ein` are supplied in the
prompt and which the model writes; the harness assembles the program from
the supplied parts and the generated ones, certifies, and records which
parts were gold. *IR + known theory* is `einaf bench check` relabelled and
runs for its cost column.

### Task T2.6.4.5 — The library conditions

The three `import` allow-lists; the theory grammar generated per condition;
the catalogue generated per condition; the condition's manifest SHA + subset
in the record. The `C(n)` count under **none**: distinct rule schemas after
canonicalisation, per family and cumulative, in the report.

### Task T2.6.4.6 — Run, read, resolve

Three seeds × arms × `val`; the tables; the readings applied; Q11 written;
the code state made to match.

## Notes

- The old P2.5's *gold IR* per puzzle is not needed: the synthetic

  instances rather than five.
- Link-grammar is English-only in practice; the RU realisations, when they
  exist, run the arm with the pre-pass off and say so.
