## Context

A synthetic instance is **a situation first, a program second and a text third**. A generator draws the
situation the problem is about (a permutation, a total order, a placement, a sequence of states, a set of
amounts), chooses statements true of it, and **counts the answers itself**: it enumerates, in Rust and not
through Ein, the situations its statements allow, and reads the question's answer off each. From that count it
writes the canonical program with its claims, and from the program's facts the English. Then
[`einaf bench check`](s2.3.1_families_and_seed_set.md#task-t2315--einaf-bench-check) admits the instance or
does not.

That order is what each promise of C2 rests on. *Exact ground truth* is the generator's enumeration; *the exact
formal theory* is the program; *controlled difficulty* is the generator's arguments; *controlled ambiguity and
contradictions* are a statement deleted and a statement added. The kernel is the second route to the same
answer, through the program's `:expect`, and not the first: the old plan made one exhaustive run of the kernel
both the oracle of the generation loop and the certificate, that command is retired
([audit](../analysis/audit_p2.3.md) § A.1), and a benchmark that measures a system with the kernel in it should
not take its gold from the kernel alone.
**A disagreement between the two routes is a finding, never a rejected instance** (T2.3.2.8).

The corpus's own generators are the precedents, none of them a generator of this stage (audit § B.5):
[`gen_arith_examples.py`](../../../utils/gen_arith_examples.py) computes a program's claims with integers
outside the engine and writes the same bytes for the same arguments;
[`region_synth.py`](../../../utils/region_synth.py) writes a program for a chosen region;
[`gen_zebra2_variants.py`](../../../utils/gen_zebra2_variants.py) splices verbatim blocks of `zebra2.ein` into
four corpus files, draws no situation and realises no English, and stays the one writer of those four
(audit § C.2).

### The three classes, by construction

| class | how the generator makes it | what it knows before the kernel is asked | the claims it writes |
|---|---|---|---|
| **one answer** | draw a situation; add statements true of it, in a random order, until its enumeration finds one answer to the question | the answer | the answer query's `(model F …)` |
| **ambiguous** | delete one statement from an instance with one answer; keep it if the enumeration now finds two answers or more | the answers | the answer query's `(or (model …) (model …))`, asked `:over maximal` where the theory states restrictions only |
| **unsatisfiable** | add one statement false of the situation, such that the enumeration finds no situation; *local* (it contradicts one statement) or *deep* (it contradicts a chain), a knob | that there is none | the answer query's `(false)`, which holds over either kind of empty R; and `(solve :expect (false))` where the family's theory refutes at root |

Three things the table does not say by itself:

- **The count is of answers, not of situations.** A deleted statement can leave several situations and one
  answer to the question. That instance is of class *one answer*, the kernel says `Ambiguity` of it, as it does
  of [`boxes12.ein`](../../../examples/word_problems/boxes12.ein), and it is kept, marked: it is where a system
  that reads the verdict word is wrong.
- **Which kind of empty R an added statement gives is the theory's**, `Contradiction` or `Open`
  ([§ How a class is established](README.md#how-a-class-is-established)). The generator writes the query's
  `(false)`, true of both; the check writes the kind into the metadata; and T2.3.2.6 reports, a family, how many
  of its unsatisfiable instances are of each.
- **A class is never read off a capped run.** A stopped run does not say `Contradiction`
  ([Q-M1d.6](../../../docs/decisions/answer/Q-M1d.6-contradiction-is-said-only-where-no-node-is.md)); under
  `ein test` a claim the budget leaves undecided is `NOT CHECKED`, and the instance is not admitted.

### What is not admitted, and the log

An instance the check does not admit is not written into the benchmark. It is logged, one line with its
arguments and the reason, in `einaf/benchmark/rejected.jsonl`:

| reason | what it measures |
|---|---|
| the program is flagged | which knob settings of a family leave what the engine answers for ([Q-M2.11](../open_questions.md#q-m211--what-is-a-flagged-program-to-the-loop)) |
| a claim is `NOT CHECKED` at the default `--region-budget`, or the run passed the wall bound the stage sets | where the kernel stops deciding the family: the first points of the solver's curve of [P2.7](../p2.7_failure_scaling_generalization/README.md) |
| the generator's own enumeration passed its bound | where the gold stops being known by construction |
| a claim `FAILED` | **the two routes disagree**: not a rejection but a finding, opened by T2.3.2.8 before the generator runs on |

### The knobs

C4's ten as generator arguments, and two more, each a field of the metadata's `knobs`:

| knob | what it varies | applies to |
|---|---|---|
| `entities` | the size of the domain or domains | all |
| `relations` | how many relations the text uses | all |
| `chain_depth` | the longest derivation the answer needs | deduction, ordering, graph, temporal, word problems |
| `branching` | alternatives a choice point | attribute matching, spatial |
| `density` | statements an entity, from under-determined to over-determined | all |
| `irrelevant` | statements true of the situation that no derivation of the answer uses | all |
| `paraphrase` | which of the surface templates of a statement type is used | all |
| `implicit` | whether a relation is stated or has to be inferred (*immediately left* stated, *left* implied) | ordering, spatial |
| `answers` | the count of answers aimed at, for the ambiguous class | all |
| `distance` | sentences between two statements one deduction needs | all |
| `steps` | the number of transitions | object tracking, word problems |
| `contradiction` | *local* or *deep*: whether the added statement contradicts one statement or a chain | the unsatisfiable class, all |

### The canonical theory where the library has none

Where a family's theory is library activators, the program's theory part is imports and property facts. Object
tracking and temporal have no module in the library, and set and category has none for disjointness; their
rules are the family's own module, written once on the anchor ([S2.3.1](s2.3.1_families_and_seed_set.md),
T2.3.1.2) and imported by every instance from its own directory. Those rules are the canonical theory: the
metadata's `theory.local` names the module, [P2.6](../p2.6_ablations/README.md)'s library ablation lists it as
*not in the library*, and a formalizer that synthesises another rule set is scored by what it derives, not by
its text. The word problems are the same case with four modules. The library does not grow for a family inside
M2 (the frame's default 11); if [M1h](../../m1h_beyond_word_problems/README.md)'s timeline and causal theories
ship before a later version of the benchmark, that version says so and the family's own module stays as the
reference.

### The unit of constraint precision and recall

The gold set of an instance, for H2 of [S2.5.3](../p2.5_harness/s2.5.3_metrics.md), is its fact forms that
carry a `:source`, its activator forms, and, where the family has a theory of its own, that module's rule forms.
A predicted program's set is taken the same way, and precision and recall are set arithmetic over the two.

- **A form is compared as loaded, not as written.** One relation has three spellings by its import's form (a
  short name listed in `:symbols`, an alias, the full name) and the answer does not depend on which. The key is
  the form under full names.
- **`:source` and `:why` texts are set aside.** Two programs that differ in a `:why` state the same constraints
  (audit § C.5).
- **The printer is the library's.** `ein_ir::dump_canonical` prints forms as written, and no command prints it
  (audit § A.1, row 9); EinAf links the crate. Whether the key is that dump over full names or the loaded facts
  themselves is settled with S2.5.3.
- **A different text with the same closure is two numbers.** A generated auxiliary relation or rule that derives
  what the gold derives is a recall miss on the form and a hit on the closure; both are reported, and the second
  is the one that matters for the families with no library theory.

## Tasks

### Task T2.3.2.1 — The generator frame

A module of `einaf/src/`, behind `einaf bench generate --family F --class C --seed S [knobs]`: draw a situation;
choose statements; enumerate; derive the class; write the program with its claims, the text and the metadata;
run the check; write or log. The frame owns the enumeration's bound, the admission and the log; a family's
module owns the situation, the statement vocabulary, the theory part, the question and the templates. The same
arguments and seed give the same bytes, and `einaf bench generate --check` regenerates every generated instance
the manifest names and compares. First act: check this file's sentences about the kernel against the kernel
(the frame's default 14).

### Task T2.3.2.2 — Attribute matching first

The permutation model and Zebra's statement vocabulary, in the encoding [S2.3.1](s2.3.1_families_and_seed_set.md)
fixed for the family. Held to the anchor: given Zebra's situation and its statements, the generator writes
Zebra's facts and activators, compared in the unit above. Grids smaller than Zebra's and over other ontologies
replace the old plan's Einstein variant and logic grids. Where the family has two encodings, as the corpus has
for Zebra, the generator writes a sample in both and the check holds the two to one answer: an invariance, the
program-level twin of a paraphrase.

### Task T2.3.2.3 — The families with a library theory

Logical deduction and ordering (a total order; `transitive`, `includes`, and whichever of `asymmetric` and the
rank encoding the anchors settled), spatial (two orders, `converse`), graph (an edge list; `transitive`,
`symmetric`), set and category (subsumption by the library, disjointness by the family's module), each in its
three classes.

### Task T2.3.2.4 — The families with none

Object tracking (a sequence of states; the `steps` knob; the transition rules of the anchor's module) and
temporal (intervals over named moments; the interval fragment of the anchor's module). The module is written
once and imported; an instance copies no rule.

### Task T2.3.2.5 — The realiser

A family, three templates or more a statement type, English, names ASCII. A fact's `:source` is the sentence
the realiser wrote for it, so the check that every `:source` is in the text is exact. An irrelevant statement is
realised from a fact of the situation no derivation of the answer uses, which the generator knows because it
drew the situation. A test holds that the templates of a type realise to distinct strings.

### Task T2.3.2.6 — The rejected log and where each family stops

`einaf/benchmark/rejected.jsonl`, and from it one table: a family, the first knob setting at which an instance
is not admitted for the budget or the wall bound, with the question `ein test` asked there (a description or a
line: [E-17](../ein_evaluation.md)); and a family, the split of its unsatisfiable instances between
`Contradiction` and `Open`. A time quoted in it is taken through
[`utils/bench_env.sh`](../../../utils/bench_env.sh), on AC. The table goes to
[P2.7](../p2.7_failure_scaling_generalization/README.md) and, as limits, to the evaluation of Ein.

### Task T2.3.2.7 — The word problems

A generator over the sixteen problems' shapes: the people, the kinds and the numbers vary, the theory modules
do not. The answer is computed with Rust's integers, outside the calculator, as `gen_arith_examples.py` does
with Python's; the classes come from the shapes the corpus has (a quantity left unstated, an assumption
written, a word with two readings, a transfer larger than what was had) and not from a deleted clue alone.
Numbers stay within what the calculator's programs are sized for
([Q-M1f.166](../../../docs/decisions/corpus/Q-M1f.166-the-generated-arithmetic-examples-are-sized-for.md)); the
`val` and `test` instances of the domain are this generator's, since the sixteen are seen by prompt development.

### Task T2.3.2.8 — What generating found of Ein

Add to [the evaluation of Ein](../ein_evaluation.md), one entry a finding, with the generator's arguments that
reproduce it: every disagreement between a generator's count and the kernel's check, once its cause is known
(the generator, the canonical theory, or the kernel; the last is also a row of
[the wrong-answer register](../../wrong_answers/README.md), with its witness, in a commit of its own); each
family's limit from T2.3.2.6; each knob setting that turns a family's programs flagged; what a theory needed
that the library lacks; how the kind of empty R fell out; and what held at scale without attention. Hundreds of
generated programs a family is the widest use of the language this milestone makes before a model writes any.

## Acceptance

- A generator for each of the eight families and the word problems, as modules of the package, behind one
  entry point; each writes an instance's files in [S2.3.1](s2.3.1_families_and_seed_set.md)'s format.
- Determinism: the same arguments and seed give byte-identical files; `einaf bench generate --check` is a step
  of EinAf's gate over the stated sample.
- Every instance written was admitted by `einaf bench check`; every other is a line of `rejected.jsonl`.
- In each family the three classes exist, or the family's page names the one it lacks and why; instances with
  several situations and one answer exist and are marked.
- Three surface templates or more a statement type a family, chosen by the `paraphrase` knob.
- No open disagreement between a generator and the kernel: each is explained, and filed where it is the
  kernel's.
- The table of T2.3.2.6, and the stage's entries in the evaluation of Ein.

## Risks

- **The generator and the theory share a mistake**, which two routes written by one hand can: the anchor, a
  third thing written first and by hand, is what both are held to (T2.3.2.2).
- **A knob setting flips a family's monotonicity.** The static check is run on every instance, not once a
  family: a hypothesis over a relation that a rule of the family reads under `absent` is a site, and whether a
  program has one can depend on its class ([§ Risks of the phase](README.md#risks)).
- **The enumeration is the bottleneck, not the kernel.** A family's enumerator is brute force by design, so
  that it shares nothing with the engine's search. Where it stops before the kernel does, the gold of larger
  instances rests on the kernel alone and the metadata says so (`gold_by: "kernel"`); such instances are kept
  out of `test` unless the user says otherwise.
- **The realiser writes a dialect** ([§ Risks of the phase](README.md#risks)).
- **`minimal` costs a run a statement.** A statement set with no redundant statement is found by trying each
  removal; the flag is optional, recorded, never assumed, and worth having at the low end of `density`.
