## Context

The decision: *a relation may be declared more than once, at one count or at several, and no declaration is
refused as a duplicate of another*. A program with two declarations of one relation loads; the same program with
one `(import …)` line is refused, `kb load error: conflicting definitions of 'likes': same name, different body`.
The refusal is the imports pass's de-duplication of declarations, keyed on the kind and the name, which runs only
where a program imports. The test that holds the decision has no import in its programs. Met twice by the
application: at two counts (S2.2.0a's probe) and at one count with two label lists (the model's `unused`).

### The user's statement, given during the stage

Passed on by the coordinator while the stage ran, quoted as the coordinator asked, the first message and its
correction:

> "A relation declared again, under an import - at first it has different global name - so it is different
> relation, but if it is imported with  :symbols then it is the same relation and in this case it is just 2
> different relation declarations - different ordinary facts of relation `relation`. If imported without :symbols,
> without alias, rules from program code does not see relation fact from module, because it has different name and
> thus it is different atom. If imported with local alias - then both program rules and module rules see the same
> objects by the same atom."

> "in the third case a.likes is M.likes, but if program declares it's own (relation likes ...) it is different,
> obviously because 'likes' != 'a.likes'"

And, beside it, *"rules with the same name are load errors"*, and on how the stage is framed:

> "2 relation declarations is also possible because they are different facts, that may be used by different rules -
> this is Ein's semantic. We would not change Ein sematic to help dumb 4B LLM write programs, we will do it another
> way." What Ein does in each case, probed on the fix:

- **A program's own two declarations of its own relation, beside an import of anything**: one relation, two
  declarations, which load. That is E-104, fixed here, the statement's simplest instance.
- **A bare import, and a program that declares its own `likes`**: two relations, `likes` and `m.likes`, neither
  file's rule reading the other's facts, at the module's count or another. As stated, and as Q-M1f.231 and
  Q-M1f.236 say; held by `under_a_bare_import_or_an_alias_a_program_and_a_module_declare_two_relations`.
- **An alias, and a program that declares its own `likes`**: the same, `likes` and `a.likes`; held by the same test.
- **A list, `(import m :symbols (likes))`, and the program's `(relation likes …)`**: the statement says one relation
  with two declarations; Ein refuses it, *'likes' is bound to two full names in the program, likes (its own
  declaration) and m.likes*, as Q-M1f.234 rules. **Not changed: the user's to rule** (Q-M2.43).
- **An alias, and the program's `(relation a.likes …)`**, the module's atom by the statement: Ein loads it and makes
  `a.likes` a relation of the program's own, in silence, which the module's rule does not read; the module's then
  prints `m.likes`. No decision says so. **Not changed** (Q-M2.43).
- **A bare import, and the program's `(relation m.likes …)`**, the full name: refused by Q-M1f.239. Recorded, not
  changed, as the coordinator asked (Q-M2.43 asks it too).

### What was built

**T2.2e.1.1, what the pass refuses.** `dedup_declarations` reads the resolved list of a program that imports, the
main file's forms among them; a program that imports nothing does not pass through it (`Resolver::resolve` returns
its forms as written, and resolves only the module every program gets). The pairs of declarations it can meet: **a
file's own twice**, the main file's or a module's; **a module's and the program's**, never, since a program cannot
declare under a module's full name (Q-M1f.239) and a short name the program declares is its own; **two modules'**,
never, a full name being one module's; **a module reached by two paths**, never, `emit` splicing a module once before
the pass. Keyed on the kind and the name, it read a relation's second declaration, at another count, with other
labels or with another `:why`, as *a different body*, and refused it: against Q-M1f.447, which says each declaration
is a fact of `relation` and none is refused as a duplicate. What it must still fold is a rule or a macro a file writes
twice the same, and refuse one written twice with two bodies. A build that printed what the pass dropped or refused,
run under `ein render program` over every corpus entry on `f281d35a`, printed nothing: no corpus program reaches
either.

**T2.2e.1.2, the fix.** `ein-ir/src/imports.rs`: a `relation` form passes through as written, the fold and the
refusal kept for a rule and a macro under the same `(kind, name)` key. No decision: Q-M1f.447 says it already, and
its *Held by* names the new tests. Tests: `ein-ir/tests/imports_semantics.rs`,
`every_declaration_of_a_relation_comes_and_a_rule_or_a_macro_once`; `ein-cli/tests/declared_counts.rs`, every case
as written and with `(import std.algebra)` first, the relation declared twice gaining a declaration with other labels,
and two tests: `what_reads_a_declaration_reads_each_with_an_import_as_without` and

claims, imported with a list so that `import_invariance.rs` makes its two other forms; `examples/zebra3.2.ein`
declares `the` at both counts it writes, its comment, its corpus note and `examples/README.md` no longer saying a

a relation is not refused), `04-ir-frontend.md` § 8.3, `08-reasoning-in-code/01-static-ir.md`.

**T2.2e.1.3, what the stage found.** E-104 closed by `8d1f89ba`. E-129: what the pass still does to a program's own
