# S2.1.2 — The feedback object: `ein-feedback/1`

**Phase:** [P2.1](README.md) (The kernel as instrumentation — Stage A)
**Estimate:** 4 days
**Depends on:** [S2.1.1](s2.1.1_census.md) — the citations and the two
measurements; the outcome table it writes into `defined_behaviour.md` is this
object's `verdict` block.
**Research plan:** [`EinAf.md` § A3](../EinAf.md#a3-establish-a-stable-machine-interface),
[§ A4](../EinAf.md#a4-separate-semantic-diagnostics-from-presentation).

## Context

The plan's A3 example is a JSON object with a verdict, a model count, a
`search_complete` flag, a query status, and empty arrays for diagnostics,
dependencies and provenance; its A4 is the vocabulary the diagnostics speak.
The engine has most of the *content* — spread over an exit code, a last line
of stderr, `ein-summary/1` and `ein-events/1` — and none of the *object*. This
stage defines the object, versions it, and builds the one producer that
assembles it; every later rung of the ladder ([S2.4.3](../p2.4_loop/s2.4.3_feedback_ladder.md))
is a renderer over it and nothing else reads the engine directly.

The schema, as a sketch — every field after `schema` optional, every array
possibly empty, so that a level that wants nothing renders nothing:

```json
{
  "schema": "ein-feedback/1",
  "source": { "path": "…/t3.ein", "canonical_sha256": "…" },
  "verdict": {
    "outcome": "multiple_models",
    "search_complete": true,
    "k": 4,
    "engine": { "type": "Ambiguity", "exhausted": true, "reason": null }
  },
  "query": { "status": "underdetermined",
             "bindings": [ { "?owner": "Alice" }, { "?owner": "Bob" } ] },
  "diagnostics": [
    { "kind": "undefined_symbol", "message": "<the pinned string, verbatim>",
      "location": { "file": "t3.ein", "line": 12, "col": 3 }, "data": {} }
  ],
  "models": [ [ "(nation-loc Norwegian House-1)", "…" ], [ "…" ] ],
  "unsat_core": [ { "fact": "(right-of Green Ivory)", "source": "The green house is …" } ],
  "dependencies": [], "provenance": [],
  "digests": { "program": "sha256:…", "state": "sha256:…", "models": "sha256:…" },
  "stats": { "enterings_total": 101, "layers_explored": 2, "…": "…" },
  "versions": { "ein": "0.1.0", "events": "ein-events/1", "stdlib_manifest": "sha256:9d1f…" }
}
```

`verdict.outcome` is the six-outcome enum of [S2.1.1](s2.1.1_census.md)
T2.1.1.3 — `invalid | inconsistent | satisfiable_incomplete |
multiple_models | unique | unknown` — and `verdict.engine` is what the engine
actually said, kept beside it so that the derivation is auditable and so that
the day [M1d](../../../docs/history/m1d_satisfiability/README.md) gives the engine a fourth
word the field stays and its source changes. `query.status` is the plan's
second axis — `answered` (every model agrees on the goal bindings),
`underdetermined` (they differ), `absent` (no model binds the goal),
`not_applicable` — because *ambiguous theory, one answer* is a real and
important state the verdict alone cannot express. `diagnostics[].kind` is
A4's list as an enum: `syntax_error, undefined_symbol, type_error,
arity_mismatch, contradiction, unsat_core, ambiguous, unconstrained_variable,
multiple_bindings, missing_dependency, alternative_models, unused_fact,
unreachable_query, dead_relation, resource_limit, search_limit` — and
`other`, carrying the pinned message, for anything the producer cannot
classify. The `message` is **always** the string `defined_behaviour.md` § 1 /
§ 4 pins, verbatim; the kind sits beside it, never instead of it. `digests`
is what [S2.4.1](../p2.4_loop/s2.4.1_state_machine.md) stops on: the
canonical dump's SHA-256 (the program), the sorted fact list's (the
saturated state — [`defined_behaviour.md` § 2.4](../../../docs/kernel/defined_behaviour.md)'s
identity, free with every solve) and the sorted model set's; none is a new
kernel computation.

## Acceptance

- `ein-feedback/1` is written down as a schema with a versioning rule, and
  one producer emits it for every corpus entry's `solve` cell; the objects
  are banked as goldens and `cargo test --workspace` diffs them.
- Every `.ein` under [`examples/broken/`](../../../examples/broken/) yields
  `outcome = invalid` with at least one diagnostic whose `kind ≠ other` and,
  where the source has a location, a `location`.
- The ten [Q-M1d.6](../../../docs/history/m1d_satisfiability/open_questions.md#q-m1d6--may-contradiction-be-said-with-exhausted--false)
  corpus entries yield `outcome = unknown`, `search_complete = false`, and a
  `search_limit` diagnostic; `zebra2-minus-15` yields `multiple_models` with
  `k = 32` under `-e`; `ein-bugs/zebra2-bad.ein` yields `inconsistent` with a
  non-empty `unsat_core` whose entries carry their `:source` quotes.
- No message string changes; no golden under `ein-cli/tests/golden/` that
  existed before the stage is re-blessed, unless T2.1.2.3's location decision
  is taken and says so in its commit.

## Tasks

### Task T2.1.2.1 — The schema and its versioning rule

A page beside [`events.md`](../../../docs/kernel/inference/events.md) —
`docs/kernel/inference/feedback.md` — in its form: the version string, the
fields, the enums, and the rule, which mirrors the events protocol's: an
*added* optional field is the same major; a removed or re-typed field, a new
enum value a consumer must know, or a change to a derivation is `ein-feedback/2`.
The page states that the object is **language-neutral** — it is JSON, the
renderers consume it, the records ([S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md))
store it — and that the `message` strings are not its to define.

### Task T2.1.2.2 — The producer

A function from `(exit code, last line of stderr, ein-summary/1, optionally
ein-events/1)` to the object. The derivation, in order:

```text
exit 1                                     → invalid       (diagnostics from the last line; T2.1.2.3)
summary.type = Aborted                     → unknown,      search_complete = false, + resource_limit
summary.type = Contradiction ∧ (exhausted ∨ core ≠ ∅)
                                           → inconsistent, unsat_core = core with :source quotes
summary.type = Contradiction ∧ ¬exhausted ∧ core = ∅
                                           → unknown,      + search_limit        (Q-M1d.6)
k ≥ 2                                      → multiple_models, search_complete = exhausted
k = 1 ∧ exhausted                          → unique
k = 1 ∧ ¬exhausted                         → unknown       (a model; uniqueness not established)
then: k ≥ 1 ∧ no model binds the goal      → satisfiable_incomplete, query.status = absent
```

The exit code is read once, for `1`, and never for `2` — which the CLI uses
for a usage error *and* a budget abort, by design. `query.status` and
`bindings` come from `solutions[].goal_bindings`; `models` from
`solutions[].facts`, already sorted by the summary so a difference downstream
is semantic; `stats` is the summary's block verbatim; `versions` from
`ein --version`. When the events file is given, `warn` lines become
diagnostics (`kind = other`, `data.category`) — and `events.md`'s payload
tables gain the `warn` row they lack. Where the producer *lives* is
[S2.1.3](s2.1.3_boundary.md)'s: (a) inside `ein-cli` as `--feedback FILE.json`,
additive like `--json-summary`, with the typed errors and `Answer` in hand;
(b) a Rust `einaf` crate linking `ein-ir` / `ein-infer`; (c) a Python module
in `einaf/` reading the four inputs as text. The derivation is the same in
all three and the goldens do not care; what differs is T2.1.2.3.

### Task T2.1.2.3 — Kinds and locations on the typed errors

Three steps, each stopping when the previous one is enough. **First**, parse
diagnostics: `ParseError`'s `file, line, col` are the location and the kind
is `syntax_error` — from the struct in placement (a)/(b), from the pinned
`file:line:col` message in (c). **Second**, load and compile diagnostics:
`KbLoadError`, `LoadError`, `MacroError` and `CompileError` are strings, so
the producer classifies the *message* — the `; `-joined problems, each
matched against the finite set of shapes the corpus's `load-negative` and
`compile-negative` groups exhibit (`undefined_symbol`, `arity_mismatch`,
`type_error`, …) — and anything unmatched is `other`. The corpus is the
test: every negative entry classified, the classification banked. **Third**,
only if a message shape is genuinely ambiguous between two kinds: an optional
`kind` field on `KbLoadError` / `CompileError` in the crates, **with the
message unchanged** — a value beside a string breaks no golden, and the
phase README's acceptance allows exactly this. The location on load errors
is a separate decision: top-level forms carry no `loc`, messages end in
`at None`, and § 1.5 pins that ([Q-M1a.6](../../../docs/history/m1a_rust/open_questions.md#q-m1a6--at-none-in-loader-messages)).
The recommendation is to take Q-M1a.6 up here — the loop is the consumer it
was waiting for, and a diagnostic that names a line is what makes F1
*localising* — at the recorded cost of amending § 1.5 and re-blessing the
corpus goldens with `EIN_BLESS=1` in one commit that says so. The fallback,
if that cost is declined, is `location: null` on load diagnostics and a line
in `feedback.md` saying why.

### Task T2.1.2.4 — Goldens over the corpus

One object per `solve`-shaped cell of [`corpus.toml`](../../../corpus/README.md) —
every `solve` run already gains `--json-summary {out}/summary.json`, so the
producer runs on what the corpus sweep writes and the 97 `solve`, 51
`solve -e`, 7 `solve -n 3` and 7 `solve -m 2` cells are the fixture set for
free. Banked under the producing crate's `tests/golden/` ([Q-M1a.9](../../../docs/history/m1a_rust/open_questions.md#q-m1a9--where-do-goldens-live)),
diffed by `cargo test --workspace`, re-banked by `EIN_BLESS=1`. The
`saturate` and `render` cells produce no object and the manifest says so in
the same way it says which runs a fixture is exercised under.

### Task T2.1.2.5 — The negative fixtures

Every `.ein` under [`examples/broken/`](../../../examples/broken/) — the
three groups, each file with its `.expected` message — yields `invalid` with
a kind and, where the source has one, a location. The `.expected` files stay
what they are: the message is still the normative observable, and the object
is the second one, beside it.

## Notes

The object is deliberately **thin on analysis**: `dependencies` and
`provenance` are empty until [S2.4.3](../p2.4_loop/s2.4.3_feedback_ladder.md)
builds F6 and F7, and `models` is the summary's list, not a difference. A
producer that computed the ladder's content here would make the ladder's
levels properties of the object rather than of the renderer, and the
experiment ([P2.6](../p2.6_ablations/README.md)) needs them to be the
renderer's.
