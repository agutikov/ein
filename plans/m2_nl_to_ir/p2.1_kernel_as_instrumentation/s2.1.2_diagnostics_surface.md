# S2.1.2 — The kernel's diagnostics as values

**Phase:** [P2.1](README.md) (The kernel as instrumentation — Stage A)
**Depends on:** [S2.1.1](s2.1.1_tree_and_outcomes.md), for the caller that shows what the values have to say; the
change itself is to Ein and reads nothing of EinAf.
**Research plan:** [`EinAf.md` § A3](../EinAf.md#a3-establish-a-stable-machine-interface) (*structured errors*),
[§ A4](../EinAf.md#a4-separate-semantic-diagnostics-from-presentation).
**The ruling it carries out:** [Q-M2.9](../open_questions.md#q-m29--does-the-kernel-grow-a-machine-surface-for-diagnostics),
*"(b)"*: the kernel grows the surface, in its own terms. **This is the one stage of the milestone that changes
Ein.**

The old plan had a stage here, *the boundary*, that was to choose the loop's language. The user ruled it, Rust
([Q-M2.7](../open_questions.md#q-m27--what-language-is-the-frontend-written-in)), and nothing of that stage is
left. This stage is the kernel's side of the boundary: what crosses it when a program is not answered.

## Context

**What the kernel says to a program today, and what it says only to a terminal**
([`analysis/audit_p2.1.md`](../analysis/audit_p2.1.md) § 0 has each case run):

| the situation | in the library | on a machine surface of the binary |
|---|---|---|
| a parse error | a value: `ParseError`, every error with its line, column, notes and ranked repairs | **nothing**: lines on stderr, exit 1, no summary; `ein test --json-report` says `outcome: "error"` and no message |
| a load refusal, of [`07-diagnostics.md`](../../../docs/ein/user/04-reference/07-diagnostics.md) § 2 | **a string**: `KbLoadError`, `LoadError`, `MacroError` and `CompileError` each wrap one, several findings joined by `; `, some with a place in front, some with one behind, some ending `at None` | **nothing**, as above |
| a `-T` abort | a value, `SolveError::Deadline` | **nothing**: one line on stderr, exit 2 (a usage error's code), no summary |
| a load's and a run's `note:` lines (a redundant hypothesis declaration, an unchecked claim, a partial run) | strings (`ein_infer::mechanisms`' `notes`, and the read-out's) | stderr only; no key of `ein-summary/2` |
| a flagged program | the detector's finding and its sites | **there**: `monotonicity.warning`, `monotonicity.sites` |
| a core's `:source` texts | a value: a described root holds its core's sources | `region.core` is strings; the `:source` is a row of stdout and of `answer.txt`, and in no JSON key |
| the core under `--single` | none is taken | `null`, by decision: a question that prints no core takes none ([Q-M1f.29](../../../docs/decisions/read-out/Q-M1f.29-a-question-that-prints-no-core-writes-a-dead.md)) |

The same gap is on file as [F23](../../followups/f23_diagnostics_in_eins_words.md)'s **D-18** (*a load diagnostic
reaches stderr and nothing else*) and **L-125** (*the JSON summary carries no line the load or the run prints on
stderr*), which this stage takes up; F23 says so.

**In Ein's terms.** The change is made under Ein's rules, as any change to it: the pages that state the behaviour
change in the same commit; no page, comment, test or name of it mentions a loop, a model or EinAf; its decision
is a file under `docs/decisions/`, under the id `Q-M2.9`, that says what Ein does and why. The reason it can be
stated without EinAf is the one F23 already gives: *a program that calls Ein cannot tell one refusal from another
but by reading text meant for a person.*

### The design, to be confirmed by the stage before it writes code

A default, the coordinator's; T2.1.2.1 holds it against Ein's rules and the code and changes what does not fit.

1. **A refusal is a value with a kind.** The three load-side errors that a program can reach (`KbLoadError`,
   `LoadError`, `MacroError`; no program reaches a `CompileError`, by its own comment) carry a list of findings,
   each with: its **kind**, one a refusal of `07-diagnostics.md` § 2, named after its section; its **place**,
   where the loader has one today; and its **message**, the normative text, byte for byte what is printed now.
   `Display` prints what it prints today, so no `.expected` fixture and no golden moves.
2. **The vocabulary is the page's.** A kind is a section of `07-diagnostics.md` § 1 and § 2; the page gains each
   kind's name beside its section, and a test holds the two lists to each other, the way the page's messages are
   held to the fixtures.
3. **The summary is written wherever the run got far enough to know where to write it**, with one more top-level
   key, `diagnostics`: a list of `{kind, severity, message, place}`, `severity` one of `error`, `warning`,
   `note`. On a refusal and on a `-T` abort the answer's keys are `null`, as every key that does not apply is
   today, and the list says why. A run that answers lists its notes there. Streams and exit codes do not change:
   an artefact option still *changes neither stream nor the exit code*
   ([`05-cli.md`](../../../docs/ein/user/04-reference/05-cli.md)). Whether one more key is `ein-summary/2` still
   or `/3` is decided by how the page defines the schema's number.
4. **`ein test --json-report` carries the diagnostics of a row whose outcome is `error`.**
5. **A core's sources stand beside the core**: a key next to `region.core`, in the core's order, each entry the
   `:source` text of that fact or `null`. `region.core` keeps its shape, which six scripts under `utils/` and the
   corpus sweeps read.
6. **No new option**, so `help_shape.txt` and the option census of
   [`06-config.md`](../../../docs/ein/user/04-reference/06-config.md) do not move.

**What the stage leaves as it is, each for a reason on file:**

- **A message that names no place gets none.** A loader message about a top-level form ends `at None`
  ([Q-M1a.6](../../../docs/decisions/diagnostics/Q-M1a.6-a-loader-message-about-a-top-level-form-names-no.md));
  giving it one moves a third of the load fixtures and is F23's D-2 and D-22. Here its `place` is `null`.
- **`--single` takes no core** (Q-M1f.29): a caller that wants one asks for a description.
- **No exit code changes** ([Q-M1e2.33](../../../docs/decisions/cli/Q-M1e2.33-every-answer-exits-0.md)): a `-T`
  abort still exits 2. What tells it from a usage error is now the summary's diagnostic, not the first word of a
  line.
- **No analysis is added**: an unused fact, a relation no rule reads, a query nothing reaches are not diagnostics
  Ein has, and are recorded in [the evaluation](../ein_evaluation.md) (E-28), not built.

## Tasks

- **T2.1.2.1 — The design against the rules.** Read the design above against: `07-diagnostics.md` (every section
  of § 1 and § 2 gets a kind, or the stage says why one does not); [`08-read-out.md`](../../../docs/ein/user/04-reference/08-read-out.md)
  § 11 (how a key is added to the summary, and what the schema's number means);
  [`10-answer-dump.md`](../../../docs/ein/user/04-reference/10-answer-dump.md) (`answer.json` is the summary byte
  for byte); `05-cli.md` § 1 and § 3; [Q-M1a.13](../../../docs/decisions/cli/Q-M1a.13-the-clis-behaviour-is-fixed-and-its-helps-layout.md);
  the `.einb` container, which stores a program's text and prints its load's notes. Write the design down as the
  draft of the decision file. **Anything in it that is the user's to choose** (a schema number that breaks a
  reader; a kind's name that is a new word of Ein's) is shown before the code.
- **T2.1.2.2 — Findings in the library.** The three load-side errors carry their findings as values; every site
  that builds one names its kind. `Display` is unchanged. The worked example of
  [`04-api.md`](../../../docs/ein/ein.rs/04-api.md) gains a refusal read by its kind (edit the test
  [`embedding.rs`](../../../ein.rs/crates/ein-cli/tests/embedding.rs), run it, paste).
- **T2.1.2.3 — Notes as values.** The notes a load and a run print (`mechanisms`' and the read-out's) each get a
  kind; what the CLI prints is built from the values and is the text it is today.
- **T2.1.2.4 — The surfaces.** The summary's `diagnostics` key and the cases it is now written in; the test
  report's; the core's sources. `08-read-out.md`, `07-diagnostics.md`, `05-cli.md` and `10-answer-dump.md` in the
  same commit.
- **T2.1.2.5 — The tests, in Ein.** Every `.ein` under `examples/broken/` that is refused yields at least one
  finding, each of a kind the page names, with the message its `.expected` holds; the kinds of the page and of
  the code are one list; for every corpus program the summary's `diagnostics` are the lines stderr printed, kind
  by kind; a `-T 0` run writes a summary whose one diagnostic is the deadline's. `summary_properties.rs` holds the
  new key's shape on every arm.
- **T2.1.2.6 — The decision and the followup.** `docs/decisions/<subject>/Q-M2.9-….md`, in Ein's words: what
  holds, why, held by which tests. F23's rows D-18 and L-125 are closed there with the commit that lands this.
- **T2.1.2.7 — EinAf reads it.** S2.1.1's outcome function reads *invalid* and *not decided* off the values, and
  no longer off an error's text. This task is EinAf's and is a commit of its own, after Ein's.
- **T2.1.2.8 — The evaluation.** What the change showed of Ein: refusals whose kind was not clear from the code,
  messages that could not be placed, any case where the page and the code disagreed.

## Risks

- **Kinds invite renaming the refusals.** The stage names what is there. A refusal whose section covers two
  different mistakes gets one kind and an entry in the evaluation, not a new section.
- **A summary on a refusal is the first artefact a refused program writes**, and something may count on its
  absence (a sweep that reads *no file* as *refused*). T2.1.2.1 looks for such a reader before the behaviour
  changes.
- **The notes are built in two crates and printed in a third.** If making them values means moving where they are
  made, the stage stops at the ones a load makes (D-18) and records the run's (L-125) as left, with what it would
  take.
- **Scope.** F23 holds other rows on the same paths (D-1, D-3, D-20). They are not this stage's; a row it happens
  to close is said so in F23, and none is taken up for its own sake.
