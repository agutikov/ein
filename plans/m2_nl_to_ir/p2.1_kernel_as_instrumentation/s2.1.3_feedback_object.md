**Depends on:** [S2.1.1](s2.1.1_tree_and_outcomes.md), the package and the outcome function;
[S2.1.2](s2.1.2_diagnostics_surface.md), the kernel's diagnostics as values.
**Research plan:** [`EinAf.md` § A3](../EinAf.md#a3-establish-a-stable-machine-interface),

## Context

A3's example is one object with a verdict, a model count, a `search_complete` flag, a query status, and lists of
diagnostics, dependencies and provenance. In August the engine had most of that content spread over an exit code,
a line of stderr and two JSON schemas, and this stage was to derive the object from them and have `ein-cli` write
it as `ein-feedback/1`.

Today the content is the engine's own ([`analysis/audit_p2.1.md`](../analysis/audit_p2.1.md) § B, S2.1.2's rows:
*search complete* is `region.exhausted`; the count is two counts; *incomplete* is a state that owes; the query's
axis is its classes; the models are states; the core has a status and the rules that refuted), EinAf links the
library and has it all as values ([Q-M2.7](../open_questions.md#q-m27--what-language-is-the-frontend-written-in)),
and the kernel does not write the object: it is **EinAf's**
([Q-M2.9](../open_questions.md#q-m29--does-the-kernel-grow-a-machine-surface-for-diagnostics): *the feedback
object stays the harness's*).

So the stage does not derive anything. It defines **one value that holds what the kernel found of one program
under one question**, for three readers that must not each read the kernel their own way:

- **the feedback ladder** ([S2.4.3](../p2.4_loop/s2.4.3_feedback_ladder.md)): each of F0 to F8 is a renderer of
  this object into a prompt, and a level shows a part of it and nothing the object does not hold;
- **the tool** ([S2.4.6](../p2.4_loop/s2.4.6_ein_as_a_tool.md)): what a call returns to the model is one of those
  renderings;
- **the record** ([S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md)): every run of the kernel is stored as
  this object, so that a table can be recomputed and a level re-rendered without running Ein again.

**What it holds**, as a sketch: every part is absent where it does not apply, so that a level that shows nothing
renders nothing.

| part | what | from |
|---|---|---|
| `schema` | `einaf-feedback/1` | EinAf |
| `program` | the digest of the program's canonical dump | `ein_ir::dump_canonical`, which the library has and no command prints |
| `kernel` | Ein's version, the events protocol, the library's manifest SHA; the commit | the first three as `ein --version` prints them; the commit from git, given by the record ([Q-M2.1](../open_questions.md#q-m21--when-is-the-kernel-frozen)) |
| `asked` | the question: a description, `--single`, `--maximal`, `-n N`, `--no-search`; the budget | the caller |
| `outcome` | one of [the seven](../README.md#the-outcomes), with the reading it was taken under | S2.1.1's function |
| `readings` | each reading of *one answer* the runs behind this object established: `--single`'s word over all of R, over the maximal line; a description's two counts | the answer; a reading not asked is absent, never guessed ([Q-M2.10](../open_questions.md#q-m210--what-does-ein-certifies-a-unique-model-mean-on-r)) |
| `diagnostics` | each with its kind, severity, message and place: a refusal's findings, an abort, a run's notes | S2.1.2's values |
| `flagged` | the sites of the static check's finding | the detector |
| `queries` | a query: its classes, their rows, whether they agree; its `:goal-text` and the line each row fills; the outcome of its `:expect` | the read-out's values: a class holds its rows and each row rendered through the query's `:goal-text` ([`04-api.md`](../../../docs/ein/ein.rs/04-api.md)), which the summary has no key for. A value's own text is [S2.2.5](../p2.2_formalizer/s2.2.5_from_text.md)'s formatters', applied by a renderer and not stored here |
| `states` | the states listed: each one's facts over the candidates' relations, and a digest | the answer |
| `owed` | what root, or the frontier, still owes, in the kernel's sentences | the answer |
| `core` | the core's facts, each with its `:source`; its status; the rules that refuted | the answer, under a description only |
| `work` | saturations, facts, layers; the wall clock | the answer's `work`; the clock is EinAf's own measurement, no surface of Ein carrying one |

**Two parts are left open on purpose**, as lists the object may hold and this stage does not fill: *dependencies*
(F6) and *provenance* (F7). What the engine can supply for each is partial ([the analysis](../analysis/README.md#p24--the-loop-audit),
the ladder's table), and what a level should show of it is the ladder's design. S2.4.3 adds them, to this type.

**One object, one question.** The loop may ask a program two questions (`--single` to decide, then a description
for a core): that is two objects, each saying what it was asked. Which questions the loop asks is
[S2.4.1](../p2.4_loop/s2.4.1_state_machine.md)'s.

**The kernel runs under a bound of EinAf's own.** Nothing in a solve stops a saturation that has no fixpoint: a
rule that nests its conclusion one deeper than its premise runs until it is killed, under `-T` and under a
budget alike ([`probes/p2.7/grow.ein`](../analysis/probes/p2.7/grow.ein); the engine's word for it is
[M1g](../../m1g_logic/README.md)'s to give, in its stage on a saturation that does not stop). The programs EinAf
runs are a model's, and one such program must not take EinAf with it. So every call of the kernel is made **in a
worker process**, the `einaf` binary in a mode of its own that links the crates, builds the object and writes it
back serialised; the parent holds the worker to a wall clock and to a memory size and stops it at either. A call
that is stopped is *not decided*, with a diagnostic of EinAf's own kind that says which bound. That is why the
object is serialisable before any record needs it.

## Tasks

- **T2.1.3.1 — The type.** `einaf::kernel::Feedback` and its parts, every part optional, built by one function
  from a load's result and an answer's values. No part is read back from text the kernel printed.
- **T2.1.3.2 — The serialisation.** JSON, versioned `einaf-feedback/1`, with the rule the engine's summary keeps
  (a key is present and `null` where it does not apply, or absent: the stage picks one and says so), and a reader
  that takes back what was written. A page of `docs/einaf/` states the object key by key.
- **T2.1.3.2b — The bounded call.** The worker's mode of the `einaf` binary and the parent's side of it: one
  program and one question in, one object out; the two bounds, each a setting that the record carries
  ([S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md)); a stopped worker read as *not decided*. Nothing else in
  EinAf calls the engine's crates. One call is one load and the questions asked of it, each of a copy, and one
  object an answer ([S2.4.1](../p2.4_loop/s2.4.1_state_machine.md) states what the loop needs of it; whether a
  worker is kept alive across an episode is its to add). **A first guard that depends on no machine**: the
  library's saturator takes a cap on its steps, which no route passes on; whether root can be saturated under a
  cap before any question, and a route then finds it as it expects, is checked first and taken if it holds.
- **T2.1.3.3 — The digests.** A program's is its canonical dump's SHA-256. A state's is over its sorted fact list,
  taken from the facts the library gives. If the library gives a state's facts only over the candidates'
  relations, the digest is of that list and says so; what a whole state would need is an entry of the evaluation
  (E-25).
- **T2.1.3.4 — Held over the corpus.** For every corpus program that is not `slow`, under the questions its
  entry declares: an object is built; it survives a round trip through JSON; and **what it says agrees with what
  the binary says of the same run**: its outcome with the summary's `verdict`, `region.empty`, `region.stopped`
  and `monotonicity`, its states and classes with the summary's, its diagnostics with the summary's
  (`ein-summary/2` as S2.1.2 leaves it). The library and the binary are two routes to one answer, and the test is
  that they agree; the binary is the one the gate built, by `$EIN_BIN`. Properties are asserted, no value of an
  answer is banked, and of a flagged program only that it is flagged.
- **T2.1.3.5 — The negative fixtures.** Every refused program under `examples/broken/` yields an object whose
  outcome is *invalid* and whose diagnostics carry the kinds S2.1.2 gave. The program whose saturation has no
  fixpoint yields *not decided* within the worker's bound, in a test of EinAf's own.
- **T2.1.3.6 — The evaluation.** What building the object from the library took: what had to be rebuilt by EinAf
  that the kernel knew and did not hand over (a state's whole fact list; a time; a bound on its own run), each an
  entry or a line on an entry that is there.

## Acceptance

- T2.1.3.4 and T2.1.3.5 hold, in EinAf's step of the gate.
- The object is stated key by key under `docs/einaf/`.
- Nothing outside `einaf::kernel` calls the engine's crates, and `einaf::kernel` calls them only in its worker:
  the formalizer, the loop, the tool and the record, when they are written, take a `Feedback`. What the ladder
  and the faithfulness judge later read of the kernel (a dependency graph, a derivation's chain, a comparison of
  two programs' answers) is added to this module by their stages, not called from theirs.

## Risks

- **Fixing the object before the ladder says what matters.** A3's list is the plan's guess and
  [P2.6](../p2.6_ablations/README.md) is the experiment. Every part is optional, the two open parts are named, and
  the schema's number moves when a part changes its meaning.
- **The object grows into a copy of the summary.** A description of an under-determined program is megabytes
  ([the analysis](../analysis/README.md#p25-and-p26--records-baselines-metrics-ablations-audit)). The object holds
  what a renderer or a metric reads; the states listed are bounded by the question asked, and a record that wants
  the whole answer stores the kernel's own dump beside the object.
- **Two routes that agree today can drift.** T2.1.3.4 is the guard, and it is why the test compares with the
  binary instead of with a golden of EinAf's own making.
