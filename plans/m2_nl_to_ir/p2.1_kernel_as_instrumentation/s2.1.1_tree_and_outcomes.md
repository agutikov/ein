## Context

This stage was *the census*: Stage A re-taken against the engine with `file:line`, two measurements, and the six
outcomes written into `defined_behaviour.md`. [The analysis](../analysis/README.md) is that census (its
[audit of P2.1](../analysis/audit_p2.1.md) § 0 is the fact base), both measurements are answered (an unknown
keyword on a fact is a parse error, [Q-M1e2.28](../../../docs/decisions/language/Q-M1e2.28-each-form-takes-a-closed-list-of-keywords.md);
the rules no program activated are a gate test over the library, by `fire` and `owe`), and the page is gone. What
is left of it is one list. What is new is that **nothing of EinAf exists**, and the user has ruled where it lives
and in what language.

So the stage creates the tree, wires it into the process, and writes into it the first thing EinAf has to know of
the kernel: which outcome a run is.

**The seven outcomes** are [the frame's](../README.md#the-outcomes). What each is read from, in the library's
values and, for a reader of the binary, in `ein-summary/2`'s keys (the audit's § 0 has each run):

| outcome | read from | not to be confused with |
|---|---|---|
| **invalid** | the load returns an error: a parse error, or a refusal of [`07-diagnostics.md`](../../../docs/ein/user/04-reference/07-diagnostics.md) § 2. No answer exists and no summary is written today | exit 1, which is also a claim the run refuted, with a summary ([Q-M1e2.33](../../../docs/decisions/cli/Q-M1e2.33-every-answer-exits-0.md)) |
| **flagged** | the static check's finding, read before any answer: `monotonicity.warning` and its sites | any of the five below: an answer is printed and nothing is claimed of it ([Q-M1f.564](../../../docs/decisions/answer/Q-M1f.564-a-non-monotone-program-loads-with-a-warning.md)) |
| **not decided** | the run stopped first: `region.exhausted false` with `region.stopped.why` `budget` or `limit`, `verdict.word null` under `--single`; or the deadline error of a `-T` run, which writes no summary today | `region.stopped.why "asked"`, which is a run that did what it was asked (`-n N`, `Ambiguity` after two states) |
| **inconsistent** | R is empty and its kind is `dead`: `Contradiction` under `--single`; under a description `region.empty "dead"` with `core`, `core_status`, `refuted_by` | an empty R whose kind is `owing` |
| **incomplete** | a state owes: `Open` under `--single`; `region.empty "owing"` or `region.root "owing"`, `root.owed`, `region.frontier` | a query whose class has no row, which is the query's axis |
| **several** | `Ambiguity`, with two states that differ | — |
| **one** | `Solution` | — |

Two things the table cannot settle and the function must carry instead of hiding:

- ***one* and *several* have two readings.** R holds partial commitments where a program states no obligation, so
  a program can be `Ambiguity` over all of R and `Solution` over its maximal line
  ([`06-solution-semantics.md`](../../../docs/ein/reasoning/02-kb-evolution/06-solution-semantics.md)). Which
  reading *certifies* is [Q-M2.10](../open_questions.md#q-m210--what-does-ein-certifies-a-unique-model-mean-on-r),
  the user's after experiments. The function returns the outcome **with the reading it was taken under**, and a
  caller that wants both asks both.
- **The outcome is of a question.** A bare solve has no verdict word; `--no-search` states no R at all. The
  function is defined for each question it accepts, and says which it was asked.

Beside the outcome, and not part of it: each query's own axis (its classes, their rows, whether they agree), and
whether a claim the program states held.

## Tasks

- **T2.1.1.1 — The package.** `einaf/Cargo.toml`: one package, `einaf`, a library and a binary of the same name,
  with `ein-core`, `ein-ir`, `ein-infer` and `ein-render` as path dependencies into `ein.rs/crates/`, and a
  `[workspace]` table of its own so that it is no member of the engine's workspace and `cargo test --workspace`
  there never sees it. Its `target/` is ignored by git. The first module, `einaf::kernel`, loads a program from
  text and asks it a question through the crates, as the worked example of
  [`04-api.md`](../../../docs/ein/ein.rs/04-api.md) does
  ([`embedding.rs`](../../../ein.rs/crates/ein-cli/tests/embedding.rs)). The binary has one subcommand for now,
  which prints a program's outcome. **Check first** that the four crates build as dependencies of a package
  outside their workspace (inherited manifest fields, features, the generated parser's build script); what that
  costs is an entry of the evaluation.
- **T2.1.1.2 — The process is told.** In one commit with the package, so that no check reads the new tree by a
  rule made for another:
  - `./build.sh` builds EinAf after the engine, and has a switch for it alone;
  - `./run_tests.sh` and the per-commit CI workflow get one step, EinAf's tests, after the engine's;
    `utils/check_gate_steps.py` holds the two lists to each other as it does the rest;
  - `utils/check_release_voice.py`'s `NOT_PROJECT` names `einaf/` and `docs/einaf/`; the other checks that walk
    the tree (`utils/doc_audit.py`'s link check, which should read EinAf's pages; `utils/check_doc_blocks.py`,
    whose rules are `docs/ein/`'s) are read and each is left reading, or not reading, the new trees on purpose;
  - `AGENTS.md`: the two trees under *Where things live*, EinAf's commands under *Running the gate*, and the
    sentences that say neither tree exists yet; the root `README.md`'s sentence that neither holds a file.
- **T2.1.1.3 — EinAf's first pages.** `docs/einaf/README.md`: what EinAf is, what it depends on, how it is built
  and tested. With it the stage **proposes what EinAf's pages hold themselves to** (the current state, as Ein's
  do; where a dated measurement lives, which is a record under `einaf/experiments/` and not a page; that the
  research plan's labels F0 to F8, B0 to B6 and G1 to G9 are EinAf's vocabulary) and records the proposal in
  [Q-M2.8](../open_questions.md#q-m28--where-does-einaf-live)'s entry for the user to correct.
- **T2.1.1.4 — The outcomes, as a function and as a page.** `einaf::kernel::Outcome`, the seven, and the function
  that reads one off a load's result and an answer, with the question and the reading it was taken under. A page
  under `docs/einaf/` states the table above as it is built: each outcome, what it is read from, and the test of
  EinAf's that holds the reading.
- **T2.1.1.5 — A2's invariants, as a list.** The same page, or one beside it: each of
  [A2](../EinAf.md#a2-define-kernel-invariants)'s six invariants with the test of Ein's that holds it or the
  decision that says otherwise (the audit's § B, S2.1.1's rows, names each), and the three sketches of the old
  plan that are false by decision. A list of links: EinAf adds no test to Ein and restates none.
- **T2.1.1.6 — The corpus as the test.** EinAf's function over every corpus entry that is not `slow`: each program
  has exactly one outcome; a `parse-negative` or `load-negative` entry is *invalid* (the one fixture under
  `examples/broken/` that solves is a `positive` entry and is not); a program the engine's own check flags is
  *flagged* and no other; where a program states an `:expect`, the outcome does not contradict it. No value of a
  flagged program's answer is asserted. Whether the corpus is read through `ein-corpus` or from
  `corpus/corpus.toml` is the stage's choice (the phase's third risk).
- **T2.1.1.7 — The evaluation.** What the stage found of Ein as a library goes into
  [the evaluation of Ein](../ein_evaluation.md): what linking the crates from outside took; what of an answer was
  a value and what had to be rebuilt from text; any outcome the function could not tell apart.

## Acceptance

- `cargo test --manifest-path einaf/Cargo.toml` passes, as a step of `./run_tests.sh` and of CI; the whole gate is
  green on the stage's last commit.
- `grep -ri einaf` over `ein.rs/crates`, `docs/ein`, `docs/decisions`, `stdlib`, `examples`, `tests` and `corpus`
  finds nothing.
- The release-voice check and the link check pass with the new trees in place, each for the reason T2.1.1.2
  recorded.
- T2.1.1.6's test holds over the corpus.
- `docs/einaf/` states the seven outcomes and the six invariants, every link resolving.

## Risks

- **A package outside the workspace builds the crates a second time**, into a `target/` of its own, and the gate
  pays for it on every run. If that is too much, EinAf's step shares the engine's target directory; it does not
  join the workspace.
- **The function invites a single verdict where the kernel has none.** A bare solve of an under-determined program
  can stop at the default budget after finding every state (the audit's § 0, the ambiguous Zebra variant): the
  function says *not decided* of that question and does not guess from the states listed.
- **Writing the process's rules for a tree before the tree has content** fixes them early. They are few, each is
  one line of a script, and T2.1.1.3 puts the proposal before the user.
