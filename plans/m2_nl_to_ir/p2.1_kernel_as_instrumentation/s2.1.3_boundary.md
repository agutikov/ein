# S2.1.3 — The boundary: Q25 decided

**Phase:** [P2.1](README.md) (The kernel as instrumentation — Stage A)
**Estimate:** 2 days
**Depends on:** [S2.1.2](s2.1.2_feedback_object.md) — the decision is taken
*after* the protocol exists, because the protocol is most of the decision.
**Research plan:** [`EinAf.md` § A3](../EinAf.md#a3-establish-a-stable-machine-interface);
the question itself is [Q25](../open_questions.md#q25--what-language-is-the-frontend-written-in).

## Context

[Q25](../open_questions.md#q25--what-language-is-the-frontend-written-in)
has two live options and, since 2026-08-23, a smaller trade than the one it
was raised with. **Rust** links `ein-ir` / `ein-infer` ([`docs/api/rust.md`](../../../docs/api/rust.md))
and gets the engine's values with no boundary; **Python** drives the `ein`
binary and gets the ecosystem — and, the entry said, *strings* for
diagnostics, which the CLI could not grow out of without breaking
[`defined_behaviour.md`](../../../docs/kernel/defined_behaviour.md) § 1 / § 4.

Two things [S2.1.2](s2.1.2_feedback_object.md) changed. The research plan's
A3 — *human-readable CLI output should not be used by the experimental
system* — made a versioned structured object mandatory **in either language**,
so `ein-feedback/1` is the boundary whichever side writes the loop; the
"strings" cost of the Python column is paid once, by the producer, and never
by a renderer. And the census ([S2.1.1](s2.1.1_census.md)) found the "values"
advantage of the Rust column to be one struct: `ParseError` has fields;
`KbLoadError`, `LoadError`, `MacroError` and `CompileError` are `String`
newtypes, so a Rust loop would be classifying message text exactly as a
Python one would, until S2.1.2 T2.1.2.3 gives those errors a kind. What is
left to decide is therefore not *how the loop reaches the engine* — through
the object — but **who writes the rest**: the client, the passes, the nine
renderers, F6's static analysis, the generators and their NL realisers, the
harness, the metrics, the plots.

## Acceptance

- The verdict is written beside [Q25](../open_questions.md#q25--what-language-is-the-frontend-written-in),
  dated, with the measurement and the two-sentence argument it rests on.
- The top-level directory for the loop is fixed, with its three commands,
  and every path in the P2.2 – P2.5 stage files that said *in Q25's language*
  is corrected once, in this stage's commit.
- The three trip-wires of [Q-M1a.23](../../../docs/history/m1a_rust/open_questions.md#q-m1a23--when-does-the-engine-need-a-python-binding)
  are re-checked against the decision and the result recorded under them,
  dated — one status line, not a rewrite of a history page.

## Tasks

### Task T2.1.3.1 — What is in the loop's language, and what is not

Language-neutral, whatever is decided: `grammars/` (GBNF text, consumed by
`llama-server`), the prompts (text, hashed), the experiment records (JSON and
JSONL directories, [S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md)),
`ein-feedback/1` itself, the benchmark's instances (text + `.ein` + metadata),
the Compose file. In the loop's language: the HTTP client
([S2.2.2](../p2.2_formalizer/s2.2.2_llama_server_and_client.md)), the four
passes and their prompt assembly ([S2.2.4](../p2.2_formalizer/s2.2.4_passes.md)),
`einaf from-text` ([S2.2.5](../p2.2_formalizer/s2.2.5_from_text.md)), the
renderers F0–F8 and F4's model difference ([S2.4.3](../p2.4_loop/s2.4.3_feedback_ladder.md)),
F6's relation-dependency analysis, the state machine and its transcript
([S2.4.1](../p2.4_loop/s2.4.1_state_machine.md)), the faithfulness judge,
the generators and realisers ([S2.3.2](../p2.3_benchmark/s2.3.2_generators.md)),
the external adapters, the harness and the metrics
([P2.5](../p2.5_harness/README.md)), the plots. Written as a table with one
column per option and the line count each side would expect, so that the
decision is about the long column and not the short one.

### Task T2.1.3.2 — The measurement that cannot decide it

[Q-M1a.23](../../../docs/history/m1a_rust/open_questions.md#q-m1a23--when-does-the-engine-need-a-python-binding)
took it on 2026-08-21: `ein --help` **1.68 ms** — the process floor — and
`ein solve examples/zebra2.ein` 11 ms, cold. One loop iteration is one LLM
call, which on a local 30B model at tens of tokens per second for a
program of a few hundred tokens is **seconds**; the solve is under one
percent of it and the process start under a tenth of that. A benchmark sweep
of a few thousand instances at five iterations is tens of thousands of
processes and under a minute of startup in total. Re-taken here on the seed
set's first runs so the number is this milestone's, and then set aside:
**startup cannot decide Q25**, and the entry's first trip-wire does not fire.

### Task T2.1.3.3 — The criteria that can

Three, in the order they weigh:

1. **Who writes the long column fastest.** T2.1.3.1's table is dominated by
   generators, realisers, adapters, metrics and plots — text and tables, the
   work `utils/` already does in Python, driving the binary by `$EIN_BIN`
   ([`utils/README.md`](../../../utils/README.md)); the repo's measurement
   discipline was built that way and has the precedent.
2. **What reads engine values.** The producer of the object (the typed
   `ParseError`, the `Answer`), F6's analysis (the parsed program — `ein-ir`
   holds the `Ast` as values; a Python loop would re-parse with a second
   parser, which is drift, or need a dump the CLI does not have), and the
   GBNF generator's check against the parser (the echo round-trip runs `ein`
   on the output — process-shaped either way).
3. **What the experiment needs to be rewritable.** Prompts, renderers and
   metrics change per experiment id; the engine does not. A side that can be
   rewritten without touching `ein.rs/` is the side the ablations live on.

### Task T2.1.3.4 — The verdict, and the directory

**Recommendation: Python drives the binary through `ein-feedback/1`; the
producer of the object lives in Rust, inside `ein-cli`, as `--feedback
FILE.json` — additive, like `--json-summary` — and F6's dependency block is
computed there too when [S2.4.3](../p2.4_loop/s2.4.3_feedback_ladder.md)
builds it.** The one thing that reads engine values is then in the engine's
language and ships with the engine, and everything that changes per
experiment — prompts, renderers, generators, metrics — is in the harness's
language, where `utils/` already set the pattern and where a rewrite touches
no crate. Fixed by the verdict: `einaf/` at the repository root, a Python
package with `python -m einaf run | evaluate | report` (names
[S2.5.1](../p2.5_harness/s2.5.1_experiment_record.md) may still adjust),
`$EIN_BIN` / `--bin` defaulting to `ein.rs/target/release/ein` as every
`utils/` script does; `grammars/` at the root; `packaging/compose/llm.yml`
for the server; `experiments/` for the records. The alternative, a Rust
`einaf` crate, is recorded beside the verdict with the one condition that
would reverse it — a renderer or judge that needs the KB as values on every
iteration rather than the object — so that the reversal is a trip-wire and
not a re-argument. Written beside [Q25](../open_questions.md#q25--what-language-is-the-frontend-written-in)
in the form the entry already has.

### Task T2.1.3.5 — Q-M1a.23's trip-wires, re-checked

A Python loop that drives the binary **is not a Python binding**: no PyO3,
no `pip install ein`, nothing `docs/api/`'s five Python pages describe — the
object crosses the boundary, not the KB. Against the three trip-wires: (1) a
per-item loop where startup dominates — no, T2.1.3.2; (2) state that must
persist across items — no, every iteration loads a fresh program, and
`.einb` exists if a saturated KB ever needs to be reopened; (3) a Python
consumer the project does not control — `einaf/` is the project's; the
paper's artifact package ([M5](../../m5_presentation/README.md), [P2.10](../p2.10_result_artifact_demo/README.md))
remains the one likely to fire it and remains a milestone away. One dated
line under the entry's trip-wires recording that they were checked on this
decision and that none fires.

## Notes

The recommendation keeps a door open that the old plan had closed the other
way: if [S2.4.4](../p2.4_loop/s2.4.4_faithfulness.md)'s judge or a renderer
turns out to want the saturated KB on every iteration — to ask *which facts
of the model trace to which source sentence* — that is the condition named
in T2.1.3.4, and the answer is a second additive flag on `ein-cli` before it
is a Rust loop.
