# Ein Research Plan — Through Level D

## 1. Research objective

The project should evolve from a symbolic reasoning engine into a **reproducible research system for iterative neuro-symbolic autoformalization**.

The central research question is:

> **Can structured feedback from a symbolic reasoner improve an LLM's ability to construct correct formal theories from natural-language problem statements?**

The stronger version is:

> **Which forms of symbolic feedback are most useful for detecting and repairing incorrect autoformalizations?**

The target system is:

```text
Natural-language problem
        │
        ▼
Semantic interpretation / theory synthesis
        │
        ▼
Candidate Ein program
        │
        ▼
┌─────────────────────────────┐
│         Ein kernel          │
│                             │
│ parsing / typing            │
│ saturation                  │
│ model search                │
│ constraint checking         │
│ contradiction detection     │
│ provenance                  │
│ dependency analysis         │
└─────────────┬───────────────┘
              │
              ▼
       symbolic feedback
              │
              ▼
       theory repair
              │
              └───────────────┐
                              │
                    candidate Ein program
                              │
                              ▼
                         Ein kernel
                              │
                              ...
                              ▼
                    verified final answer
```

The research artifact is not merely this architecture. Level D requires:

**system + formal description + benchmark + baselines + ablations + quantitative results + failure analysis + reproducibility + technical paper.**

# Stage A — Establish the symbolic kernel as the experimental foundation

The existing engine becomes the trusted symbolic component of the experiment.

## A1. Freeze the semantic boundary of Ein

Define precisely what an Ein program means.

Document the semantics of:

* objects;
* types/classes;
* relations of different arities;
* facts;
* rules;
* hypothesis rules;
* constraints;
* queries;
* saturation;
* model completion;
* contradiction;
* ambiguity;
* uniqueness;
* provenance;
* no-goods;
* search.

The distinction between these outcomes must be mathematically and operationally explicit:

```text
invalid program
valid but inconsistent theory
valid satisfiable incomplete theory
multiple complete models
unique complete model
resource-limit / unknown
```

`unknown` must never silently become `false`, `ambiguous`, or `contradiction`.

## A2. Define kernel invariants

Examples:

```text
Every emitted fact is justified by:
    input fact
    OR
    rule + antecedent facts

Every contradiction has a recorded derivation.

Every reported solution satisfies all active constraints.

Unique means:
    exactly one complete model was found
    AND search space was exhausted.

Ambiguous means:
    at least two distinct satisfying models exist.

Unsat means:
    exhaustive search established zero satisfying models.
```

These become testable invariants.

## A3. Establish a stable machine interface

Human-readable CLI output should not be used by the experimental system.

Provide structured input/output, for example:

```json
{
  "verdict": "ambiguous",
  "models_found": 4,
  "search_complete": true,
  "query": {
    "status": "underdetermined"
  },
  "diagnostics": [],
  "dependencies": [],
  "provenance": [],
  "stats": {}
}
```

Errors should also be structured:

```json
{
  "verdict": "invalid",
  "diagnostics": [
    {
      "kind": "arity_mismatch",
      "relation": "owns",
      "expected": 2,
      "actual": 3,
      "location": "..."
    }
  ]
}
```

The protocol should be versioned.

## A4. Separate semantic diagnostics from presentation

Internally define a diagnostic vocabulary.

For example:

```text
syntax_error
undefined_symbol
type_error
arity_mismatch

contradiction
unsat_core

ambiguous
unconstrained_variable
multiple_bindings
missing_dependency
alternative_models

unused_fact
unreachable_query
dead_relation

resource_limit
search_limit
```

The LLM interface consumes these structured objects rather than arbitrary prose generated by Ein.

## A5. Build kernel validation suites

Maintain separate suites for:

```text
parser correctness
type-system correctness
saturation correctness
constraint correctness
search correctness
provenance correctness
unsat-core correctness
model-count correctness
determinism
performance regression
```

Include deliberately pathological cases.

At the end of Stage A, the symbolic component should be treated as **experimental instrumentation**, not an evolving prototype.

# Stage B — Define autoformalization as an explicit task

The neural component should initially do only one difficult thing:

> Convert a natural-language problem into an executable Ein theory.

Avoid mixing solving and formalization.

## B1. Define the formalization contract

Input:

```text
problem statement
```

Output:

```text
Ein program
```

Optionally require an explicit decomposition:

```text
entities
relations
constraints
query
Ein program
```

But evaluate whether this intermediate representation helps rather than assuming that it does.

## B2. Separate source facts from generated knowledge

An important invariant:

> The formalizer may restructure information from the source but must not invent problem-specific facts.

Distinguish:

```text
source-derived facts
generic theory / stdlib
generated auxiliary relations
generated inference rules
generated assumptions
```

This later allows hallucination analysis.

## B3. Define the model's available knowledge

Explicitly control what the formalizer receives:

```text
Ein language specification
stdlib catalogue
few-shot examples
problem statement
previous diagnostics, if iterative
```

Do not allow hidden benchmark solutions into prompts.

## B4. Establish prompt versioning

Every experiment must record:

```text
model
model version
system prompt hash
formalization prompt hash
Ein specification version
stdlib version
generation parameters
```

Prompt changes are experimental changes.

# Stage C — Construct a heterogeneous benchmark

The benchmark should test **theory construction**, not merely whether Ein can solve Zebra-like puzzles.

## C1. Start with several reasoning families

Good initial families include:

### Logical deduction

```text
A is older than B.
B is older than C.
Who is youngest?
```

### Ordering

```text
Alice arrived before Bob.
Carol arrived after Bob.
...
```

### Spatial reasoning

```text
A is left of B.
C is above A.
...
```

### Object tracking

```text
The key starts in box A.
A and B are swapped.
Then B and C are swapped.
Where is the key?
```

### Attribute matching

Zebra-like:

```text
person ↔ house ↔ animal ↔ colour
```

### Set/category reasoning

```text
Every A is B.
No B is C.
x is A.
Can x be C?
```

### Graph reasoning

```text
reachable
adjacent
connected
ancestor
dependency
```

### Temporal reasoning

```text
before
after
overlap
interval containment
```

Later expand into more difficult compositional combinations.

## C2. Use both external and controlled synthetic tasks

External benchmarks provide ecological validity.

Synthetic generators provide:

* arbitrary dataset size;
* exact ground truth;
* exact formal theory;
* controlled difficulty;
* controlled ambiguity;
* controlled contradictions;
* systematic perturbations.

Both are necessary.

## C3. Generate deliberately ambiguous problems

Do not benchmark only tasks with unique answers.

Construct:

```text
unique
ambiguous
unsatisfiable
```

instances.

This tests whether the system distinguishes:

```text
"I don't know"
"there are several valid answers"
"the assumptions are inconsistent"
"the formalization failed"
```

Those are fundamentally different states.

## C4. Parameterize difficulty

For synthetic tasks vary:

```text
number of entities
number of relations
reasoning-chain depth
branching factor
constraint density
irrelevant information
linguistic paraphrasing
implicit vs explicit relations
number of possible models
distance between relevant statements
```

This allows scaling curves rather than one aggregate score.

## C5. Freeze benchmark splits

Maintain:

```text
development
validation
test
```

The final test set must not drive prompt development.

---

# Stage D — Establish baselines

A research result is meaningless without credible alternatives.

The minimum baseline family should be:

```text
B0  Direct LLM answer

B1  LLM with explicit reasoning/self-reflection

B2  LLM → Ein, one-shot

B3  LLM → Ein → generic retry

B4  LLM → Ein → verdict feedback

B5  Full iterative Ein feedback
```

Where possible add another symbolic backend or structured reasoning approach.

The critical comparison is not simply:

```text
LLM vs Ein
```

because the full system consumes additional inference calls.

The stronger comparison is:

```text
same model
similar inference budget
different feedback information
```

This isolates the value of symbolic verification.

# Stage E — Build the iterative formalization loop

Now close the loop.

## E1. Define the state machine

For example:

```text
GENERATE
   │
   ▼
PARSE
   ├── invalid ─────► REPAIR
   │
   ▼
ANALYZE
   ├── contradiction ─► REPAIR
   ├── ambiguous ─────► REPAIR
   ├── incomplete ─────► REPAIR
   │
   ▼
SOLVE
   │
   ▼
ANSWER
```

Every transition must be logged.

## E2. Repair instead of regenerate

Compare two strategies:

```text
regenerate the entire theory

vs

edit the existing theory
```

Repair is potentially valuable because Ein can localize failure.

The model might receive:

```text
Original statement

Current theory

Diagnostic:
Query variable ?owner is not constrained through any path
involving relation pet-loc.

Task:
Repair the theory using only information justified by
the original statement.
```

## E3. Protect against feedback-induced hallucination

A dangerous failure mode is:

```text
Ein: theory is ambiguous
LLM: invents an additional constraint
Ein: unique
```

The resulting formal theory is internally valid but semantically false.

Therefore every repair must be judged against the source.

Introduce:

```text
semantic faithfulness
```

as a first-class metric.

## E4. Termination policy

The loop terminates on:

```text
verified success
unrecoverable invalidity
iteration budget
token budget
solver resource budget
repeated identical theory
repair cycle
```

Detect cycles by canonicalized program hashes.

# Stage F — Make symbolic feedback progressively richer

The core research variable is the **information supplied by Ein to the neural formalizer**.

Define feedback levels.

## F0 — no feedback

```text
try again
```

## F1 — syntactic feedback

```text
undefined relation
type mismatch
arity mismatch
```

## F2 — verdict

```text
SAT
UNSAT
AMBIGUOUS
```

## F3 — cardinality/model feedback

```text
4 valid models remain
query has 3 possible bindings
```

## F4 — counterexample/model difference

Show how two valid models differ:

```text
Model A:
    owner(zebra) = Alice

Model B:
    owner(zebra) = Bob

Relevant difference:
    ...
```

This tells the formalizer exactly what remains underconstrained.

## F5 — unsat core

For inconsistent theories:

```text
These source-derived constraints jointly imply contradiction:
    ...
```

## F6 — dependency information

For example:

```text
query ?owner
    depends on nationality
    depends on house
    has no dependency path to pet
```

## F7 — provenance

Expose relevant derivation chains:

```text
fact X
  ← rule R
     ← fact A
     ← fact B
```

## F8 — combined structured diagnostic

The full feedback object might contain:

```json
{
  "verdict": "ambiguous",
  "models": 4,
  "query_values": ["Alice", "Bob"],
  "model_difference": "...",
  "missing_dependency": "...",
  "relevant_provenance": [...]
}
```

The system should not assume F8 is best.

That is an empirical question.

# Stage G — Ablation program

This is where the architecture becomes a research experiment.

## G1. Retry-control ablation

Compare:

```text
one-shot
generic retry
Ein-guided retry
```

This tests whether improvement comes merely from additional inference.

## G2. Verdict ablation

Compare:

```text
generic failure
vs
SAT/UNSAT/AMBIGUOUS
```

## G3. Unsat-core ablation

Compare:

```text
UNSAT
vs
UNSAT + core
```

Measure repair success.

## G4. Provenance ablation

Compare:

```text
diagnostic without provenance
vs
diagnostic with provenance
```

## G5. Model-difference ablation

For ambiguity:

```text
"4 models remain"
```

versus:

```text
two representative models + their relevant difference
```

## G6. Feedback-size ablation

Compare:

```text
minimal diagnostic
medium diagnostic
complete derivation trace
```

More information may actually make the model worse.

## G7. Iteration-depth ablation

Measure:

```text
0
1
2
3
...
```

repair iterations.

Plot marginal improvement against cost.

## G8. Formal representation ablation

Potentially compare:

```text
direct Ein generation
```

against:

```text
NL → structured semantic representation → Ein
```

This tests whether explicit decomposition improves autoformalization.

## G9. Theory-library ablation

Compare:

```text
no stdlib
minimal stdlib
full stdlib
```

This answers how much performance comes from reusable human-provided theory versus generated reasoning.

# Stage H — Define rigorous metrics

Do not reduce evaluation to answer accuracy.

Measure at least four layers.

## H1. Final-task metrics

```text
answer accuracy
exact match
unique-answer accuracy
ambiguity detection
contradiction detection
```

## H2. Formalization metrics

```text
parse success
type correctness
solver acceptance
semantic faithfulness
constraint recall
constraint precision
```

Synthetic tasks with canonical source theories make the last two measurable.

## H3. Repair metrics

```text
fraction repaired
iterations to repair
new errors introduced by repair
semantic hallucination rate
repair-cycle rate
```

## H4. System metrics

```text
LLM calls
input/output tokens
wall-clock latency
Ein runtime
search nodes
saturation rounds
memory
cost per correctly solved task
```

An especially useful metric is:

```text
P(answer correct | Ein certifies unique model)
```

This measures whether symbolic certification is a useful reliability signal.

Another:

```text
P(formalization faithful | Ein certifies unique model)
```

The difference between these two is important: a formally valid model can represent the source incorrectly.

# Stage K — Generalization experiments

Avoid demonstrating only benchmark memorization or prompt specialization.

## K1. Linguistic paraphrase

Same formal problem, many surface realizations.

Measure invariance.

## K2. Structural generalization

Train/develop prompts on smaller problems and evaluate larger ones.

For example:

```text
development: 3–5 entities
test:        8–15 entities
```

## K3. Cross-domain transfer

Develop using ordering and Zebra-like tasks.

Evaluate unseen reasoning families.

## K4. Novel relation vocabulary

Replace familiar names:

```text
left-of
```

with arbitrary relations:

```text
zorps
```

while explaining their semantics in the problem.

This separates relational reasoning from lexical priors.

## K5. Adversarial irrelevant information

Insert facts that are:

```text
irrelevant
redundant
distracting
superficially similar
```

and measure robustness.

# Stage L — Compare symbolic representations

Once Ein itself is established, ask whether its representation has specific advantages.

Possible comparison:

```text
Ein
SMT encoding
Datalog encoding
general-purpose code execution
proof-assistant encoding
```

Do not attempt to prove that one representation is universally superior.

Instead ask narrower questions:

```text

Which produces the most useful repair diagnostics?

Which detects semantic incompleteness?

Which yields the highest verified-answer precision?

Which requires the least generated formal text?
```

This can become a substantial research contribution on its own.

# Stage M — Formalize the conceptual model

The paper should describe Ein mathematically, independently of the Rust implementation.

For example define a knowledge state roughly as:

$$
K=(O,R,F,\Gamma,P)
$$

where:

* (O): objects;
* (R): relations;
* (F): known facts;
* (\Gamma): rules/constraints;
* (P): provenance.

Define saturation as a monotone operator:

$$
T_\Gamma(K)
$$

and fixpoint:

$$
K^*=\operatorname{lfp}(T_\Gamma).
$$

Then define hypotheses/commitments and model space.

The search process operates over candidate extensions:

$$
K^* \subseteq M
$$

subject to constraints:

$$
M \models \Gamma.
$$

Then:

$$
|\mathcal M|=0
\Rightarrow \text{contradiction}
$$

$$
|\mathcal M|=1
\Rightarrow \text{unique model}
$$

$$
|\mathcal M|>1
\Rightarrow \text{ambiguity}.
$$

Then describe autoformalization as synthesis:

$$
A_\theta(x)\rightarrow T
$$

where (x) is natural language and (T) an Ein theory.

Ein evaluates:

$$
E(T)\rightarrow (v,d)
$$

with verdict (v) and diagnostic (d).

Iterative repair becomes:

$$
T_{i+1}=A_\theta(x,T_i,E(T_i)).
$$

This gives the entire project a clean research formulation:

$$
x
\rightarrow T_0
\rightarrow E(T_0)
\rightarrow T_1
\rightarrow E(T_1)
\rightarrow\cdots
\rightarrow T_n.
$$

Now the central empirical question can be stated precisely:

$$
P(\text{faithful}(T_n)\land\text{correct}(T_n))
$$

as a function of the feedback supplied by (E).

# Stage N — Reproducibility

Level D requires someone else to be able to reproduce the central tables.

Provide one canonical workflow:

```bash
ein-research download-benchmark
ein-research generate
ein-research evaluate
ein-research report
```

or equivalent.

Freeze:

```text
benchmark versions
model identifiers
prompts
random seeds
Ein commit
stdlib commit
configuration
raw model outputs
generated Ein programs
solver outputs
evaluation results
```

Store each experiment as an immutable record.

For example:

```text
docs/experiments/
  experiment-0042/
    config.json
    prompt.txt
    tasks.jsonl
    generations.jsonl
    theories/
    solver-results.jsonl
    metrics.json
```

Final plots and tables should be generated directly from these records.

# Stage O — Produce the central research result

By this point the project should be able to support a claim of the form:

> Structured symbolic diagnostics improve iterative autoformalization compared with direct answering, one-shot formalization, generic retries, and self-refinement under comparable inference budgets.

Or perhaps the result will be narrower:

> Unsat-core feedback substantially improves repair of over-constrained theories, while full provenance provides little additional benefit.

That would also be a good result.

A negative result is acceptable:

> Symbolic verification dramatically increases precision of accepted answers but does not improve overall task accuracy because semantic misformalization dominates.

That is still research.

Do not design the experiment around obtaining a predetermined positive conclusion.

   9.2 What it cannot catch
   9.3 Faithfulness vs satisfiability
   9.4 Neural/symbolic boundary

The distinction between **formal correctness** and **semantic faithfulness** deserves particular emphasis.

Ein can prove:

```text
the generated theory has exactly one model
```

but this does **not** prove:

```text
the generated theory faithfully represents the English statement.
```

That gap is arguably one of the most interesting research problems in the entire project.

# Level progression

I would define the milestones precisely.

**Level A — Symbolic engine.** Ein independently demonstrates a substantial reasoning system: representation, saturation, constraints, model search, provenance, diagnostics and testing.

**Level B — Autoformalization system.** Previously unseen natural-language tasks can automatically become executable Ein theories and answers.

**Level C — Research system.** Iterative symbolic feedback exists, there are multiple reasoning domains, credible baselines, quantitative benchmarks, ablations and failure analysis. The system supports an empirical claim.

**Level D — Complete research artifact.** Level C plus formal treatment, heterogeneous and frozen benchmark, generalization/scaling experiments, rigorous faithfulness analysis, reproducible experimental infrastructure, released raw results, technical paper and a minimal end-to-end demonstration.

The transition that matters most is therefore:

```text
A
symbolic reasoning engine
        ↓
B
automatic theory synthesis
        ↓
C
controlled experiments about
neural ↔ symbolic interaction
        ↓
D
reproducible empirical + formal
research contribution
```

The defining characteristic of **Level D is not feature completeness**. Ein can still have an enormous roadmap. Level D is reached when there is a **well-defined research hypothesis, an implemented system capable of testing it, controlled evidence that distinguishes competing explanations, a formal account of what the system does, and enough released material for another researcher to reproduce or challenge the result.**
