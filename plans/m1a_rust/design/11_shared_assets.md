# 11 — Shared assets: one stdlib, one corpus

**Settles:** how ein.py and ein.rs read the *same* `.ein` library and the
*same* example corpus, and how drift is detected.
**Phase:** [P1a.0](../p1a.0_conformance_harness/README.md), stage
[S1a.0.3](../p1a.0_conformance_harness/s1a.0.3_shared_stdlib_and_examples.md).

---

## 1. Why this is a correctness requirement

A forked stdlib makes every parity result meaningless: a T2 diff would
report "the engines disagree" when in fact the *programs* differ. The
stdlib is 1 231 lines of ein-lang across seven modules
(`algebra` 454, `slots` 439, `bijection` 143, `elim` 76, `typing` 63,
`closure` 35, `macro` 21), and `zebra2.ein` imports from three of them.
It is not test data — it is part of the semantics under test.

The same argument holds, more weakly, for `examples/`: it is the corpus,
and a corpus that differs between the two suites is two corpora.

---

## 2. Where things are today

```
ein.py/src/ein/stdlib/*.ein          ← the stdlib, inside the Python package
examples/**/*.ein                    ← the corpus, at repo root
ein.py/tests/golden/**               ← DOT / trace / dump goldens
```

- `imports._stdlib_root()` returns `Path(ein.__file__).parent / "stdlib"`
  — i.e. *the installed package directory*. That is correct for a wheel
  and is why the stdlib lives there.
- `pyproject.toml` ships it as package data
  (`"ein" = ["stdlib/*.ein", "stdlib/**/*.ein"]`).
- `imports.stdlib_macro_names()` **parses `macro.ein` at runtime** to
  learn which macro names `std.macro` exports (so the S1.8a.f20
  unimported-macro check is derived, not hardcoded). Any relocation must
  keep that working.
- Tests already reach the repo root for examples
  (`REPO = Path(__file__).resolve().parents[2]`), so `examples/` needs no
  move.

---

## 3. Decision

**The stdlib moves to repo-root `stdlib/`, which becomes the single
source of truth. Neither implementation keeps a checked-in copy.**

```
stdlib/
├── README.md
├── MANIFEST.sha256        ← one line per module: <sha256>  <name>.ein
├── algebra.ein
├── bijection.ein
├── closure.ein
├── elim.ein
├── macro.ein
├── slots.ein
└── typing.ein
```

### Resolution order — identical in both implementations

1. `$EIN_STDLIB` — an explicit override. Always wins. This is what the
   conformance harness sets so both engines demonstrably read the same
   bytes.
2. **The repo checkout**: `stdlib/` found by walking up from the
   binary/package location and confirmed by the presence of
   `MANIFEST.sha256`. A source checkout is always authoritative, so
   editing a module takes effect without a rebuild or reinstall.
3. **The packaged / embedded copy** — the wheel's `ein/stdlib/` for
   Python, the `include_dir!`-embedded tree for the Rust binary.

Step 3 keeps the two distribution promises intact: `pip install ein`
still works, and `ein.rs` still ships as one self-contained binary.

### Packaging

- **Python**: `ein.py/src/ein/stdlib/` is removed from git and
  `.gitignore`d; an **in-tree PEP 517 backend** (`ein.py/_build.py`,
  `build-backend = "_build"` + `backend-path = ["."]`) delegates every hook
  to setuptools and copies `stdlib/` into it on the way to a wheel, an sdist
  or an editable install. `_stdlib_root()` becomes the three-step chain
  above. Installed behaviour is unchanged.

  It was a `[tool.setuptools.cmdclass] build_py` entry until 2026-08-18 and
  that never worked: a cmdclass module is resolved under `package-dir`, which
  `packages.find`'s `where = ["src"]` fills in *before* the field is expanded,
  so `_build.py` at the project root was searched for at `src/_build.py` and
  every install died with `ModuleNotFoundError: _build` while still gathering
  build requirements. Two consequences of the mechanism are load-bearing and
  are tested rather than assumed: `MANIFEST.in` must ship `_build.py` in the
  sdist (an sdist that omits its own backend cannot be built at all), and the
  copy now lands in a *checkout* too, so anything enumerating `.ein` files
  must read `stdlib/` and not the package copy.
- **Rust**: `include_dir!("$CARGO_MANIFEST_DIR/../../stdlib")` in
  `ein-ir`, exposed as an in-memory filesystem behind the same
  `StdlibSource` trait the on-disk path implements.

### Drift detection

- `stdlib/MANIFEST.sha256` is regenerated by a script and checked in.
- CI runs `stdlib-check`: the manifest matches the files, the Python
  packaged copy (when built) matches, and the Rust embedded copy matches
  (a build-time `const` digest compared against the manifest).
- The manifest hash lands in `.einb`'s `META`
   ([10](10_binary_format.md) §4), so a stdlib edit invalidates every
   derived artefact automatically.

## 4. The corpus

`examples/` stays where it is. What is added is an explicit **manifest**
so both suites enumerate the same entries with the same run matrix:

```toml
# conformance/corpus.toml
[[entry]]
path   = "examples/zebra2.ein"
group  = "positive"
runs   = ["solve", "solve -e", "solve -n 3", "solve --trace", "saturate",
          "render rules", "render constraints", "render lattice"]
levers = "all"          # the SolverConfig on/off matrix
slow   = true

[[entry]]
path   = "examples/broken/unclosed_paren.ein"
group  = "parse-negative"
runs   = ["parse"]
```

- Generated once from the tree, then maintained by hand; a CI check fails
  on any `.ein` under `examples/` or `stdlib/` that has no entry, so the
  corpus cannot silently miss a file. This is the mechanical version of
  the rule [`examples/README.md`](../../../examples/README.md) already
  states in prose ("one line per file / sub-dir").
- `slow = true` entries run in the nightly tier only.
- The load-negative fixtures (`KBLoadError` cases currently embedded in
  `ein.py/tests/**` as inline source strings) are **extracted into
  `examples/broken/load/*.ein`** with their expected message beside them,
  so both suites can assert the same text. That extraction is a task in
  [S1a.0.1](../p1a.0_conformance_harness/s1a.0.1_parity_contract_and_corpus.md);
  ein.py's tests then read the fixtures instead of inlining, which keeps
  them honest too.

## 5. Goldens

`ein.py/tests/golden/**` (2 `.golden` dumps, 15 `.dot` files, a trace
`.md`, a KB `.dot`) are cross-implementation artefacts living in a
Python-specific directory. Two options:

- **(a) read in place** — ein.rs's tests point at
  `../ein.py/tests/golden/`. Zero churn, slightly odd layout.
- **(b) promote to repo-root `testdata/golden/`** — symmetrical, costs a
  move plus a path update in ~6 Python test files.

**Recommendation: (a) now, (b) at the [P1a.5](../p1a.5_presentation/README.md)
gate**, when ein.rs starts *producing* goldens and the asymmetry would
become confusing. Tracked as Q-M1a.9.

---

## 6. Acceptance

- `EIN_STDLIB=/tmp/empty ein solve examples/zebra2.ein` fails with a
  clear "module not found" from **both** implementations (proving
  neither has a hidden fallback).
- Editing `stdlib/algebra.ein` in a checkout changes both engines'
  behaviour without a rebuild or reinstall.
- `stdlib-check` fails on a deliberately corrupted copy.
- The corpus completeness check fails when a new `examples/**/*.ein` is
  added without a manifest entry.
